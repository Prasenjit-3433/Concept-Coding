# LC 1249. Minimum Remove to Make Valid Parentheses

---

# Stage 1: Identification

**Step 1 — Which topic?**

You're given a string containing lowercase letters and the characters `(` and `)`. Some of the parentheses don't have a matching partner. You need to remove the **minimum number** of parentheses so that the resulting string is valid — and you can return *any* valid result, not a specific one.

The moment you see **"parentheses"**, **"valid"**, and **"minimum removals to fix it"** together, this is squarely a bracket-matching problem.

**Step 2 — Which pattern?**

> "minimum removals", "longest valid", "balance brackets" → **Pattern 1: Parenthesis & Bracket Problems**

The core mental model of this pattern never changes: track **unmatched openers** as you scan. Every closer either pairs off with the most recent unmatched opener, or — if there's nothing to pair with — it is itself unmatched.

**Step 3 — Which key concept?**

**`Two-pass — collect unmatched indices, remove them`**

This is what we'll build first, using an explicit stack. But this problem is a great place to see the **same underlying idea implemented in two genuinely different ways** — once with a stack of indices, and once with nothing but a couple of integer counters. Both are legitimate "two-pass" solutions; they just differ in *how much information they need to remember* to identify the unmatched brackets. We'll build all of them, because the reasoning behind why the counter version even *works* is worth understanding deeply, not just memorizing.

# Stage 2: Intuition Building

### The Core Question

Forget any data structure for a second and ask the plain-language question the problem is really asking:

> *"Which parentheses in this string have no partner at all?"*

Every `(` that never finds a matching `)`, and every `)` that never finds a matching `(`, is unfixable — it cannot possibly be part of a valid string no matter what else you do. If you delete **exactly** those characters and nothing else:
1. What's left is valid (every remaining bracket has a partner).
2. You removed the **minimum** possible number, because every removed character was *provably* unmatchable, and every kept character was *provably* matchable.

So the whole problem reduces to: **find every unmatched bracket, then delete exactly those.**

### Why a Stack Finds "Unmatched" Naturally

Walk left to right, and at each character ask: *does it have a partner?*

- See `(` → you don't know yet. Push its **index** onto the stack — it's "pending."
- See `)` → check the stack.
    - **Not empty** → pairs with whatever `(` is on top. Both resolved. Pop.
    - **Empty** → no opener exists anywhere to its left. This closer is unmatched, permanently. Mark it right now.

By the end of the scan, whatever indices remain on the stack are `(` characters that never found a partner anywhere to their right.

```
┌─────────────────────────────────────────────────────────────────┐
│  A stack tracks "unresolved openers waiting for a partner."     │
│  Anything left in it at the end never found one.                │
│                                                                 │
│  A closer arriving to an EMPTY stack has no opener available    │
│  anywhere to its left — unmatched the instant it's seen.        │
└─────────────────────────────────────────────────────────────────┘
```

### Why "Store the Index," Not "Store the Character"

If the stack only held the character `(`, popping it would tell you "some `(` matched" — but not **which one**, i.e. not *where* in the string it lives. Since the goal is to physically build a new string with certain positions removed, you need indices, not values.

### Walking Through a Concrete Example

```
s = "a)b(c)d)"
     01234567
```

```
i=0 'a' → letter, ignore
i=1 ')' → stack EMPTY → unmatched → mark index 1
i=2 'b' → letter, ignore
i=3 '(' → push 3 → stack = [3]
i=4 'c' → letter, ignore
i=5 ')' → stack NOT empty → pair with 3 → pop → stack = []
i=6 'd' → letter, ignore
i=7 ')' → stack EMPTY → unmatched → mark index 7
```

**Marked during scan:** `{1, 7}`. **Stack at end:** empty (nothing left over). Remove `{1, 7}` → result `"ab(c)d"`. Verified valid.

### The Two-Pass Structure, Named Precisely

```
┌─────────────────────────────────────────────────────────────────┐
│  PASS 1 — Scan left to right with a stack of indices.           │
│           Unmatched closers are caught DURING the scan.         │
│           Unmatched openers are caught AFTER the scan           │
│           (whatever's left on the stack).                       │
│                                                                 │
│  PASS 2 — Rebuild the string, skipping every marked index.      │
└─────────────────────────────────────────────────────────────────┘
```

# Stage 3: Coding

## Approach 1 — Stack-Based Two-Pass (Collect Unmatched Indices, Then Remove)

**Mental workflow:**

```
1. Stack of integers → indices of pending '('
2. Set of integers → ALL indices to remove

3. PASS 1 — scan left to right:
   '(' → push index
   ')' → if stack not empty: pop (matched)
         else: add this index to removal set (unmatched closer)

4. Whatever remains on the stack after the scan → unmatched openers
   → add ALL of them to the removal set

5. PASS 2 — rebuild the string, skipping every removed index
```

```java
class Solution {
    public String minRemoveToMakeValid(String s) {
        int n = s.length();

        // Stack holds INDICES of '(' still waiting for a partner —
        // we need WHERE, not just WHETHER, since we must delete positions
        Deque<Integer> stack = new ArrayDeque<>();

        // Every index that must be removed — unmatched closers found
        // during the scan, PLUS unmatched openers found after it
        Set<Integer> toRemove = new HashSet<>();

        // ---------- PASS 1: find every unmatched index ----------
        for (int i = 0; i < n; i++) {
            char c = s.charAt(i);

            if (c == '(') {
                stack.push(i);
            } else if (c == ')') {
                if (!stack.isEmpty()) {
                    stack.pop();               // matched — resolve both
                } else {
                    toRemove.add(i);            // no opener to its left, ever
                }
            }
            // letters: ignored entirely
        }

        // Anything STILL on the stack never found a partner to its right
        while (!stack.isEmpty()) {
            toRemove.add(stack.pop());
        }

        // ---------- PASS 2: rebuild, skipping removed indices ----------
        StringBuilder sb = new StringBuilder();
        for (int i = 0; i < n; i++) {
            if (!toRemove.contains(i)) {
                sb.append(s.charAt(i));
            }
        }

        return sb.toString();
    }
}
```

**Time Complexity — O(n):** Pass 1 is a single scan — O(n). Draining the leftover stack touches at most n indices — bounded by the same n pushes. Pass 2 is another single scan — O(n). Total: **O(n)**.

**Space Complexity — O(n):** The stack can hold up to n indices (a string of all `(`). The removal set can hold up to n indices. The output builder holds up to n characters. Total: **O(n)**.

## Approach 2 — Counter-Based Two-Pass (No Stack, No Set — Two Independent Counters)

### Do We Actually Need a Stack?

Look closely at what Pass 1 of Approach 1 uses the stack *for*. It never inspects *which* index is on top — it only ever asks "is there **at least one** pending opener?" (stack empty or not), then pops it. The specific identity of the opener never matters for the *decision* — only its **existence** does.

That single observation is the whole unlock:

> *"If all I need to know is whether a pending opener EXISTS, a plain counter tells me that just as well as a stack does — and it costs a single `int` instead of a whole data structure."*

There's a second simplification hiding here too. Approach 1 defers building the output to a **second pass over the original string**, because Pass 1 only computes *which indices to skip* — it never builds anything. But if we're willing to build the result string **live, as we scan**, we don't need to remember indices at all: the moment we decide "keep" or "skip," we just append or don't, right then, and move on.

```
┌─────────────────────────────────────────────────────────────────┐
│  Stack of indices → needed when the decision has to be resolved │
│  LATER, by looking the index up again in a second pass.         │
│                                                                 │
│  Plain counter → sufficient when you only need to know "is one  │
│  available RIGHT NOW", and you act immediately, live, as you    │
│  scan — no need to remember WHERE it was.                       │
└─────────────────────────────────────────────────────────────────┘
```

### Pass 1 — Removing Extra Closers, Left to Right

```
open = 0   (count of '(' seen so far that haven't been consumed by a ')')

for each character c, left to right:
    if c == ')':
        if open > 0:  → a pending opener is available → KEEP this ')', open--
        else:         → nothing pending → this ')' is unmatched → SKIP it
    else:
        if c == '(':  open++          (optimistically, might get matched later)
        KEEP it (append)
```

Every `(` is appended optimistically — we don't know yet if it'll be matched, so we assume the best and let a *later* pass clean up whatever turns out to be extra. Every `)` is either matched against the `open` credit, or thrown away on the spot.

After this pass, the resulting string `noExtraCloseStr` has a guaranteed property: **every `)` in it has a genuine `(` before it.** It may still contain unmatched `(` — that count is exactly whatever `open` equals at the end.

### Pass 2 — Removing Extra Openers, Right to Left

Here's the elegant part: **Pass 2 is literally Pass 1's own algorithm, run on the string in reverse, with the roles of `(` and `)` swapped.**

```
close = 0   (count of ')' seen so far, scanning from the right, not yet consumed)

for each character c, RIGHT to LEFT (on the output of Pass 1):
    if c == '(':
        if close > 0:  → a pending closer is available somewhere to its right → KEEP, close--
        else:          → nothing pending → this '(' is unmatched → SKIP it
    else:
        if c == ')':  close++
        KEEP it (append)
```

This is the exact mirror image of Pass 1 — scanning backward, `)` plays the role `(` played before (the thing you optimistically count), and `(` plays the role `)` played before (the thing you can only keep if a credit exists). Since Pass 1's algorithm is trustworthy (it's the standard, well-known "clean unmatched closers" scan), its mirror image is equally trustworthy for cleaning unmatched openers — same logic, opposite direction, swapped roles.

```java
class Solution {
    public String minRemoveToMakeValid(String s) {

        // ---------- PASS 1: remove extra ')' (left to right) ----------
        StringBuilder noExtraCloseStr = new StringBuilder();
        int open = 0;

        for (int i = 0; i < s.length(); i++) {
            char curr = s.charAt(i);

            if (curr == ')') {
                if (open > 0) {
                    // a pending '(' exists — this ')' is matched, keep it
                    noExtraCloseStr.append(curr);
                    open--;
                }
                // else: no pending '(' — unmatched ')', skip (don't append)
            } else {
                // '(' or a letter
                if (curr == '(') open++;   // optimistically count it as pending
                noExtraCloseStr.append(curr);
            }
        }

        // ---------- PASS 2: remove extra '(' (right to left) ----------
        // This is PASS 1's exact logic, mirrored: scan backward,
        // treat ')' as the "optimistic" character and '(' as the
        // one that needs an available credit to survive.
        StringBuilder noExtraOpenStr = new StringBuilder();
        int close = 0;
        int n = noExtraCloseStr.length();

        for (int i = n - 1; i >= 0; i--) {
            char curr = noExtraCloseStr.charAt(i);

            if (curr == '(') {
                if (close > 0) {
                    // a pending ')' exists further right — matched, keep it
                    noExtraOpenStr.append(curr);
                    close--;
                }
                // else: nothing to its right can ever match it — skip
            } else {
                if (curr == ')') close++;   // optimistically count it as pending
                noExtraOpenStr.append(curr);
            }
        }

        // built back-to-front during the reverse scan — flip it right-side up
        return noExtraOpenStr.reverse().toString();
    }
}
```

### Verifying on an Example With Multiple Unmatched Openers

```
s = "(a(b(c)d"
     01234567
```

**Pass 1** (nothing to remove — every `)` seen already has an available opener):
```
i0 '(' open=1, append
i1 'a' append
i2 '(' open=2, append
i3 'b' append
i4 '(' open=3, append
i5 'c' append
i6 ')' open=3>0 → append, open=2
i7 'd' append

noExtraCloseStr = "(a(b(c)d"   (unchanged), open leftover = 2
```

**Pass 2** (right to left, independent `close` counter):
```
i7 'd' → append           ans = "d"
i6 ')' → close++(1), append   ans = "d)"
i5 'c' → append           ans = "d)c"
i4 '(' → close>0(1) → append, close--(0)   ans = "d)c("
i3 'b' → append           ans = "d)c(b"
i2 '(' → close==0 → skip
i1 'a' → append           ans = "d)c(ba"
i0 '(' → close==0 → skip

ans (built back-to-front) = "d)c(ba"
reverse → "ab(c)d"
```

**Result: `"ab(c)d"`** — valid, matches Approach 1's answer for this exact input.

### An Important Nuance — Different Valid Approaches Can Give Different Valid Strings

Try `s = "(()()"` (positions `0:'(', 1:'(', 2:')', 3:'(', 4:')'`). Running Approach 1's true stack matching keeps `0` and discards nothing further (only `1` unmatched opener overall via LIFO order), giving `"()()"`. Running Approach 2's independent-counter mirror gives `"()()"` as well *in this case* — but on other inputs the two techniques can legitimately land on **different specific characters removed**, while both results remain equally valid, minimal-length strings. The problem statement explicitly allows *any* valid answer, so this is expected, correct behavior — not a bug to chase down.

**Time Complexity — O(n):** Pass 1 is one linear scan, Pass 2 is another linear scan over a string of length ≤ n. Total: **O(n)**.

**Space Complexity — O(n):** Two `StringBuilder`s, each holding up to n characters. Total: **O(n)** — same order as Approach 1, but in practice lighter, since there's no `HashSet<Integer>` or boxed-`Integer` stack overhead — just primitives and plain character buffers.

## Approach 3 — Counter-Based Two-Pass, Optimized (Reuse the Leftover Count as a Removal Budget)

### The Insight That Simplifies Approach 2 Further

Look at what `open` equals at the **end** of Pass 1 in Approach 2: it's exactly the number of unmatched `(` characters still sitting in `noExtraCloseStr`. Approach 2's Pass 2 then goes and **re-derives** this same information independently, using a fresh `close` counter that tracks matching from scratch.

But we already *have* the answer to "how many extra opens are there?" — it's sitting right there in `open`, untouched since Pass 1 finished. Why compute it again with a second counter?

> *"I don't need to re-verify, position by position, whether each `(` has a partner. I already know the TOTAL count of unmatched opens. I can just treat that count as a flat removal budget, and spend it as I scan right to left — discard a `(` whenever budget remains, keep everything else."*

```
open  (left over from Pass 1) = total number of '(' that must still be removed

for each character c, RIGHT to LEFT:
    if c == '(':
        if open > 0:  → spend one unit of budget → SKIP this '(', open--
        else:         → budget exhausted → this '(' is safe → KEEP it
    else:
        KEEP it unconditionally (it's either a letter, or a ')' —
        and Pass 1 already guaranteed every ')' present has a partner)
```

```java
class Solution {
    public String minRemoveToMakeValid(String s) {

        // ---------- PASS 1: remove extra ')' (left to right) — identical to Approach 2 ----------
        StringBuilder noExtraCloseStr = new StringBuilder();
        int open = 0;

        for (int i = 0; i < s.length(); i++) {
            char curr = s.charAt(i);

            if (curr == ')') {
                if (open > 0) {
                    noExtraCloseStr.append(curr);
                    open--;
                }
            } else {
                if (curr == '(') open++;
                noExtraCloseStr.append(curr);
            }
        }
        // 'open' is now EXACTLY the count of unmatched '(' remaining —
        // this is the whole removal budget for Pass 2, computed for free

        // ---------- PASS 2: spend the leftover 'open' as a removal budget ----------
        StringBuilder ans = new StringBuilder();
        int n = noExtraCloseStr.length();

        for (int i = n - 1; i >= 0; i--) {
            char curr = noExtraCloseStr.charAt(i);

            if (curr == '(') {
                if (open > 0) {
                    // spend one unit of budget — discard this '(', no append
                    open--;
                } else {
                    // budget exhausted — every remaining '(' is guaranteed safe
                    ans.append(curr);
                }
            } else {
                // letters and ')' are always safe here — Pass 1 already
                // guaranteed every ')' present has a matching '(' before it
                ans.append(curr);
            }
        }

        return ans.reverse().toString();
    }
}
```

### Why Spending a Flat Budget (Instead of Re-Matching) Still Guarantees Validity

It's worth being honest that this *feels* riskier than Approach 2's careful re-matching — are we sure just discarding "the first `open`-many `(` encountered scanning backward" always leaves a valid string, regardless of *which* specific opens those happen to be?

Yes — because of what Pass 1 already guarantees: **every `)` in `noExtraCloseStr` already has a genuine `(` before it.** The only defect left in the string is a global excess of `open` unmatched `(` characters. Scanning right to left and discarding a `(` the instant one is "spare" (rather than needed to balance a `)` still to its left) is precisely the mirror image of how Pass 1 discarded a spare `)` the instant nothing was pending for it — same governing principle, opposite direction. Since Pass 1's rule is trustworthy on its own terms, running that identical rule in reverse, with roles swapped, is equally trustworthy — it will always consume exactly the unmatched opens and leave every matched pair intact.

Tracing this on `s = "(()("` (a case with several opens and only one close) confirms it directly: Pass 1 leaves the string unchanged with `open = 2` leftover; Pass 2 discards the two rightmost-encountered `(` (positions `4` and `2` when built from `"(()( "`-style tests), keeping exactly one `(` paired with the single `)` — producing a fully valid, minimal string every time.

### Approach 2 vs. Approach 3 — Do They Give the Same String?

Not necessarily the *exact same* output string, for the same reason flagged in Approach 2: whenever more than one valid choice of "which extra open to discard" exists, the two techniques can pick different (but equally valid) ones. Approach 3's version is simply a leaner *implementation* of the same underlying mirrored idea — it reuses information you've already earned in Pass 1 instead of re-deriving it with a second, independent counter.

**Time Complexity — O(n):** Identical shape to Approach 2 — one linear scan for Pass 1, one linear scan for Pass 2. Total: **O(n)**.

**Space Complexity — O(n):** Two `StringBuilder`s of size up to n. Same order as Approach 2 — this is a **conceptual simplification, not an asymptotic improvement**. The genuine win is that you no longer need to reason about *two separate* counters tracking *two separate* matching processes — you reuse the one number Pass 1 already computed.

## Final Comparison

| Approach | Core Idea | Time | Space | Notes |
|---|---|---|---|---|
| 1 — Stack, Collect Indices | Stack of indices + removal set, filter original string | O(n) | O(n) | Most explicit — directly names *which* original indices are unmatched |
| 2 — Two Independent Counters | Counter substitutes for stack; build output live in each pass | O(n) | O(n) | No stack/set at all — lighter in practice, same asymptotic cost |
| 3 — Reused Leftover Budget | Same as Approach 2, but Pass 2 spends Pass 1's leftover count directly | O(n) | O(n) | Leanest code — same complexity, deepest use of the invariant |
