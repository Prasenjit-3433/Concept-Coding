# LC 767. Reorganize String

---

# Stage 1: Identification

**Step 1 — Which topic?**

You're given a string `s`. Rearrange its characters (using every character exactly once) so that **no two adjacent characters are the same**. Return any valid rearrangement, or `""` if none exists.

**Step 2 — Which pattern?**

**Pattern 1: Standard Heap Problems** — specifically the **frequency-based greedy** sub-pattern. At every step you need to know "which remaining character is currently most urgent to place?" — and "most urgent" changes as characters get consumed.

**Step 3 — Which key concept?**

**Max-heap on character frequency — always place the most frequent remaining character that is legal to place right now (not equal to what you just placed), decrement, and reinsert.**

# Stage 2: Intuition Building

### Why does this need a heap at all? (The recognition test, applied here)

Ask the same question we've been asking throughout this pattern: *do I repeatedly need the current best (max, here) of a collection that keeps mutating?*

At every position in the output string, you want to place **whichever remaining character currently has the highest leftover count** — because if you don't spend down the most abundant character aggressively, it will pile up and eventually be forced into an adjacent collision with itself once everything else runs out. And after you place a character, its count drops by 1, and the "most abundant" character for the *next* slot might be a completely different one. That's the repeating "extract current best, mutate, ask again" shape — the exact heap-recognition trigger from Last Stone Weight and Minimum Cost to Connect Sticks, just now applied to *frequency* instead of *value*.

### Deriving the impossibility condition from first principles

Before even touching a heap, ask: when is this task **impossible**?

Think of the string as `n` slots to fill. If some character `c` has frequency `f`, and you want no two `c`'s adjacent, you need at least `f - 1` *other* characters to sit strictly between every pair of consecutive `c`'s. The tightest possible packing places a `c` in every other slot:

```
c _ c _ c _ c ...
```

For `f` copies of `c` to fit this way without collision, you need enough total slots that this alternating pattern still has room — the maximum `f` that can be packed into `n` slots this way is `⌈n/2⌉` (ceiling of half). The moment `f > ⌈n/2⌉`, there simply aren't enough "gaps" anywhere in a string of length `n` to keep every pair of `c`'s separated — it's a pigeonhole argument, not something recursion or a heap can work around.

```
if max frequency > ⌈n / 2⌉  →  return "" immediately, no arrangement can ever work
```

Your own check — `map.get(ch) > Math.ceil((double) n/2)` — is exactly this, computed incrementally as you count. Nice catch also stress-testing it against the single-character-only case (`n > 1 && map.size() == 1`): worth noting that check is actually **redundant** — if `map.size() == 1`, that one character's frequency equals `n` itself, and `n > ⌈n/2⌉` is already true for any `n > 1`, so your first check already catches it. Good instinct to add a safety net, but it's provably subsumed.

### Why "always place the current most frequent" is actually safe (not just plausible)

Recognizing "I need the max repeatedly" tells you *how* to execute efficiently — it doesn't yet prove that greedily consuming the largest bucket first is *correct*. Here's the argument: if you ever delay placing the currently most-frequent character in favor of a less-frequent one, you let the big bucket's *relative* share of the remaining string grow even larger, since the total remaining slots shrink while that bucket's count doesn't. Push this too far, and the big bucket's count can exceed half of the *remaining* slots, at which point you're mathematically forced into an adjacent collision — the same pigeonhole trap as the impossibility check, just triggered mid-construction instead of upfront. Always draining the biggest bucket first keeps every bucket's share as balanced as possible for as long as possible, which is exactly what prevents that trap from ever springing, given the upfront check already confirmed a solution exists.

### Two ways to enforce "not the same as what I just placed"

**Idea A — pop one at a time, look back at what you just placed.** This is your own approach: pop the current max; if it matches the last character you appended, you can't use it *yet* — so temporarily pop the second-highest instead, place that, and put the first one back for later. This is a completely general technique (it also handles harder variants like "no two identical characters within distance k," e.g. Task Scheduler), so it's good machinery to have — it's just more than this particular problem strictly requires.

**Idea B — pop the top *two* together, every round, and place both.** Since gap-of-1 (just "not adjacent") is the *weakest* possible spacing constraint, there's a simpler guarantee available: if you always grab the two currently-most-frequent characters and place them back-to-back, they are — by construction — two *different* characters (you popped two distinct heap entries), so they can never collide with each other. And because you always place the biggest two together, the same greedy "keep buckets balanced" argument from above still applies. This sidesteps the "look back at the last placed char" bookkeeping entirely.

### A genuinely different idea — placement by index, no heap at all

Here's a completely different way to satisfy "not adjacent," inspired by the observation you worked out yourself: instead of deciding characters one output-slot at a time, decide **slot order** once, up front, then walk through the sorted-by-frequency characters and drop each one into the next slot in that order.

**The slot order:** fill index `0`, then `2`, then `4`, ... (all even indices, low to high) — and once you run past the end, continue at index `1`, then `3`, then `5`, ... (all odd indices, low to high).

Why does filling "every other slot" in this specific order guarantee no adjacency? Physically adjacent output positions are `i` and `i+1`. Under this fill order, position `i` and position `i+1` are visited **far apart in time** — one belongs to the "even pass," the other to the "odd pass," and an entire half of the string's worth of placements happens in between. Since no character's frequency ever exceeds `⌈n/2⌉` (guaranteed by the impossibility check), even the single most frequent character — which gets placed first and most densely — never has enough copies to still be active by the time the fill order wraps from evens into odds and starts revisiting nearby physical positions. Lower-frequency characters, filled afterward, have even less chance of colliding.

**A subtlety worth flagging precisely, since it's easy to get subtly wrong:** the wraparound rule must be **"reset the index to 1 once it runs past the last valid index,"** not a blind `(index + 2) % n`. Watch what happens with `n = 9` (odd) versus `n = 8` (even):

```
n = 9 (odd):  0 → 2 → 4 → 6 → 8 → (8+2)%9=1 → 3 → 5 → 7 → (7+2)%9=0
              This visits ALL 9 indices exactly once before repeating —
              because gcd(2, 9) = 1, stepping by 2 modulo 9 cycles through
              every residue. The modulo trick "just works" here.

n = 8 (even): 0 → 2 → 4 → 6 → (6+2)%8=0 → 2 → 4 → 6 → ...
              This NEVER touches an odd index at all — because
              gcd(2, 8) = 2, stepping by 2 modulo 8 only cycles through
              the 4 even residues, forever. Silently broken.
```

So the correct, general rule is an **explicit reset**, not a raw modulo:

```
if index >= n:  index = 1     (jump to the start of the odd half)
```

This works for both even and odd `n`, whereas the pure `(index + 2) % n` version you discovered only happens to work when `n` is odd — worth knowing precisely *why* it worked in your own test case, and why it would silently break on an even-length input.

# Stage 3: Coding

## Approach 1 — Max-Heap, Single-Pop with Lookback (your approach, refined)

This is Idea A from Stage 2 — general-purpose, handles the "don't repeat what I just placed" rule explicitly by deferring the top pick one round when necessary.

```java
import java.util.*;

class Solution {
    public String reorganizeString(String s) {
        int n = s.length();

        // Step 1: frequency count + upfront impossibility check
        // WHY ceil(n/2): pigeonhole — no character can occupy more than
        // half the slots (rounded up) without forcing an adjacent collision
        Map<Character, Integer> freq = new HashMap<>();
        for (char ch : s.toCharArray()) {
            freq.put(ch, freq.getOrDefault(ch, 0) + 1);
            if (freq.get(ch) > (n + 1) / 2) return "";
        }

        // Step 2: max-heap on frequency — always know the currently
        // most-abundant remaining character in O(log k), k = distinct chars
        PriorityQueue<int[]> maxHeap = new PriorityQueue<>((a, b) -> b[0] - a[0]);
        for (Map.Entry<Character, Integer> e : freq.entrySet()) {
            maxHeap.offer(new int[] { e.getValue(), e.getKey() });
        }

        StringBuilder ans = new StringBuilder();

        while (!maxHeap.isEmpty()) {
            int[] top = maxHeap.poll();

            // Legal to place directly — doesn't match the last char appended
            if (ans.length() == 0 || ans.charAt(ans.length() - 1) != (char) top[1]) {
                ans.append((char) top[1]);
                top[0]--;
            } else {
                // top clashes with last placed char — borrow the SECOND
                // most frequent character for this slot instead, and
                // save 'top' to be reinserted afterward
                if (maxHeap.isEmpty()) break; // no valid alternative — shouldn't
                                               // happen given the upfront check

                int[] second = maxHeap.poll();
                ans.append((char) second[1]);
                second[0]--;

                if (second[0] > 0) maxHeap.offer(second);
            }

            if (top[0] > 0) maxHeap.offer(top);
        }

        return ans.length() == n ? ans.toString() : "";
    }
}
```

**Time Complexity — O(n log k):**
where `k` is the number of distinct characters (at most 26 for lowercase letters, so effectively O(n)). Building the frequency map is O(n). Building the heap is O(k log k). The main loop runs `n` times (one character placed per iteration in the common case), and each iteration does at most two `poll()`/`offer()` pairs, each O(log k). Total: O(n log k).

**Space Complexity — O(k):**
The heap and frequency map hold at most `k` entries (bounded by the alphabet size, so effectively O(1) for lowercase-only strings). The output `StringBuilder` holds O(n) characters, which is unavoidable output space.

## Approach 2 — Max-Heap, Pop-Two-Together (Idea B — codestorywithMIK's Approach 1)

Since "not adjacent" only ever needs a gap of exactly 1, popping the top *two* distinct entries every round and placing them consecutively automatically satisfies the constraint — no lookback bookkeeping needed at all.

```java
import java.util.*;

class Solution {
    public String reorganizeString(String s) {
        int n = s.length();

        Map<Character, Integer> freq = new HashMap<>();
        for (char c : s.toCharArray()) {
            int count = freq.getOrDefault(c, 0) + 1;
            if (count > (n + 1) / 2) return "";
            freq.put(c, count);
        }

        PriorityQueue<int[]> maxHeap = new PriorityQueue<>((a, b) -> b[0] - a[0]);
        for (char c : freq.keySet()) {
            maxHeap.offer(new int[] { freq.get(c), c });
        }

        StringBuilder sb = new StringBuilder();

        // Grab the two currently most-frequent characters each round —
        // they are DIFFERENT characters by construction (two distinct
        // heap entries), so placing them back-to-back never collides
        while (maxHeap.size() >= 2) {
            int[] first = maxHeap.poll();
            int[] second = maxHeap.poll();

            sb.append((char) first[1]);
            sb.append((char) second[1]);

            first[0]--;
            second[0]--;

            if (first[0] > 0) maxHeap.offer(first);
            if (second[0] > 0) maxHeap.offer(second);
        }

        // Exactly one character type may remain if n is odd —
        // safe to place alone at the very end (nothing comes after it)
        if (!maxHeap.isEmpty()) {
            sb.append((char) maxHeap.poll()[1]);
        }

        return sb.toString();
    }
}
```

**Time Complexity — O(n log k):**
Same shape as Approach 1 — each round does two `poll()`s and up to two `offer()`s, all O(log k), across roughly `n/2` rounds. Total: O(n log k).

**Space Complexity — O(k):**
Heap and map bounded by alphabet size; output is O(n).

## Approach 3 — No Heap: Sort by Frequency, Fill Even-then-Odd Indices

Idea from Stage 2's index trick — this is the approach that doesn't need a heap at all, just one sort.

```java
import java.util.*;

class Solution {
    public String reorganizeString(String s) {
        int n = s.length();

        int[] freq = new int[26];
        for (char c : s.toCharArray()) {
            freq[c - 'a']++;
            if (freq[c - 'a'] > (n + 1) / 2) return "";
        }

        // Sort characters by frequency, descending
        // WHY sort once instead of a heap: we only need ONE global
        // ordering (most frequent → least frequent), not a repeatedly
        // updated "current max" — the placement order is decided
        // entirely upfront
        Integer[] order = new Integer[26];
        for (int i = 0; i < 26; i++) order[i] = i;
        Arrays.sort(order, (a, b) -> freq[b] - freq[a]);

        char[] result = new char[n];
        int index = 0;

        for (int charIdx : order) {
            int count = freq[charIdx];
            char ch = (char) ('a' + charIdx);

            while (count > 0) {
                // WHY explicit reset, not (index + 2) % n:
                // pure modulo only revisits every-other index forever
                // when n is even (gcd(2, n) = 2) — it never crosses
                // into the other half. An explicit reset to 1 is what
                // correctly forces the jump from "all evens done" to
                // "start of odds," for BOTH even and odd n.
                if (index >= n) {
                    index = 1;
                }
                result[index] = ch;
                index += 2;
                count--;
            }
        }

        return new String(result);
    }
}
```

**Time Complexity — O(n + k log k):**
Counting frequencies is O(n). Sorting the (at most 26) distinct characters by frequency is O(k log k) — a constant, since k ≤ 26. Filling the result array is one pass over all `n` characters. Total: **O(n)** in practice, since the sort is over a fixed-size alphabet.

**Space Complexity — O(n):**
The `result` char array holds `n` characters (this is also the output, so essentially unavoidable). The `order` array and frequency array are O(1) (bounded by alphabet size 26).

## Final Comparison

| Approach | Time | Space | Notes |
|---|---|---|---|
| Max-Heap, Single-Pop + Lookback | O(n log k) | O(k) + O(n) output | General-purpose; also solves harder "distance-k" variants |
| Max-Heap, Pop-Two-Together | O(n log k) | O(k) + O(n) output | Simplest heap version — exploits gap=1 being the weakest constraint |
| Sort + Even/Odd Index Fill | O(n) | O(n) | Best — no heap needed at all, since k ≤ 26 makes the "sort" essentially free |

## The Key Takeaway

```
┌───────────────────────────────────────────────────────────────────────┐
│  Two independent lessons from this problem:                           │
│                                                                       │
│  1. THE IMPOSSIBILITY CHECK IS A PIGEONHOLE ARGUMENT, NOT A HEURISTIC │
│     max frequency > ⌈n/2⌉  →  provably impossible, full stop.         │
│     Derive this BEFORE writing any placement logic — it's what        │
│     guarantees every later greedy step will actually succeed.         │
│                                                                       │
│  2. "NOT ADJACENT" IS THE WEAKEST SPACING CONSTRAINT — EXPLOIT IT.    │
│     A general "look back at what I just placed" heap technique        │
│     (Approach 1) always works, but for gap=1 specifically, you can    │
│     get away with much less machinery:                                │
│       - popping the top TWO heap entries together (Approach 2), or    │
│       - deciding the ENTIRE fill order once, upfront, via a single    │
│         sort — no heap, no re-querying "what's currently max"         │
│         at all (Approach 3).                                          │
│                                                                       │
│  3. THE EVEN/ODD INDEX TRICK — the subtle correctness point:          │
│     "index = (index + 2) % n" only coincidentally works when n is     │
│     ODD (gcd(2, n) = 1 guarantees every index gets visited exactly    │
│     once). For EVEN n, it silently loops through only half the        │
│     indices forever. The robust version is an EXPLICIT reset:         │
│     "if index >= n: index = 1" — this correctly forces the jump       │
│     from the even half to the odd half regardless of n's parity.      │
│                                                                       │
│  General signal for future problems: whenever a "no two adjacent      │
│  equal" or "at least k apart" constraint shows up, ask whether the    │
│  gap requirement is exactly 1 (weak — a one-time sort + placement     │
│  trick may suffice) or a general k (strong — you genuinely need the   │
│  heap's ability to re-query "current max" after every single          │
│  placement, since the greedy choice can change round to round).       │
└───────────────────────────────────────────────────────────────────────┘
```
