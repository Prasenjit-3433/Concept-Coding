# LC 1046. Last Stone Weight

---

# Stage 1: Identification

**Step 1 — Which topic?**

You're given an array of stone weights. Repeatedly: pick the **two heaviest** stones, smash them together. If they're equal, both vanish. If not, the lighter one's weight gets subtracted from the heavier one, and a new stone of that leftover weight goes back into the collection. Keep doing this until at most one stone remains — return its weight (or 0 if none remain).

The phrase that should jump out immediately: **"repeatedly find the two maximum values from a changing collection."** Not the maximum once — the maximum, **again and again**, from a collection that keeps shrinking and growing after every single operation.

**Step 2 — Which pattern?**

This is **Pattern 1: Standard Heap Problems** — direct heap usage with no extra bells attached (no size-k constraint, no two-group balancing, no k sorted sequences to merge). The heap itself *is* the entire algorithm here.

**Step 3 — Which key concept?**

**Max-heap simulation — repeatedly extract the two largest, combine, reinsert.**

---

# Stage 2: Intuition Building — How Do We Identify That We Need a Heap?

This is the single most important skill for this whole pattern, so let's build it slowly, from first principles, rather than just naming the data structure.

### What does the problem actually demand, operation by operation?

Strip away the "stones and smashing" story and ask: what are the *raw operations* this problem needs, over and over?

```
Operation A: "Give me the current largest element."
Operation B: "Give me the current second-largest element."
Operation C: "Remove those two elements from the collection."
Operation D: "Insert one new element (the leftover weight) back into the collection."
```

And critically — **this whole cycle repeats**, because after every smash, the collection has changed shape (two elements gone, possibly one new one added), and you need to find the new maximum and second-maximum all over again, from this *updated* collection.

### Why "just find the max" isn't the real signal

If the problem only ever asked for the maximum **once**, you wouldn't need any special data structure — a single linear scan does it in O(n), and that's the end of the story. The reason this problem is harder is that **finding the max is not a one-time question — it's a question you must be able to answer instantly, again and again, after the collection has been mutated.**

This is the exact recognition trigger from the pattern sheet:
> *"Do I need the running minimum or maximum of a dynamically changing set?"*

Say that sentence about this problem specifically: *"I need the running maximum (and second maximum) of a dynamically changing set of stones."* The moment you can honestly say that sentence about a problem, you should be reaching for a heap — because a heap is a data structure purpose-built to answer "what's the current best (min or max)?" in O(1), and to accept insertions/removals in O(log n), no matter how many times the collection changes.

### Why not just re-sort every time? (Building the intuition by first trying — and rejecting — the natural first idea)

The most natural first instinct, and a completely reasonable place to start, is: *"I need the two largest — let me just sort the array, grab the last two, and repeat."*

Walk through why this is expensive. Every single smash operation, under this approach, costs you:

```
1. Sort the entire array again          → O(n log n)
2. Pop the last two elements            → O(1)
3. Insert the new leftover weight       → O(n) if you want to keep it sorted (insertion point search + shift),
                                            or you just append and re-sort next time anyway
```

And you do this **once per smash**, and the number of smashes is roughly `n` (each smash removes 2 stones and, at most, puts 1 back — so the collection shrinks by at least 1 every time). That gives you roughly:

```
n smashes × O(n log n) per smash = O(n² log n)
```

That's a lot of *repeated, wasted* sorting work. Every time you sort the whole array from scratch, you're throwing away all the ordering information you already had, just to fix up the position of **one single new element** among elements that were already sorted a moment ago.

### The realization that leads straight to a heap

Here's the key mental shift: after a smash, the array isn't in total chaos — it was fully sorted a moment ago, and now you've removed two elements and inserted at most one new one. That is an **almost-sorted** situation. You don't need to re-establish order from scratch; you need a structure that can:

- Tell you the max instantly, **without a scan**
- Remove the max efficiently
- Accept a fresh insertion and automatically slot it into the right position, without re-sorting everything

That combination — instant access to the current max, cheap removal of the max, cheap insertion that preserves the max-ordering property — is *precisely* the definition of a **max-heap**. This isn't a coincidence; the three raw operations we listed earlier (extract-max, extract-second-max, insert-new-value) map onto exactly what a heap is designed to do in O(log n) each, instead of O(n log n) per cycle from re-sorting.

```
┌────────────────────────────────────────────────────────────────┐
│  The Heap Recognition Test, applied to this problem:           │
│                                                                │
│  "Do I repeatedly need the current best (min/max) from a set   │
│   that keeps changing (elements removed, new ones added)?"     │
│                                                                │
│  YES → reach for a heap. The heap's entire job is to keep      │
│        "who's currently on top" instantly available, cheaply   │
│        updated, without ever re-sorting the whole collection.  │
└────────────────────────────────────────────────────────────────┘
```

### Why max-heap specifically, not min-heap?

We always want the **two largest** stones at each step — a max-heap keeps the largest element at the root, giving O(1) peek and O(log n) extraction of exactly the value we need every single round.

### Walking Through the Example with This Lens

```
stones = [2, 7, 4, 1, 8, 1]
```

Build a max-heap from this array. The root is always the current maximum.

```
Round 1: extract max → 8, extract max again → 7
         smash: |8 - 7| = 1 → insert 1 back into the heap
         heap now conceptually holds: [2, 4, 1, 1, 1]

Round 2: extract max → 4, extract max again → 2
         smash: |4 - 2| = 2 → insert 2 back
         heap now conceptually holds: [1, 1, 1, 2]

Round 3: extract max → 2, extract max again → 1
         smash: |2 - 1| = 1 → insert 1 back
         heap now conceptually holds: [1, 1, 1]

Round 4: extract max → 1, extract max again → 1
         smash: |1 - 1| = 0 → both destroyed, nothing to insert
         heap now conceptually holds: [1]

Only one stone left → answer = 1
```

Every single "extract the two largest" and "insert the leftover" is an O(log n) heap operation — no re-sorting, no linear scans, ever.

### Stopping Condition

The game continues as long as **at least 2 stones remain** (you need two to smash). The moment the heap's size drops to 1 or 0, you're done.

```
if heap.size() == 0 → no stones left, return 0
if heap.size() == 1 → one stone left, return it
```

# Stage 3: Coding

## Approach 1 — Brute Force (Repeated Sort)

**The thinking:** Directly simulate the process using the most natural tool — sort the array, grab the last two, smash, insert the leftover, repeat.

```java
import java.util.*;

class Solution {
    public int lastStoneWeight(int[] stones) {
        // Use a dynamic list since the array's size shrinks/grows each round
        List<Integer> stoneList = new ArrayList<>();
        for (int s : stones) stoneList.add(s);

        // Continue as long as at least 2 stones remain to smash
        while (stoneList.size() > 1) {

            // Sort ascending — the two heaviest are now at the very end
            // WHY re-sort every round: after removing/inserting, order is
            // no longer guaranteed, and this brute force doesn't maintain
            // any special structure to avoid a full re-sort
            Collections.sort(stoneList);

            int n = stoneList.size();

            // Pop the two heaviest (last two after sorting)
            int first = stoneList.remove(n - 1);
            int second = stoneList.remove(n - 2);

            // Smash them — leftover goes back in if they weren't equal
            int diff = first - second;
            if (diff > 0) {
                stoneList.add(diff);
            }
            // if diff == 0, both are destroyed — nothing added back
        }

        // At most one stone remains
        return stoneList.isEmpty() ? 0 : stoneList.get(0);
    }
}
```

**Time Complexity — O(n² log n):**
In the worst case, roughly `n` smash-rounds happen (each round removes at least one stone permanently from the game). Each round pays `O(n log n)` to fully re-sort the list from scratch. Multiplying these together gives `O(n² log n)` — for every single round, we throw away and rebuild the entire sorted order, even though only one or two elements actually changed.

**Space Complexity — O(n):**
The `ArrayList` holding the stones takes O(n) space. `Collections.sort` on an `ArrayList` typically uses O(n) auxiliary space for its merge-sort-based implementation (in the worst case for object arrays).

## Approach 2 — Optimal (Max-Heap)

**The thinking:** Replace "sort the whole thing every round" with a structure that keeps the maximum instantly accessible and cheaply updated — a max-heap. This is the direct translation of the intuition built in Stage 2.

Java's `PriorityQueue` is a **min-heap by default**. To get max-heap behavior, we supply a reversed comparator.

```java
import java.util.*;

class Solution {
    public int lastStoneWeight(int[] stones) {
        // Max-heap: PriorityQueue is min-heap by default in Java,
        // so we flip the ordering with Collections.reverseOrder()
        PriorityQueue<Integer> maxHeap = new PriorityQueue<>(Collections.reverseOrder());

        // Build the heap — O(n log n) total (n insertions, each O(log n))
        for (int stone : stones) {
            maxHeap.offer(stone);
        }

        // Continue as long as at least 2 stones remain to smash
        while (maxHeap.size() > 1) {

            // Extract the two heaviest — O(log n) each
            int first = maxHeap.poll();
            int second = maxHeap.poll();

            // Smash: if unequal, the leftover weight re-enters the game
            // WHY only insert when diff > 0: equal weights destroy
            // each other completely, nothing to put back
            int diff = first - second;
            if (diff > 0) {
                maxHeap.offer(diff);
            }
        }

        // At most one stone remains — return its weight, or 0 if none left
        return maxHeap.isEmpty() ? 0 : maxHeap.poll();
    }
}
```

**Time Complexity — O(n log n):**
Building the initial heap costs `O(n log n)` (n insertions, each `O(log n)`). Then, each smash round performs two `poll()` operations and at most one `offer()` — each of these is `O(log n)`. The number of rounds is bounded by `O(n)` (the collection loses at least one stone every round). So the total cost of all rounds is `O(n log n)`. Overall: `O(n log n) + O(n log n) = O(n log n)` — a genuine improvement over the brute force's `O(n² log n)`, because we never throw away and rebuild the ordering — we only ever pay `log n` to fix up the *specific* elements that actually changed.

**Space Complexity — O(n):**
The heap holds up to `n` elements at any point. No other significant auxiliary space is used.
