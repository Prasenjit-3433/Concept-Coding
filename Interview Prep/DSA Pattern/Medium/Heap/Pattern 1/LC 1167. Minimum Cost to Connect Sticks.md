# LC 1167. Minimum Cost to Connect Sticks

---

# Stage 1: Identification

**Step 1 — Which topic?**

You're given an array of stick lengths. You want to connect **all** of them into a single stick. Each move: pick any **two** sticks, connect them (paying a cost equal to the **sum** of their two lengths), and the resulting combined stick goes back into your collection as one new stick. Repeat until only one stick remains. Find the **minimum total cost** to connect everything.

The phrase to notice: **"pick two sticks"** — but *which* two? The problem doesn't fix an order, and different choices of which two to connect first lead to different total costs. This is an optimization over a sequence of choices — the classic "try to be greedy at every step, and prove the greedy choice is always safe" shape.

**Step 2 — Which pattern?**

**Pattern 1: Standard Heap Problems** — specifically, this is the **canonical Huffman-coding-style** problem: repeatedly combine the two smallest, add the cost, and reinsert.

**Step 3 — Which key concept?**

**Min-heap simulation — always combine the two currently cheapest sticks first.**

---

# Stage 2: Intuition Building — Identifying the Heap, Then Proving the Greedy

### Recognizing the heap need, the same way as before

Ask the same question we asked for Last Stone Weight: *does this problem need the current best (min or max) of a changing collection, repeatedly, not just once?*

Here, at every step, you need to find the **two currently smallest** sticks — and after you combine them, a *new* stick (their sum) goes back in, and the collection has shrunk by one. Then you need the two smallest **again**, from this updated collection. That's the same repeating pattern as Last Stone Weight: extract best(s), combine, reinsert, repeat — just with **min** instead of **max**, and **sum** instead of **subtract**.

```
┌────────────────────────────────────────────────────────────────┐
│  Same recognition test as before:                              │
│  "Do I repeatedly need the current best (min/max) from a       │
│   collection that keeps mutating?"                             │
│                                                                │
│  Here: repeatedly need the two SMALLEST sticks → min-heap.     │
└────────────────────────────────────────────────────────────────┘
```

### But *why* should we always pick the two smallest first? (The greedy proof)

Recognizing "I need a heap" tells you *how* to efficiently get the two smallest each round — but it doesn't yet tell you *that* picking the two smallest each round is actually the optimal strategy. That needs its own justification, because a wrong greedy rule executed efficiently is still wrong.

Think about **how many times each original stick's length gets "counted" into the total cost.** Every time a stick (or a combined stick containing it) participates in a connection, its length gets added to the cost again. A stick that gets combined **early** (near the bottom of the connection process) ends up being "re-paid for" many times over, as it keeps getting folded into bigger and bigger combined sticks. A stick that gets combined **late** (near the very end) only gets paid for once or twice.

So, to minimize total cost, you want **small sticks to be combined early** (so their small values get "re-charged" repeatedly, which is cheap) and **large sticks to be combined late** (so their large values get "re-charged" as few times as possible).

This is *exactly* the same structural idea as Huffman coding: characters with low frequency should sit deep in the tree (combined early, re-counted often but cheaply), and characters with high frequency should sit shallow (combined late, re-counted rarely). **Always combining the two smallest available values at each step** is the greedy rule that achieves this — it's a well-established result (the same exchange-argument proof that underlies Huffman coding): swapping the order to combine anything other than the current two smallest can never produce a lower total cost, and can only make it worse or equal.

### Walking Through the Example

```
sticks = [2, 4, 3]
```

```
Round 1: two smallest → 2, 3. Cost = 2 + 3 = 5. Combined stick = 5.
         Collection now: [4, 5]

Round 2: two smallest → 4, 5. Cost = 4 + 5 = 9. Combined stick = 9.
         Collection now: [9]

Total cost = 5 + 9 = 14
```

Only one stick left — done. Every "find the two smallest" and "insert the new sum" is exactly the O(log n) heap operation we identified as necessary.

### Stopping Condition

Same shape as Last Stone Weight: keep going while **at least 2 sticks** remain in the heap.

```
if heap.size() == 1 → done, everything is connected
```

# Stage 3: Coding

## Approach 1 — Brute Force (Repeated Sort)

**The thinking:** Same as before — without a heap, you'd sort the collection every round just to find the two smallest.

```java
import java.util.*;

class Solution {
    public int connectSticks(int[] sticks) {
        List<Integer> stickList = new ArrayList<>();
        for (int s : sticks) stickList.add(s);

        int totalCost = 0;

        // Continue as long as more than one stick remains to connect
        while (stickList.size() > 1) {

            // Sort ascending — the two smallest are now at the very front
            // WHY re-sort every round: no structure is maintained between
            // rounds, so order must be re-established from scratch each time
            Collections.sort(stickList);

            // Pick the two smallest (first two after sorting)
            int first = stickList.remove(0);
            int second = stickList.remove(0);

            int cost = first + second;
            totalCost += cost;

            // The combined stick goes back into the collection
            stickList.add(cost);
        }

        return totalCost;
    }
}
```

**Time Complexity — O(n² log n):**
Roughly `n` connection-rounds occur (each round permanently reduces the stick count by one, since two sticks become one). Each round re-sorts the entire remaining collection at cost `O(n log n)`. Multiplying gives `O(n² log n)` — the same wasteful re-sort-from-scratch cost as Last Stone Weight's brute force.

**Space Complexity — O(n):**
The `ArrayList` holds up to `n` elements; sorting uses O(n) auxiliary space in the worst case.

## Approach 2 — Optimal (Min-Heap)

**The thinking:** Direct translation of the greedy rule proven in Stage 2 — always combine the two currently smallest sticks, using a min-heap to make "find the two smallest" and "reinsert the sum" both O(log n).

Java's `PriorityQueue` is a **min-heap by default** — no comparator flip needed here, unlike Last Stone Weight.

```java
import java.util.*;

class Solution {
    public int connectSticks(int[] sticks) {
        // Min-heap: PriorityQueue's default ordering is exactly what we need —
        // the smallest element is always at the root
        PriorityQueue<Integer> minHeap = new PriorityQueue<>();

        // Build the heap — O(n log n) total
        for (int stick : sticks) {
            minHeap.offer(stick);
        }

        int totalCost = 0;

        // Continue as long as more than one stick remains to connect
        while (minHeap.size() > 1) {

            // Extract the two currently smallest sticks — O(log n) each
            int first = minHeap.poll();
            int second = minHeap.poll();

            // Connect them: cost is their sum, and this becomes a new stick
            int cost = first + second;
            totalCost += cost;

            // The combined stick re-enters the pool of sticks to connect
            minHeap.offer(cost);
        }

        return totalCost;
    }
}
```

**Time Complexity — O(n log n):**
Building the initial heap costs `O(n log n)`. Each of the roughly `n` connection-rounds performs two `poll()` calls and one `offer()` call, each `O(log n)`. Total across all rounds: `O(n log n)`. Overall: `O(n log n)` — same structural improvement over brute force as in Last Stone Weight, for the same reason: we never re-sort the whole collection, we only pay `log n` to fix up the one new value that was actually inserted.

**Space Complexity — O(n):**
The heap holds up to `n` sticks at any point in time.
