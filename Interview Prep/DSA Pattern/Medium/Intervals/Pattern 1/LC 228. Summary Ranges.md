# LC 228. Summary Ranges

---

# Stage 1: Identification

**Step 1 — Which topic?**

You're given a sorted array of **unique** integers. You need to group the numbers into the smallest possible list of ranges, where each range is either a single number (`"5"`) or a contiguous run (`"5->7"`) — a run being a stretch of numbers that increases by exactly 1 each step.

**Step 2 — Which pattern?**

This is **Intervals Pattern 1: Interval Basics & Merge Fundamentals**. The sheet's own trigger for this pattern is exactly this shape: *"Sorted input already — single pass grouping consecutive numbers into ranges."* There's no need to sort (already sorted), no need to merge overlapping intervals in the general sense — you're doing the simplest possible version of "interval building": walking once, left to right, and closing a range the moment the consecutive chain breaks.

**Step 3 — Which key concept?**

**Let the outer loop's index do double duty as both "start of the current range" and "scanner" — collapse the state-tracking into a nested `while`, instead of a separate boolean flag.**

This is exactly the part worth slowing down on, since you flagged code quality. The naive way people solve this problem is to walk the array with a single loop and a few flag variables — `rangeStart`, `inRange` boolean, etc. — and decide at every index whether to "start a new range," "extend the range," or "close the range and start fresh." That's three branches to keep in sync, and it's very easy to get the boundary conditions (what happens at the very last element? what if a range has length 1?) subtly wrong under interview pressure. The fix: instead of deciding what to do at *each* index, decide **at the moment you open a range, how far it extends** — using an inner loop that eats the entire run in one shot. Once you do that, there's exactly one thing left to decide per range: is it a single number or a "start->end" pair? That's a single ternary, not a chain of if-else.

# Stage 2: Intuition Building

### The Problem, Concretely

```
nums = [0, 1, 2, 4, 5, 7]
```

Walking through it: `0, 1, 2` are consecutive (each is one more than the last) — that's one range, `"0->2"`. Then `4, 5` — another consecutive run, `"4->5"`. Then `7` stands alone — `"7"`.

```
Result: ["0->2", "4->5", "7"]
```

### Why the "Flag" Approach Gets Messy

The instinct many people reach for first: walk the array once, and at each index ask three questions — *"am I starting a new range? am I continuing one? did the previous range just end?"* That naturally produces code shaped like:

```
for i in range(n):
    if not inRange:
        start = nums[i]
        inRange = True
    if i == n-1 or nums[i+1] != nums[i] + 1:
        # close the range
        ...
        inRange = False
```

Notice the problem: you now have **two separate conditions competing for attention at every index** — one about opening, one about closing — plus a boolean that has to be threaded correctly across iterations. In an interview, this is exactly the kind of code that looks fine when you write it but breaks the moment you're asked "what if the array has one element?" or "what if the whole array is one big range?" — because the flag's initial state and its reset timing become edge cases you have to reason about separately.

### The Cleaner Mental Model: "Open a range, then immediately ask how far it goes"

Instead of deciding range membership one index at a time, flip the order of operations: **the moment you're standing at an unclaimed index, that index is definitely the start of a new range.** So mark it as the start, and then — right then and there — walk forward with a second cursor for as long as the numbers keep incrementing by exactly 1. When that inner walk stops, you already know the *entire* range in one shot: its start and its end. There's no "was I in a range" question to ask ever again, because the outer loop only ever lands on indices that are range-starts by construction — the inner `while` is the one that consumes everything else.

```
nums = [0, 1, 2, 4, 5, 7]
        i

i=0: start=0. Extend while next is start+1:
     nums[1]=1=nums[0]+1 → extend, i=1
     nums[2]=2=nums[1]+1 → extend, i=2
     nums[3]=4≠nums[2]+1 → stop
     range is [0,2] → "0->2"
     (outer loop's i now sits at 2; next outer iteration moves to i=3)

i=3: start=4. Extend while possible:
     nums[4]=5=nums[3]+1 → extend, i=4
     nums[5]=7≠nums[4]+1 → stop
     range is [4,5] → "4->5"

i=5: start=7. Nothing to extend, next index doesn't exist.
     range is [7,7] → "7"
```

The outer `for` loop's index `i` is reused as the "current start," and after the inner `while` finishes consuming the run, `i` has already moved to the **last** element of that range — so the outer loop's own increment naturally lands on the first unclaimed index next. That's the whole trick: **one loop variable, two jobs, zero flags.**

### Turning a Range Into a String

Once a range's `start` and its final `i` (the end) are known, there's exactly one decision left:

```
if start == i:  it's a single number → "start"
else:           it's a real range    → "start->end"
```

That's a single ternary — not a multi-branch if-else chain — because by this point all the *hard* work (figuring out where the range ends) is already done.

# Stage 3: Coding

## Approach 1 — The Flag-Based Version (What to Avoid, and Why)

```java
class Solution {
    public List<String> summaryRanges(int[] nums) {
        List<String> result = new ArrayList<>();
        int n = nums.length;
        if (n == 0) return result;

        int rangeStart = nums[0];

        for (int i = 0; i < n; i++) {
            // Check if the range breaks here
            if (i + 1 == n || nums[i + 1] != nums[i] + 1) {
                if (rangeStart == nums[i]) {
                    result.add(String.valueOf(rangeStart));
                } else {
                    result.add(rangeStart + "->" + nums[i]);
                }
                // Prepare start for the next range, guarding array bounds
                if (i + 1 < n) {
                    rangeStart = nums[i + 1];
                }
            }
        }

        return result;
    }
}
```

This is correct, but notice the shape: an `if` to detect the break, a nested `if` to guard against reading past the array, and an `if-else` to decide the format — three separate conditionals **all inside one loop body**, each depending on the others being right. This is the "worst-side interview" version — technically passing, but every reviewer's eye catches the tangle immediately, and it's fragile to modify (e.g., extending this to also *count* elements per range requires touching three different spots).

**Time Complexity — O(n):** single pass.
**Space Complexity — O(1)** extra (output list aside).

## Approach 2 — Optimal: One Loop, One Ternary

```java
class Solution {
    public List<String> summaryRanges(int[] nums) {
        List<String> result = new ArrayList<>();
        int n = nums.length;

        for (int i = 0; i < n; i++) {
            int start = i;

            // Consume the entire consecutive run in one shot —
            // WHY: this is the only place that needs to know
            // "are we still in a range?" — no flag required,
            // because the outer loop only ever starts at an
            // unclaimed index by construction
            while (i + 1 < n && nums[i + 1] == nums[i] + 1) {
                i++;
            }

            // By now, start = first element of the range, i = last element.
            // Exactly one decision remains: single number, or a real range?
            result.add(start == i
                    ? String.valueOf(nums[start])
                    : nums[start] + "->" + nums[i]);
        }

        return result;
    }
}
```

**Why this reads better in an interview:** there is exactly **one** conceptual step per outer iteration — "consume a range" — followed by exactly **one** decision — "format it." No boolean state survives across iterations, so there's nothing to get out of sync, and no boundary case (empty array handled by the loop simply not running once; single-element array handled by the `while` never firing, `start == i` immediately) needs separate handling.

**Time Complexity — O(n):**
Although there's a `for` loop with a nested `while`, every index in `nums` is visited **exactly once** across the two loops combined — the `while` advances `i` forward and the outer `for`'s own increment never re-visits ground the `while` already covered. So the total work is O(n), not O(n²), even though it looks like nested loops.

**Space Complexity — O(1)** extra, beyond the output list itself (which is required regardless of approach, since it *is* the answer).
