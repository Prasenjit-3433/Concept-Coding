# Stage 1: Identification

**Step 1 — Which topic?**

You are given the root of a **Binary Search Tree** (not a generic binary tree) and a target value. You need to find and return the **node** holding that value — or `null` if it doesn't exist anywhere in the tree.

**Step 2 — Which pattern?**

This is the very first, most foundational problem in BST — the trigger is as direct as it gets:

> "search" in a BST → **Pattern 1: Basic BST Operations**

Every later BST problem — insert, delete, floor/ceiling, closest value — builds on the exact same directional-decision idea this problem introduces. This is the template problem for the entire BST topic, the same role LC 144/94/145 played for Binary Tree traversals, and the same role LC 104 played for Tree Properties.

**Step 3 — Which key concept?**

**BST Compass — prune one entire subtree at every node using the ordering invariant.**

The single fact that makes this problem different from searching a generic binary tree: in a BST, **everything in a node's left subtree is smaller than the node, and everything in its right subtree is larger.** That's not just a structural label — it's a **compass**. At any node, comparing the target against that one node's value tells you, with total certainty, which entire half of the remaining tree can be thrown away without looking at a single node inside it. You never have to check both sides "just in case" — the BST property already guarantees which side the answer must live on, if it exists at all.

# Stage 2: Intuition Building

### Why This Isn't Just "Binary Tree Search"

If this were a plain binary tree with no ordering guarantee, there would be no way to know whether your target hides in the left subtree or the right subtree without actually looking inside both. You'd need a full traversal — preorder, inorder, whatever — checking every node until you either find a match or run out of nodes. That's **O(n)**, because in the worst case the value you want is the very last node you check.

A BST changes this completely, because of one guarantee it carries at *every single node*, not just the root:

```
┌─────────────────────────────────────────────────────────────────┐
│  At ANY node in a BST:                                          │
│      everything in its LEFT subtree  < node.val                 │
│      everything in its RIGHT subtree > node.val                 │
│                                                                 │
│  This holds recursively — it's true at the root, true at every  │
│  child, true at every grandchild, all the way down.             │
└─────────────────────────────────────────────────────────────────┘
```

The moment you know this holds at *every* node — not just the root — you can make a **local decision** at each node that is guaranteed globally correct: compare the target against the current node, and let that single comparison tell you which entire subtree is worth exploring and which one can be discarded outright.

### The Tree We're Working With

```
8 5
8 12
5 4
5 7
7 6
7 null
12 10
12 14
14 null
```

Paste into a tree visualizer, or picture it directly:

```
              8
            /   \
           5     12
          / \    /  \
         4   7  10   14
            /
           6
```

### The Core Question — What Does a Mismatch Actually Tell You?

Say you're standing at node `8`, searching for `10`. The moment you see `10 != 8`, don't just think "not a match, keep going." Ask the sharper question Striver's whole explanation hinges on:

> *"Given that `10 != 8`, do I already know — with total certainty — which side `10` must be on, without looking at either side?"*

Yes. The BST invariant says everything in `8`'s left subtree is smaller than `8`, and everything in its right subtree is larger than `8`. Since `10 > 8`, `10` **cannot possibly exist anywhere in the left subtree** — not a single node there is even eligible. So the left subtree isn't just "less promising" — it's **provably irrelevant**. The only place `10` could possibly be is somewhere in the right subtree. There's nothing to "search" on the left; there's nothing to even check.

```
┌─────────────────────────────────────────────────────────────────┐
│  target < node.val   →  target CANNOT exist in the right        │
│                          subtree → go LEFT, discard right       │
│                                                                 │
│  target > node.val   →  target CANNOT exist in the left         │
│                          subtree → go RIGHT, discard left       │
│                                                                 │
│  target == node.val  →  found it. Return this node.             │
└─────────────────────────────────────────────────────────────────┘
```

This is exactly the same decision structure as binary search on a sorted array — except instead of a `mid` index splitting a sorted array in half, the **current node itself** splits the remaining search space in half, because the tree's shape already encodes the sorted order.

### Tracing Search(10) on the Example Tree

Start at the root, target = `10`:

```
At node 8:  10 != 8, and 10 > 8
            → left subtree of 8 (rooted at 5) is entirely < 8,
              so it's entirely < 10 too — irrelevant, discard it
            → move to the RIGHT child: 12

At node 12: 10 != 12, and 10 < 12
            → right subtree of 12 (rooted at 14) is entirely > 12,
              so it's entirely > 10 too — irrelevant, discard it
            → move to the LEFT child: 10

At node 10: 10 == 10 → MATCH FOUND
            → return this node
```

Notice what never got touched: nodes `5`, `4`, `7`, `6`, `14` — five of the tree's nine nodes were never even glanced at. That's the entire benefit of the BST invariant in action: half the remaining tree gets eliminated at every single step, purely from one comparison.

### Tracing Search(9) — The Not-Found Case

```
At node 8:  9 != 8, and 9 > 8  → discard left, move RIGHT to 12
At node 12: 9 != 12, and 9 < 12 → discard right, move LEFT to 10
At node 10: 9 != 10, and 9 < 10 → discard right, move LEFT to... null
At null:    there's nothing here → the search path has run out
            → return null
```

The moment you hit `null`, that's not a failure of the algorithm — it's the algorithm correctly telling you the value genuinely doesn't exist. If `9` existed anywhere in this tree, the same directional logic that led you to `10`'s position would have led you to `9`'s position instead, since the invariant holds at every node along the way. Reaching `null` means you've followed the *only* path `9` could possibly have taken, and there was nothing there.

### Why the Search Always Terminates

Every step moves to a **child** — strictly one level deeper — never sideways, never back up. Since the tree is finite and has no cycles, every downward path eventually ends at `null`. So the search either finds an exact match and stops immediately, or it runs out of tree and hits `null`. There's no third outcome.

### Why This Is O(height), Not O(n)

At every node, you do a constant amount of work (one comparison) and then move to exactly **one** child — never both. So the total number of nodes touched equals the number of edges walked from root to wherever the search ends, which is bounded by the tree's height, `h`. You are never forced to look at every node — only the ones lying on this single root-to-target path.

```
┌──────────────────────────────────────────────────────────────────┐
│  Binary Tree search (no ordering guarantee): O(n)                │
│      → must potentially check every node, no way to prune        │
│                                                                  │
│  BST search (ordering guarantee at every node): O(h)             │
│      → one comparison eliminates an entire subtree,              │
│        only one root-to-node path is ever walked                 │
│                                                                  │
│  For a reasonably balanced BST, h = O(log n) — this is what      │
│  most BSTs handed to you in practice look like.                  │
│  For a SKEWED BST (e.g., built by inserting an already-sorted    │
│  sequence), h degenerates to O(n) — same worst case as a         │
│  linked list. The O(log n) claim is a common-case expectation,   │
│  not a guarantee the data structure enforces on its own.         │
└──────────────────────────────────────────────────────────────────┘
```

# Stage 3: Coding

### Brute Force — Ignore the BST Property Entirely

**The honest (but wasteful) thinking:**

> "Just do a plain traversal — preorder, inorder, whatever — and check every node's value against the target."

```java
class Solution {
    public TreeNode searchBST(TreeNode root, int val) {
        if (root == null) return null;
        if (root.val == val) return root;

        TreeNode left = searchBST(root.left, val);
        if (left != null) return left;

        return searchBST(root.right, val);
    }
}
```

This works correctly on *any* binary tree, BST or not — which is exactly the problem. It never uses the ordering guarantee, so it explores **both** children at every node regardless of what the comparison tells you. Worst case, it visits every node: **O(n)**. This is the "I forgot I was given a BST" solution — establishes correctness only, not the intended approach.

---

### Optimal — BST Compass: One Comparison, One Direction, Every Node

**Mental workflow before writing a single line:**

```
1. If root is null → nothing here, target doesn't exist on this path → return null

2. If root.val == val → found it → return this node directly

3. If val < root.val → target can ONLY be in the left subtree
   → recurse/iterate into root.left, discard right entirely

4. If val > root.val → target can ONLY be in the right subtree
   → recurse/iterate into root.right, discard left entirely
```

There are two equally valid ways to express this — **iterative** (Striver's version) and **recursive** (your version). Both follow the exact same directional logic; they differ only in *how* the "move to one child and repeat" step is implemented.

---

#### Striver's Version — Iterative

```java
class Solution {
    public TreeNode searchBST(TreeNode root, int val) {
        while (root != null && root.val != val) {
            root = val < root.val ? root.left : root.right;
        }

        return root;
    }
}
```

Read the loop condition exactly as the algorithm's stopping rule: **keep moving while you haven't run out of tree (`root != null`) AND you haven't found the target yet (`root.val != val`).** The moment either condition breaks — you've hit `null`, or you've found a match — the loop stops, and whatever `root` currently is becomes the answer. If it stopped because of a match, `root` is the found node. If it stopped because `root` became `null`, that null itself is exactly what you return — no separate check needed.

Inside the loop, the ternary is the compass reading directly translated into code: `val < root.val` means "go left," anything else (`val > root.val`, since equality already exited the loop) means "go right."

---

#### Your Version — Recursive

```java
class Solution {
    public TreeNode searchBST(TreeNode root, int val) {
        // base
        if (root == null) return null;

        // match found
        if (root.val == val) return root;

        // binary search
        if (val < root.val) {
            TreeNode left = searchBST(root.left, val);
            if (left != null) return left;
        } else {
            TreeNode right = searchBST(root.right, val);
            if (right != null) return right;
        }

        return null;
    }
}
```

This is functionally identical in *which* nodes get visited — it still only ever recurses into **one** child per call, exactly like Striver's iterative version, because the `if (val < root.val) { ... } else { ... }` branching means only one of the two recursive calls ever actually happens at each level. The `if (left != null) return left;` guard is slightly redundant here (since the recursive call on the correct side is the *only* call made, its result — match or `null` — can simply be returned directly), but it doesn't change correctness or complexity. A tightened version of the same idea:

```java
class Solution {
    public TreeNode searchBST(TreeNode root, int val) {
        if (root == null || root.val == val) return root;

        return val < root.val
            ? searchBST(root.left, val)
            : searchBST(root.right, val);
    }
}
```

This collapses your version down to the same three-decision shape as Striver's loop, just expressed recursively instead of iteratively.

---

### Iterative vs Recursive — What Actually Differs

```
┌──────────────────────────────────────────────────────────────────┐
│  Both versions:                                                  │
│    → visit exactly ONE node per level — never both children      │
│    → same O(h) TIME complexity                                   │
│                                                                  │
│  Iterative (Striver's):                                          │
│    → no call stack — just a pointer being reassigned in a loop   │
│    → SPACE: O(1)                                                 │
│                                                                  │
│  Recursive (yours):                                              │
│    → each call adds one frame to the call stack, only unwound    │
│      once a base case (null or match) is hit                     │
│    → SPACE: O(h) — proportional to the tree's height             │
└──────────────────────────────────────────────────────────────────┘
```

Neither is "wrong" — they visit the identical set of nodes in the identical order. The only real-world difference is the recursion's call-stack overhead, which becomes relevant on a very skewed BST (deep, thin tree) where `h` approaches `n`.

---

## Complexity Analysis

**Time Complexity — O(h), where h is the height of the tree:**

At every node visited, the work done is O(1) — one comparison — and then the search moves to exactly one child, never both. So the number of nodes touched equals the length of the single root-to-target (or root-to-null) path, which is bounded by the tree's height.

- **Balanced / typical BST:** `h = O(log n)` — this is the expectation for most BSTs you'll encounter, since insertions into a reasonably random sequence tend to keep the tree roughly balanced.
- **Worst case (skewed BST):** if the tree was built by inserting values in already-sorted order, it degenerates into something resembling a linked list, and `h = O(n)`.

So the honest statement is **O(h)**, which simplifies to `O(log n)` in the common case and `O(n)` in the worst case — never `O(n)` guaranteed-good the way it would be misleading to just say "O(log n)" outright.

**Space Complexity:**

- **Iterative version — O(1):** no extra data structure is used beyond a single pointer being reassigned each step.
- **Recursive version — O(h):** each recursive call adds a stack frame, and since only one recursive branch is ever taken (not both), the maximum stack depth at any point equals the current search path's length — bounded by the tree's height, same as the time complexity's bound.

## Comparing Brute Force vs Optimal

| Property | Brute Force (ignores BST property) | Optimal (BST Compass) |
| --- | --- | --- |
| Uses ordering invariant? | No — treats it like a generic binary tree | Yes — every comparison eliminates a subtree |
| Children explored per node | Both (left AND right) | Exactly one |
| Time | O(n) | O(h) → O(log n) typical, O(n) worst case (skewed) |
| Space | O(h) recursion stack | O(1) iterative, or O(h) recursive |

## The Key Takeaway

```
┌───────────────────────────────────────────────────────────────────┐
│  The BST invariant holds at EVERY node, not just the root:        │
│      left subtree < node < right subtree                          │
│                                                                   │
│  This turns every mismatch into FREE INFORMATION:                 │
│      target < node.val  →  right subtree is PROVABLY irrelevant   │
│      target > node.val  →  left subtree is PROVABLY irrelevant    │
│                                                                   │
│  So at every step, you don't "choose" a more promising side —     │
│  you ELIMINATE a side with total certainty, based on one          │
│  comparison. Only one path from root to the answer (or to         │
│  null) is ever walked.                                            │
│                                                                   │
│  This is binary search — just expressed on a tree's shape         │
│  instead of an array's indices. The height plays the role         │
│  the "search space size" plays in array binary search.            │
│                                                                   │
│  Time  — O(h): O(log n) typical, O(n) worst case (skewed BST).    │
│  Space — O(1) iterative, O(h) recursive (call stack).             │
└───────────────────────────────────────────────────────────────────┘
```
