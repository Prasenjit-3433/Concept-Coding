# LC 543. Diameter of Binary Tree

---

# Stage 1: Identification

**Step 1 — Which topic?**

You are given the root of a binary tree. You need to find its **diameter** — the length of the **longest path between any two nodes** in the tree.

**Step 2 — Which pattern?**

Still **Pattern 2: Tree Properties** — this is a structural measurement of the whole tree, computed by recursing through it. The trigger:

> "diameter", "longest path between any two nodes" → **Tree Properties**

**Step 3 — Which key concept?**

**Global max updated at each node; diameter ≠ depth of tree.**

This is the first problem in the pattern where the value you eventually want (the diameter) is **not** the same thing as the value you return up the recursion (the height). You need a separate variable — updated as a side effect at *every* node visited — that tracks the best answer seen anywhere in the tree, completely independent of what gets passed back to each node's parent.

---

# Stage 2: Intuition Building

### What Exactly Is "Diameter"?

Two things about the definition matter, and Striver calls out both explicitly:

1. **It's the longest path between *any* two nodes** — not necessarily leaves, not necessarily the two farthest-apart leaves in some obvious sense.
2. **The path does not need to pass through the root.** It can be a path entirely contained within some subtree, far from the root.

### Example 1 — A Small Tree

```
1 2
1 3
2 4
2 5
```

```
        1
       / \
      2   3
     / \
    4   5
```

The longest path here is `4 → 2 → 5`, which has length **3** (three edges: 4-2, 2-5, that's... let's count nodes on the path: 4, 2, 5 — that's 2 edges, so length by edge-count is 2, but Striver counts diameter as **number of edges on the path**, and confirms it as 3 by tracing `4 → 2 → 1 → 3` in his example instead — path length in *edges*).

Actually — matching Striver's own worked example precisely: for his first tree, taking node **4** and node **3**, the path is `4 → 2 → 1 → 3`, which covers **3 edges**. That is the diameter: **3**.

### Example 2 — Diameter Does NOT Need to Pass Through Root

```
        (root)
         ...
          |
          X
         / \
        6   ...
       /
      ...
       \
        9
```

Striver's second example: taking node **6** and node **9**, the path between them winds through several intermediate nodes **without ever touching the root** at all — and this path turns out to be the longest one in the whole tree, with length **6**.

```
┌────────────────────────────────────────────────────────────────┐
│  KEY DEFINITION POINTS                                         │
│                                                                │
│  → Diameter = longest path between ANY two nodes               │
│  → Measured in number of EDGES on that path                    │
│  → The path is NOT required to pass through the root           │
│  → It could be entirely "hidden" inside some subtree far       │
│    from the root — you cannot just check the root and stop     │
└────────────────────────────────────────────────────────────────┘
```

This last point is exactly *why* you can't just compute "left height + right height" once at the root and call it done — the true longest path might live entirely inside, say, the left subtree, never touching the root's own left/right split.

---

### The Core Question — What Is the Longest Path *Through* a Given Node?

Forget the whole tree for a second. Stand at **one specific node** and ask:

> *"If a path is required to pass through me, connecting something in my left subtree to something in my right subtree — how long can that path possibly be?"*

The answer falls out immediately: go as deep as possible into the left subtree (that's `leftHeight` edges away), and as deep as possible into the right subtree (that's `rightHeight` edges away). Gluing those two together through the current node gives a path of:

```
longest path through this node = leftHeight + rightHeight
```

This is **not** the height of the node — height is `1 + max(leftHeight, rightHeight)`. This is a completely different quantity: the **sum**, not `1 + the larger one`.

### Walking Through Striver's First Tree, Node by Node

```
        1
       / \
      2   3
     / \
    4   5
```

At every node, compute `leftHeight`, `rightHeight`, and the candidate diameter `leftHeight + rightHeight` — separately from what gets returned as this node's own height:

```
Node 4 → leaf → LH=0, RH=0 → candidate diameter = 0 + 0 = 0
                            → height returned = 1 + max(0,0) = 1

Node 5 → leaf → LH=0, RH=0 → candidate diameter = 0
                            → height returned = 1

Node 2 → LH = height(4) = 1, RH = height(5) = 1
                            → candidate diameter = 1 + 1 = 2
                            → height returned = 1 + max(1,1) = 2

Node 3 → leaf → LH=0, RH=0 → candidate diameter = 0
                            → height returned = 1

Node 1 → LH = height(2) = 2, RH = height(3) = 1
                            → candidate diameter = 2 + 1 = 3
                            → height returned = 1 + max(2,1) = 3
```

Candidates seen across the whole traversal: `0, 0, 2, 0, 3`. The **maximum** of these is `3` — and that's the diameter. Notice: node 2 by itself only offered a candidate of `2` (the path `4 → 2 → 5`), but node 1 offered a *better* candidate of `3` (the path `4 → 2 → 1 → 3`). The true diameter-producing node isn't always obvious in advance — that's exactly why **every single node** must be checked and compared, not just the root.

```
┌───────────────────────────────────────────────────────────────┐
│  Diameter of the WHOLE tree = the MAXIMUM, across ALL nodes,  │
│  of (leftHeight + rightHeight) computed at that node.         │
│                                                               │
│  This is fundamentally different from height:                 │
│      height(node)    = 1 + max(LH, RH)   → returned UPWARD    │
│      diameter(node)  = LH + RH           → compared GLOBALLY  │
└───────────────────────────────────────────────────────────────┘
```

---

### The Naive Approach — And Why It's O(n²)

The direct translation of the idea above: at every node, separately call a `findHeight()` function to get its left height and right height, add them, compare against a running maximum.

```
┌────────────────────────────────────────────────────────────────┐
│  Same trap as LC 110 (Balanced Binary Tree):                   │
│                                                                │
│  You already have a function that computes height in O(n)      │
│  by visiting every node ONCE. But if you call THAT function    │
│  freshly at EVERY node just to get its LH and RH, you're       │
│  re-walking subtrees you're about to walk again anyway.        │
│                                                                │
│  O(n) nodes × O(n) height computation at each = O(n²)          │
│  Confirmed worst case: a skewed tree, exactly like before.     │
└────────────────────────────────────────────────────────────────┘
```

### The Optimization — Reuse the Height Recursion's Own LH/RH

This is the exact same realization from LC 110, applied again:

> *"The height-computing recursion ALREADY has `leftHeight` and `rightHeight` sitting right there in its local variables at every single node it visits. Why compute them a second time with a separate call? Just use the ones already being computed as a byproduct of finding the height."*

So take the LC 104 height function, unchanged in its recursive shape, and simply add **one extra line** at every node: before returning the height, update a globally-tracked maximum with `leftHeight + rightHeight`.

```
┌────────────────────────────────────────────────────────────────┐
│  LC 104 height recurrence (unchanged):                         │
│      height(node) = 1 + max(leftHeight, rightHeight)           │
│                                                                │
│  LC 543 — ONE line added, using the SAME LH/RH already in      │
│  hand at this exact point in the recursion:                    │
│      maxDiameter = max(maxDiameter, leftHeight + rightHeight)  │
│      return 1 + max(leftHeight, rightHeight)   ← unchanged     │
│                                                                │
│  Height computation and diameter tracking now happen in        │
│  the SAME single postorder pass — no recomputation, no         │
│  second traversal.                                             │
└────────────────────────────────────────────────────────────────┘
```

### Why a "Global" Variable, Not a Returned Value?

This is the conceptually new part of this problem compared to LC 104 and LC 110. In those problems, the single `int` returned by the recursive function **was** the answer the parent needed. Here, that's no longer true — the value returned upward (`height`) and the value we actually want at the end (`diameter`) are two *different* numbers. The diameter at any node isn't something the parent needs to combine further — it's a **candidate answer** that needs to be compared against every other candidate seen *anywhere* in the tree, not just along one root-to-node path.

So instead of trying to thread the maximum diameter back up through return values (which would require returning two pieces of information per node — awkward), the cleaner move is: keep one shared variable (global, or passed by reference / wrapped in a single-element array in Java, exactly as Striver does), and update it as a **side effect** every time a node computes its `leftHeight + rightHeight`. The return value keeps doing its normal job (feeding height upward to the parent); the global variable quietly accumulates the best diameter candidate across the whole traversal, independent of the call chain's return values.

```
┌─────────────────────────────────────────────────────────────────┐
│  RETURN VALUE  → height, needed by the PARENT to do ITS         │
│                  own height/diameter computation                │
│                                                                 │
│  GLOBAL VALUE  → running best diameter candidate, needed by     │
│                  NOBODY in particular — just tracked across     │
│                  the entire traversal and read once at the end  │
│                                                                 │
│  These two serve different masters. Don't try to force both     │
│  into a single return value — let one be returned, and let      │
│  the other live outside the recursion entirely.                 │
└─────────────────────────────────────────────────────────────────┘
```

### Why the Recursion Still Terminates and Still Visits Every Node Once

Nothing about the traversal shape changed — it's still the same postorder recursion from LC 104: base case `null → 0`, resolve left, resolve right, combine. The diameter-tracking line is just extra constant-time work inserted at each node, right where `leftHeight` and `rightHeight` are already sitting in scope. So the total work is still bounded by the number of nodes: **O(n)**.

# Stage 3: Coding

## Approach 1 — Brute Force (O(n²))

**The honest thinking:**

> "At every node, call a separate findHeight() to get the left height and right height, add them, compare with the running maximum. Then recurse into both children and repeat."

```java
class Solution {
    private int maxDiameter = 0;

    public int diameterOfBinaryTree(TreeNode root) {
        solve(root);
        return maxDiameter;
    }

    private void solve(TreeNode node) {
        if (node == null) return;

        int leftHeight = findHeight(node.left);   // separate O(n) call
        int rightHeight = findHeight(node.right); // separate O(n) call

        maxDiameter = Math.max(maxDiameter, leftHeight + rightHeight);

        solve(node.left);
        solve(node.right);
    }

    private int findHeight(TreeNode node) {
        if (node == null) return 0;
        return 1 + Math.max(findHeight(node.left), findHeight(node.right));
    }
}
```

**Why this is O(n²):** `findHeight()` is a full O(n) traversal, called twice at every one of the O(n) nodes visited by `solve()`. Worst case (skewed tree), this becomes `O(n²)` — the same trap as LC 110's brute force. Establishes correctness only.

---

## Approach 2 — Optimal: Fused Height Computation + Global Diameter Tracking (O(n))

**Mental workflow before writing a single line:**

```
1. Keep a single shared variable maxDiameter, initialized to 0
   (in Java: wrap in a 1-element array since primitives aren't
   passed by reference)

2. Write solve(node) — the EXACT same shape as the LC 104
   height function:
   → base case: node == null → return 0
   → leftHeight  = solve(node.left)
   → rightHeight = solve(node.right)

3. ONE new line, inserted right here (LH and RH already in hand):
   → maxDiameter = max(maxDiameter, leftHeight + rightHeight)

4. Return the height, UNCHANGED from LC 104:
   → return 1 + max(leftHeight, rightHeight)

5. In the main function: call solve(root), then return maxDiameter
```

```java
class Solution {
    // Java has no pass-by-reference for primitives, so a
    // single-element array plays that role — exactly the
    // trick Striver uses in the Java version of his code
    private int[] maxDiameter = new int[1];

    public int diameterOfBinaryTree(TreeNode root) {
        maxDiameter[0] = 0;
        solve(root);
        return maxDiameter[0];
    }

    private int solve(TreeNode node) {
        // Base case: an empty tree has height 0 —
        // identical to LC 104
        if (node == null) return 0;

        // Step 1: resolve LEFT subtree first (same as LC 104)
        int leftHeight = solve(node.left);

        // Step 2: resolve RIGHT subtree next (same as LC 104)
        int rightHeight = solve(node.right);

        // NEW STEP — the only real addition to LC 104's code:
        // the longest path THROUGH this node connects its
        // deepest left descendant to its deepest right
        // descendant, which is exactly leftHeight + rightHeight.
        // Compare this candidate against the best seen so far,
        // ACROSS THE WHOLE TREE — not just along this call chain.
        maxDiameter[0] = Math.max(maxDiameter[0], leftHeight + rightHeight);

        // Step 3: COMBINE and return height — UNCHANGED from
        // LC 104. This value is for the PARENT's use only;
        // it has nothing to do with maxDiameter directly.
        return 1 + Math.max(leftHeight, rightHeight);
    }
}
```

## Workflow Trace on Striver's Example

```
        1
       / \
      2   3
     / \
    4   5
```

```
solve(4): leaf → LH=0, RH=0
          maxDiameter = max(0, 0+0) = 0
          returns 1 + max(0,0) = 1

solve(5): leaf → LH=0, RH=0
          maxDiameter = max(0, 0+0) = 0
          returns 1

solve(2): LH = solve(4) = 1, RH = solve(5) = 1
          maxDiameter = max(0, 1+1) = 2
          returns 1 + max(1,1) = 2

solve(3): leaf → LH=0, RH=0
          maxDiameter = max(2, 0+0) = 2   ← unchanged, 0 < 2
          returns 1

solve(1): LH = solve(2) = 2, RH = solve(3) = 1
          maxDiameter = max(2, 2+1) = 3   ← updated! 3 > 2
          returns 1 + max(2,1) = 3

Final: maxDiameter = 3
```

**Diameter = 3**, matching Striver's traced answer exactly — achieved via the path `4 → 2 → 1 → 3`.

## Complexity Analysis

**Time Complexity — O(n):**

Every node is visited **exactly once** by `solve()`. At each node, the work done is constant: two recursive calls' results are combined via one addition (for the diameter comparison) and one `max()` + addition (for the height to return) — no repeated re-traversal of any subtree, unlike the brute force. With `n` total nodes, each handled in O(1) time, total time is **O(n)** — the height computation and the diameter tracking are fused into a single pass, exactly like LC 110 fused height and balance-checking.

**Space Complexity — O(h), where h is the height of the tree:**

The only auxiliary space is the recursion call stack, exactly as in LC 104 and LC 110 — one frame per node on the current root-to-node path.

- **Best case (balanced tree):** `h = O(log n)`.
- **Worst case (skewed tree):** `h = O(n)`, since the call stack holds all `n` nodes on the single chain at once, as Striver explicitly notes when describing the worst case.

So: **O(h) auxiliary space — O(log n) balanced, O(n) worst case (skewed tree)**. The `maxDiameter` variable itself is a single integer (or a 1-element array in Java) — O(1) extra space, negligible next to the recursion stack.

---

## Comparing Brute Force vs Optimal

| Property | Brute Force | Fused (Optimal) |
| --- | --- | --- |
| Height computed | Separately, at every node, via two fresh O(n) calls | Once per node, as a byproduct of one traversal |
| Time | O(n²) worst case | O(n) |
| What gets returned | Nothing meaningful (void) | Height — used only by the parent |
| Where diameter lives | Updated inside a separate wrapper function | Updated as a side effect inside the height recursion itself |
| Core trick | None — direct translation of the definition | Reuse LH/RH already in scope; separate "returned value" from "globally tracked answer" |
