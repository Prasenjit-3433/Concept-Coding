# LC 662. Maximum Width of Binary Tree

---

# Stage 1: Identification

**Step 1 — Which topic?**

You are given the root of a binary tree. You need to find its **maximum width** — defined as the maximum number of nodes that would exist between the leftmost and rightmost node **on any single level**, counting the null gaps in between as if they were real nodes.

**Step 2 — Which pattern?**

This is a **level-based** measurement — "width" is inherently tied to "what's the spread across one level." The trigger:

> "width", "between any two nodes on the same level" → **Tree Properties**, but the level-by-level nature of the question points specifically toward a **BFS / level-order** mechanism, not postorder recursion.

**Step 3 — Which key concept?**

**BFS + heap-style index; width = rightmost index − leftmost index + 1.**

The key concept has two layers. First: if every node carried an **index** — as if the tree were a complete binary tree stored in an array, using the classic heap-indexing formula (`left child = 2i+1`, `right child = 2i+2`) — then the width of any level collapses to simple arithmetic: `(index of last node on level) − (index of first node on level) + 1`. Second, and this is the subtle part: applying that formula naively causes integer overflow on skewed trees, so the index must be **normalized** at the start of every level before being used to compute children.

---

# Stage 2: Intuition Building

### What Does "Width" Actually Mean?

Width is the number of nodes that would exist between the leftmost and rightmost node of a level **if the tree were fully filled in** at that level — including positions where nodes don't actually exist.

**Example 1:**

```
        1
       / \
      3   7
     /     \
    8       4
```

At the deepest level, node `8` and node `4` are the leftmost and rightmost nodes. Even though there's nothing between them in the actual tree, if you imagine the tree fully filled in at that level, there would be `8` positions between (and including) `8` and `4`. So the width here is **8** — not the count of *actual* nodes present, but the span of positions they occupy.

**Example 2 — Contrast with a case where width is small:**

```
      1
     / \
    3   2
```

Here the deepest level has nodes at adjacent positions — width is **2**.

```
┌────────────────────────────────────────────────────────────────┐
│  Width ≠ "count of nodes actually present on a level."         │
│  Width = "the span of POSITIONS from the leftmost to the       │
│           rightmost node on that level, as if the tree         │
│           were a complete tree with every position filled."    │
└────────────────────────────────────────────────────────────────┘
```

---

### The Core Insight — Indexing Like a Complete Tree

Imagine numbering every node in the tree as though it were stored in an array representing a **complete** binary tree — regardless of whether nodes are actually present at every position. Using 0-based indexing:

```
For a node at index i:
    left child  → index (2 * i + 1)
    right child → index (2 * i + 2)
```

If every node — real or hypothetical — carries such an index, then the question "what is the width of this level" becomes purely arithmetic:

```
width of a level = (index of the LAST node on that level)
                  − (index of the FIRST node on that level)
                  + 1
```

Why does this work? Because the indexing scheme itself already encodes "how many positions would exist between any two nodes on the same level" — indices increase left to right within a level exactly the way array positions would in a complete tree.

```
┌────────────────────────────────────────────────────────────────┐
│  Give every node a heap-style index. Then width becomes:       │
│      lastIndexOnLevel − firstIndexOnLevel + 1                  │
│                                                                │
│  This is EXACTLY why we need BFS — a level-order traversal     │
│  naturally groups nodes by level, so "first" and "last" on     │
│  a level are trivially the first and last nodes popped         │
│  during that level's processing.                               │
└────────────────────────────────────────────────────────────────┘
```

### Why BFS, Specifically?

Width is fundamentally a **per-level** quantity. Recursive postorder (the shape used in LC 104, LC 110, LC 543) processes the tree by diving deep first — it doesn't naturally group "all nodes at depth 3" together in one place. BFS, by contrast, processes the tree in complete rings, one level at a time — exactly the grouping needed to compare "first node's index" against "last node's index" *within a single level*.

---

### The Overflow Problem — Why Naive Indexing Breaks

Here's where the transcript's own worked failure case matters. Suppose the tree is heavily skewed — say, every node only has a left child, going many levels deep. If you *never* reset the index at the start of a level, and simply keep applying `2i+1` / `2i+2` generation after generation starting from a single-digit index at the root, the index **doubles (roughly) at every level**:

```
Level 0: index 0
Level 1: index 1 (or 2)
Level 2: index 3 (or 4, or up to 6)
Level 3: index 7 ... up to 14
Level 4: index 15 ... up to 30
...
```

For a tree with `10^5` levels (a fully skewed worst case), the index would balloon toward `2^(10^5)` — an astronomically large number that overflows any fixed-size integer type almost immediately. This isn't a rare edge case; **any sufficiently deep skewed tree triggers it**, so the raw formula cannot be used as-is.

### The Fix — Normalize the Index at the Start of Every Level

The trick: at the beginning of processing each level, take the **minimum index seen on that level** and subtract it from every node's index **before** using that index to generate children.

```
┌────────────────────────────────────────────────────────────────┐
│  BEFORE computing a node's children's indices:                 │
│      normalizedIndex = currentIndex − minIndexOnThisLevel      │
│                                                                │
│  THEN generate children using the normalized index:            │
│      left  child index = 2 * normalizedIndex + 1               │
│      right child index = 2 * normalizedIndex + 2               │
│                                                                │
│  This resets every level's numbering to start near 0,          │
│  preventing indices from doubling uncontrollably across        │
│  many levels — while still preserving correct RELATIVE         │
│  spacing between nodes WITHIN each level, which is all         │
│  the width formula actually needs.                             │
└────────────────────────────────────────────────────────────────┘
```

Why is this safe? The width formula only cares about the **difference** between the first and last index on a given level — not their absolute values. Subtracting the same constant (the level's minimum index) from every node on that level shifts all of them down uniformly, so the *difference* between any two nodes on that level is completely unaffected. It's exactly like re-zeroing a ruler — the measurements between marks stay the same even if the starting point changes.

### Walking Through Striver's Example

```
        1
       / \
      3   7
     / \   \
    8   -   4
```

(Using edge-list style — node 3 has only a left child `8`, node 7 has only a right child `4`)

**Level 0:** Queue holds `(1, index=0)`.

```
Only one node → width = 0 − 0 + 1 = 1
```

Generate children: minIndex on this level = 0, so normalized index of node 1 = 0 − 0 = 0.
```
left child (3):  index = 2*0 + 1 = 1
right child (7): index = 2*0 + 2 = 2
```

**Level 1:** Queue holds `(3, index=1)`, `(7, index=2)`.

```
First = 1, Last = 2 → width = 2 − 1 + 1 = 2   ← better than current best (1), update
```

Generate children. minIndex on this level = 1.
```
For node 3 (index=1): normalized = 1 − 1 = 0
    left child (8):  index = 2*0 + 1 = 1
    (no right child)

For node 7 (index=2): normalized = 2 − 1 = 1
    (no left child)
    right child (4): index = 2*1 + 2 = 4
```

**Level 2:** Queue holds `(8, index=1)`, `(4, index=4)`.

```
First = 1, Last = 4 → width = 4 − 1 + 1 = 4   ← better than current best (2), update
```

No further children to process. Queue empties.

**Final answer: maximum width = 4.**

This matches exactly what direct visual inspection confirms: at the last level, if the tree were fully filled between node `8` (leftmost) and node `4` (rightmost), there would be 4 total positions.

---

### Why Subtracting the Minimum Doesn't Break Anything

A natural doubt: *"If I renumber every level starting near 0, don't I lose the true absolute position of each node?"*

No — because the width computation is **entirely local to one level**. You never compare an index from level 2 against an index from level 5; you only ever compare first-vs-last **within the same level's BFS batch**. As long as the relative spacing *within* a level is preserved (which subtracting a constant offset guarantees), the width formula produces the exact same answer it would have with the "true," unnormalized indices — just without the overflow risk.

# Stage 3: Coding

## Approach — BFS with Normalized Heap-Style Indexing

**Mental workflow before writing a single line:**

```
1. Edge case: root == null → return 0

2. Queue holds pairs of (node, index). Seed with (root, 0).
   answer = 0

3. While queue is not empty:
   → levelSize = current queue size (snapshot before processing)
   → minIndex = index of the FIRST node in this batch
     (this is the node that will be dequeued first this round)
   → firstIndex, lastIndex = track as you pop through this level

   → for i in 0 to levelSize - 1:
       pop (node, currIndex) from queue
       normalizedIndex = currIndex - minIndex   ← prevents overflow

       if i == 0: firstIndex = normalizedIndex
       if i == levelSize - 1: lastIndex = normalizedIndex

       if node.left != null:
           push (node.left, 2*normalizedIndex + 1)
       if node.right != null:
           push (node.right, 2*normalizedIndex + 2)

   → answer = max(answer, lastIndex - firstIndex + 1)

4. Return answer
```

```java
import java.util.*;

class Solution {

    // Small helper class to bundle a node with its heap-style index
    static class Pair {
        TreeNode node;
        int index;

        Pair(TreeNode node, int index) {
            this.node = node;
            this.index = index;
        }
    }

    public int widthOfBinaryTree(TreeNode root) {
        if (root == null) return 0;

        int answer = 0;

        Queue<Pair> queue = new LinkedList<>();
        // Start the root at index 0
        queue.add(new Pair(root, 0));

        while (!queue.isEmpty()) {
            int levelSize = queue.size();

            // minIndex = the index of whichever node is at the
            // FRONT of the queue right now — this is the smallest
            // index on the level we're about to process
            int minIndex = queue.peek().index;

            int firstIndex = 0, lastIndex = 0;

            for (int i = 0; i < levelSize; i++) {
                Pair curr = queue.poll();

                // NORMALIZE: subtract this level's minimum index
                // before doing anything further with it. This is
                // what prevents the index from doubling out of
                // control across many levels on a skewed tree.
                int normalizedIndex = curr.index - minIndex;

                if (i == 0) firstIndex = normalizedIndex;
                if (i == levelSize - 1) lastIndex = normalizedIndex;

                // Generate children using the NORMALIZED index,
                // not the original — this keeps every level's
                // indices small and safe from overflow
                if (curr.node.left != null) {
                    queue.add(new Pair(curr.node.left, 2 * normalizedIndex + 1));
                }
                if (curr.node.right != null) {
                    queue.add(new Pair(curr.node.right, 2 * normalizedIndex + 2));
                }
            }

            // Width of this level = span between first and last
            // node's (normalized) index, inclusive
            answer = Math.max(answer, lastIndex - firstIndex + 1);
        }

        return answer;
    }
}
```

## Complexity Analysis

**Time Complexity — O(n):**

Every node is enqueued exactly once and dequeued exactly once during the BFS. At each node, the work done is constant — a subtraction, a couple of comparisons, and possibly pushing up to two children. With `n` total nodes, each handled in O(1) time, total time is **O(n)**.

**Space Complexity — O(n) in the worst case:**

The queue can hold up to one entire level's worth of nodes at a time. For a tree whose widest level approaches `n/2` nodes (e.g., a complete binary tree's last level), the queue's peak size is **O(n)**. This is the same worst-case bound as the standard level-order BFS used for LC 104's alternative approach.

---

## Why the Normalization Step Is the Entire Point of This Problem

Every other piece of this solution — BFS traversal, heap-style child indexing, the final subtraction formula — is standard machinery seen in earlier problems (level order traversal is the same mechanism from LC 104's BFS alternative; the `2i+1`/`2i+2` indexing is the standard array representation of a complete binary tree). The **one genuinely new idea** this problem introduces is recognizing that raw indices explode on skewed trees, and that re-zeroing the index at the start of every level fixes this without changing the answer — because width only ever depends on **relative** position within a level, never on a node's absolute position in the whole tree.
