# Stage 1: Identification

**Step 1 — Which topic?**

You are given the root of a **complete binary tree** — a tree where every level except possibly the last is completely filled, and all nodes in the last level are pushed as far left as possible. You need to count its total number of nodes, but the problem explicitly demands a solution **faster than O(n)**.

**Step 2 — Which pattern?**

Still **Pattern 2: Tree Properties** — you're computing a single structural fact (a count) about the tree. The trigger:

> "count nodes", "complete binary tree", **"better than O(n)"** → **Tree Properties**, but the "better than O(n)" phrase is the real signal — it tells you plain traversal alone cannot be the final answer, and you must exploit the specific structural guarantee of a *complete* tree.

**Step 3 — Which key concept?**

**O(log²n) — exploit the complete tree height property instead of plain O(n) recursion.**

The key concept is a **shortcut formula**: a **full** binary tree of height `h` (every level completely filled) has exactly `2^h - 1` nodes. If you can cheaply detect, at any node, whether *its own subtree* happens to be full, you can apply this formula and skip traversing that entire subtree — never visiting any of its nodes individually. The trick is finding a cheap way to detect "is this subtree full?" without paying O(subtree size) to check it.

# Stage 2: Intuition Building

### The Obvious Approach First — And Why It's Not Good Enough

The first instinct: do any traversal (preorder, inorder, whatever) and increment a counter at every node visited.

```
Every traversal visits every node once → O(n) time
```

This is correct, but the problem explicitly asks for something **better than O(n)**. So simply counting node-by-node, no matter which traversal you pick, cannot be the final answer — you need to find a way to **skip** visiting large chunks of the tree entirely.

### The Formula That Unlocks Everything

Take a **full** binary tree — not just complete, but *fully* filled at every level, no exceptions. If such a tree has height `h`, how many nodes does it have?

```
Level 1 (root):        1     node
Level 2:                2     nodes
Level 3:                4     nodes
...
Level h:              2^(h-1) nodes

Total = 1 + 2 + 4 + ... + 2^(h-1) = 2^h - 1
```

Concretely: a full tree of height 3 has `2^3 - 1 = 7` nodes. Verify by counting directly: 1 (root) + 2 (level 2) + 4 (level 3) = 7. ✓

```
┌────────────────────────────────────────────────────────────────┐
│  full binary tree of height h  →  exactly (2^h - 1) nodes      │
│                                                                │
│  If you can confirm a subtree is FULL, you get its node        │
│  count for FREE — just by knowing its height. No need to       │
│  visit a single node inside it.                                │
└────────────────────────────────────────────────────────────────┘
```

### The Core Question — How Do You Cheaply Detect "Is This Subtree Full"?

This is the entire crux of the problem. Checking "is a subtree full" by inspecting every node inside it would cost O(subtree size) — defeating the whole purpose. You need a **cheap test**.

Here's the insight: at any node, walk **straight down the leftmost path** (root → left → left → left → ...) and count steps — call this `leftHeight`. Separately, walk **straight down the rightmost path** (root → right → right → right → ...) and count steps — call this `rightHeight`.

> *"If leftHeight equals rightHeight, is the subtree guaranteed to be full?"*

Yes — and this is where the **complete tree property** (not just any binary tree) becomes essential. Because the input is guaranteed to be a complete tree, if the leftmost path and the rightmost path reach the same depth, there is no way for the last level to have a "gap" anywhere inside this subtree — a complete tree always fills its last level from the left, so if the rightmost node in this subtree exists at the same depth as the leftmost node, everything between them must also exist. **This equality check would NOT be safe on an arbitrary binary tree** — only the completeness guarantee makes it valid.

```
┌────────────────────────────────────────────────────────────────┐
│  leftHeight == rightHeight  (for THIS subtree specifically)    │
│       →  subtree is FULL  →  node count = 2^leftHeight - 1     │
│       →  apply formula, DO NOT recurse into this subtree       │
│                                                                │
│  leftHeight != rightHeight                                     │
│       →  subtree is NOT full (has a gap somewhere)             │
│       →  must recurse into BOTH children to count exactly      │
└────────────────────────────────────────────────────────────────┘
```

### Walking Through Striver's Example

```
        1
       / \
      2   3
     / \ / \
    4  5 6  7
   /
  8
```

Edge-list notation:
```
1 2
1 3
2 4
2 5
3 6
3 7
4 8
```

**Standing at the root (node 1):**

```
leftHeight  = walk 1 → 2 → 4 → 8 = 4 steps
rightHeight = walk 1 → 3 → 7     = 3 steps

4 ≠ 3 → NOT full → cannot apply the formula here.
Take 1 (for the current node itself) and recurse into
BOTH the left subtree and the right subtree.
```

**Recurse into the left subtree (rooted at node 2):**

```
leftHeight  = walk 2 → 4 → 8 = 3 steps
rightHeight = walk 2 → 5     = 2 steps

3 ≠ 2 → NOT full → recurse further into node 2's children.
```

At this point node 2's subtree still needs to split further — but notice this only happened because it genuinely wasn't full; we haven't wasted work, we've only paid for what we needed to check.

**Recurse into the right subtree (rooted at node 3):**

```
leftHeight  = walk 3 → 6 = 1 step
rightHeight = walk 3 → 7 = 1 step

1 == 1 → FULL! → apply the formula directly:
nodeCount = 2^1 - 1 = 1... 
```

Wait — let's be careful with what "height" means here. If `leftHeight` and `rightHeight` are counted as *number of edges* walked (1 edge to reach node 6, 1 edge to reach node 7), the **height in terms of levels** is `leftHeight + 1 = 2`. Using the formula with height counted as *levels*:

```
height (levels) = 2  →  nodeCount = 2^2 - 1 = 3
```

This matches directly: node 3's subtree contains `{3, 6, 7}` — exactly 3 nodes. ✓ So this subtree returns `3` **without ever separately visiting 6 or 7 as individual recursive calls** — the formula alone accounts for them.

**Back at node 2:** left child (node 4's subtree) still needs full recursion since it wasn't full; eventually the counts bubble up: node 2's subtree total, using Striver's own worked numbers, comes out as `1 + 7 (from a similar full-subtree shortcut lower down) + 3 = 11` in his walked example (matching his dry run tree, whose shape has an extra full layer on the left compared to the minimal example above).

The exact numbers depend on the precise tree shape, but the **mechanism** is identical every time:

```
┌──────────────────────────────────────────────────────────────────┐
│  At every node:                                                  │
│    1. Compute leftHeight (walk root→left→left→... to the end)    │
│    2. Compute rightHeight (walk root→right→right→... to the end) │
│    3. If equal → subtree is full → return 2^height - 1           │
│                  → STOP, do not recurse into this subtree        │
│    4. If not equal → return 1 + solve(left) + solve(right)       │
│                  → genuinely recurse into both children          │
└──────────────────────────────────────────────────────────────────┘
```

### Why This Is Faster Than Plain O(n)

The key realization: **you only ever recurse deeper along the "seam" where the tree stops being full** — that is, along the boundary where the last level starts to trail off. Every subtree that happens to be full anywhere else gets resolved instantly via the formula, without visiting a single one of its internal nodes.

Picture the worst-case shape: a complete tree where the last level is only partially filled. At every level as you descend from the root, one side (say, the right subtree) is *already* full and gets shortcut immediately by the formula. Only the *other* side (say, the left subtree) might still need further splitting, because that's where the "unfilled" portion of the last level actually lives. So the recursion only ever "genuinely" branches deeper along **one path** — the rest gets resolved in O(1)-per-level via the formula.

```
┌────────────────────────────────────────────────────────────────┐
│  You NEVER traverse more than O(height) = O(log n) "real"      │
│  recursive steps — because at every level, at most ONE side    │
│  needs further splitting; the other side is shortcut instantly │
│  by the full-tree formula.                                     │
└────────────────────────────────────────────────────────────────┘
```

### Why the Total Time Is O(log²n), Not O(log n)

At *each* of the `O(log n)` levels where genuine recursion happens, you still have to **compute leftHeight and rightHeight** for that node — and each of those height computations is itself an O(height) walk, i.e., O(log n) work.

```
O(log n) levels of genuine recursion
        ×
O(log n) work per level to compute leftHeight/rightHeight
        =
O(log n × log n) = O(log²n)
```

This is exactly the derivation Striver walks through: you're never touching all `n` nodes — at most `O(log n)` nodes ever trigger a "real" recursive split, and each of those pays an `O(log n)` cost to determine whether it can shortcut via the formula.

# Stage 3: Coding

## Approach 1 — Brute Force: Plain Traversal (O(n))

**The honest thinking:**

> "Just traverse the whole tree with any traversal and count every node visited."

```java
class Solution {
    public int countNodes(TreeNode root) {
        if (root == null) return 0;
        return 1 + countNodes(root.left) + countNodes(root.right);
    }
}
```

**Why this doesn't satisfy the problem:** It's correct, but it's O(n) — visiting every single node — and the problem explicitly demands better than that, by exploiting the fact that the tree is guaranteed to be *complete*, not just any binary tree. Establishes correctness only.

---

## Approach 2 — Optimal: Full-Subtree Shortcut via Height Comparison (O(log²n))

**Mental workflow before writing a single line:**

```
1. Base case: root == null → return 0

2. At the current node:
   → leftHeight  = walk straight down root→left→left→... , count steps
   → rightHeight = walk straight down root→right→right→..., count steps

3. If leftHeight == rightHeight:
   → this subtree is FULL (guaranteed valid ONLY because the
     input is a complete tree)
   → return (2^height) - 1 directly — do NOT recurse further

4. If leftHeight != rightHeight:
   → this subtree is not full — must count exactly
   → return 1 + countNodes(root.left) + countNodes(root.right)
```

```java
class Solution {
    public int countNodes(TreeNode root) {
        // Base case: an empty tree has 0 nodes
        if (root == null) return 0;

        // Compute how far a straight walk down the LEFT edge goes
        int leftHeight = findLeftHeight(root);

        // Compute how far a straight walk down the RIGHT edge goes
        int rightHeight = findRightHeight(root);

        // KEY SHORTCUT: if both heights match, this subtree is
        // guaranteed FULL — this equality check is only valid
        // because the tree is a COMPLETE binary tree. A complete
        // tree always fills its last level from the left, so no
        // gap can exist if leftmost and rightmost paths agree in depth.
        if (leftHeight == rightHeight) {
            // Full binary tree of height h has exactly (2^h - 1) nodes.
            // No need to recurse into this subtree at all —
            // every node inside it is accounted for by the formula.
            return (1 << leftHeight) - 1; // 2^leftHeight - 1
        }

        // Not full — there's a "gap" somewhere in this subtree's
        // last level. Must genuinely recurse into BOTH children
        // to count precisely.
        return 1 + countNodes(root.left) + countNodes(root.right);
    }

    // Walks root → left → left → ... until null, counting steps.
    // This is the "cheap probe" used to detect full subtrees.
    private int findLeftHeight(TreeNode node) {
        int height = 0;
        while (node != null) {
            height++;
            node = node.left;
        }
        return height;
    }

    // Walks root → right → right → ... until null, counting steps.
    private int findRightHeight(TreeNode node) {
        int height = 0;
        while (node != null) {
            height++;
            node = node.right;
        }
        return height;
    }
}
```

## Workflow Trace on a Complete Tree

```
        1
       / \
      2   3
     / \ / \
    4  5 6  7
   /
  8
```

```
solve(1):
  leftHeight  = 1→2→4→8 = 4
  rightHeight = 1→3→7   = 3
  4 ≠ 3 → NOT full → recurse into both children

  solve(2):
    leftHeight  = 2→4→8 = 3
    rightHeight = 2→5   = 2
    3 ≠ 2 → NOT full → recurse into both children

    solve(4):
      leftHeight  = 4→8 = 2
      rightHeight = 4   = 1
      2 ≠ 1 → NOT full → recurse into both children

      solve(8): leftHeight=1, rightHeight=1 → FULL
                → return 2^1 - 1 = 1

      solve(null) → return 0   (node 4's right child)

      solve(4) returns 1 + 1 + 0 = 2

    solve(5): leftHeight=1, rightHeight=1 → FULL
              → return 2^1 - 1 = 1

    solve(2) returns 1 + 2 + 1 = 4

  solve(3):
    leftHeight  = 3→6 = 1
    rightHeight = 3→7 = 1
    1 == 1 → FULL → return 2^2... 
```

Careful with height units again — using "steps taken" (edges) as the height variable exactly as coded above: `leftHeight = 1` means one edge was walked, so `(1 << leftHeight) - 1 = (1 << 1) - 1 = 1`. But node 3's subtree `{3, 6, 7}` has 3 nodes, not 1 — this reveals the height must be measured consistently. Re-examining the code: `findLeftHeight` counts **nodes visited** in the `while` loop (increments `height` once per node stepped onto, including the starting node itself), so for `solve(3)`: starting at node 3 (`height=1`), step to node 6 (`height=2`), node 6's left is null → loop ends → `leftHeight = 2`. Similarly `rightHeight`: node 3 (`height=1`), step to node 7 (`height=2`) → `rightHeight = 2`. So `leftHeight == rightHeight == 2`, and `(1 << 2) - 1 = 3` — correctly matching the 3 nodes `{3, 6, 7}`. ✓ (The trace above undercounted — `findLeftHeight`/`findRightHeight` count nodes stepped onto, starting from 1 at the root itself, not edges.)

```
  solve(3) returns 3   (via the shortcut formula)

solve(1) returns 1 + 4 + 3 = 8
```

**Total: 8 nodes** — matches the tree `{1,2,3,4,5,6,7,8}` exactly. ✓

## Complexity Analysis

**Time Complexity — O(log²n):**

The recursion only genuinely branches into both children at nodes where `leftHeight != rightHeight` — meaning the subtree straddles the "seam" where the last level trails off. As argued in Stage 2, at every level of the tree, **at most one side** requires further genuine recursion; the other side gets resolved instantly via the `2^h - 1` formula. This bounds the number of "real" recursive calls to `O(log n)` (one path down the tree, from root to the incomplete region).

At **each** of those `O(log n)` genuine recursive calls, computing `leftHeight` and `rightHeight` costs `O(log n)` (a straight walk down one side of the current subtree, whose height is itself `O(log n)`).

```
O(log n) genuine recursive levels
        ×
O(log n) work per level (height probes)
        =
O(log²n)
```

This is strictly better than the brute-force O(n), satisfying the problem's explicit requirement.

**Space Complexity — O(log n):**

The only auxiliary space is the recursion call stack for the "genuine" recursive calls, which — as established — only ever goes `O(log n)` levels deep (bounded by the tree's height, and further bounded by the fact that only one side per level needs real recursion). The height-probing helper functions (`findLeftHeight`/`findRightHeight`) use an iterative `while` loop, not recursion, so they contribute no additional stack depth.

## Comparing Brute Force vs Optimal

| Property | Brute Force (Plain Traversal) | Full-Subtree Shortcut |
| --- | --- | --- |
| Exploits completeness? | No — works on any binary tree | Yes — the `leftHeight == rightHeight → full` check is only valid because the tree is complete |
| Time | O(n) | O(log²n) |
| Space | O(h) = O(log n) for a complete tree | O(log n) |
| Core trick | None — visit every node | Full subtree → apply `2^h - 1` formula → skip recursing into it entirely |
