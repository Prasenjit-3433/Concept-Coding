# LC 104. Maximum Depth of Binary Tree

---

# Stage 1: Identification

**Step 1 — Which topic?**

You are given the root of a binary tree. You need to find its **maximum depth** — the number of nodes along the longest path from the root down to the farthest leaf.

**Step 2 — Which pattern?**

This is the **first** problem of **Pattern 2: Tree Properties**. Unlike Pattern 1, we are no longer just visiting nodes in some order — we now need to **compute something** about the tree's structure and return it as a single value. The trigger words are direct:

> "height", "maximum depth" → **Tree Properties**

**Step 3 — Which key concept?**

**Base template — height via postorder recursion (or BFS level count).**

This is the foundational problem for the *entire* pattern. Every later "Tree Properties" problem (diameter, balanced check, univalue subtrees, and so on) reuses this exact recursive shape — compute something about the left subtree, compute something about the right subtree, then **combine** those two things at the current node. Once this shape is internalized, most of Pattern 2 becomes "the same recursion, with a different combine step."

---

# Stage 2: Intuition Building

### The Core Question

Forget code for a moment. Stand at the root and ask yourself a very simple question:

> *"If I already knew the height of my left subtree, and I already knew the height of my right subtree — how would I compute my own height?"*

Think about what "height" even means here: the number of nodes on the longest path starting from you, going all the way down to a leaf. That path either dives into your left subtree first, or your right subtree first — whichever one is deeper. Either way, **you** are always the first node on that path. So:

```
height(node) = 1 (for the node itself) + the taller of its two subtrees
             = 1 + max(height(left), height(right))
```

That's the entire idea. Nothing more sophisticated is needed.

### Why This Question Naturally Points to Postorder

Notice something important: to answer "what is my height," you first need the answer for your **left child** and your **right child**. You cannot compute your own height before theirs is known. This is exactly the shape of **postorder** — fully resolve the left subtree, fully resolve the right subtree, *then* do your own work (combine) using both results.

This is the pattern-defining realization for all of Pattern 2:

```
┌───────────────────────────────────────────────────────────────┐
│  Tree Properties = Postorder + a "combine" step               │
│                                                               │
│  1. Recurse into left  → get leftResult                       │
│  2. Recurse into right → get rightResult                      │
│  3. Combine leftResult and rightResult at the current node    │
│     → that combined value IS the answer for this node         │
└───────────────────────────────────────────────────────────────┘
```

For this particular problem, the "combine" step is `1 + max(leftHeight, rightHeight)`.

### The Base Case

What is the height of an empty tree — a `null` node?

```
If node == null → there is nothing here, height is 0.
```

This is not just a technicality — it's what makes the recurrence bottom out correctly. A leaf node has two `null` children, so its height becomes `1 + max(0, 0) = 1`, which is exactly right — a single node, by itself, has height 1.

### Walking Through the Example (Striver's Tree)

```
1 2
1 3
3 4
3 6
4 5
```

Paste into csacademy.com to visualize (as a tree, children in order given). This produces:

```
          1
         / \
        2   3
           / \
          4   6
         /
        5
```

**Working from the bottom up — this is the mental order recursion actually resolves things in, even though the code is written top-down:**

```
Node 5  → leaf → height = 1 + max(0, 0) = 1

Node 2  → leaf → height = 1 + max(0, 0) = 1

Node 4  → left = height(5) = 1, right = height(null) = 0
        → height = 1 + max(1, 0) = 2

Node 6  → leaf → height = 1 + max(0, 0) = 1

Node 3  → left = height(4) = 2, right = height(6) = 1
        → height = 1 + max(2, 1) = 3

Node 1 (root) → left = height(2) = 1, right = height(3) = 3
              → height = 1 + max(1, 3) = 4
```

**Final answer: height = 4.**

Notice this matches the longest path directly: `1 → 3 → 4 → 5` is 4 nodes long — that is exactly the answer, and the recursion arrived at it without ever explicitly "finding the longest path." It just kept asking the same one question at every node and trusting the combine step to produce the right number.

### Why the Recursion Terminates

Every recursive call moves strictly to a child. The tree is finite with no cycles, so every path downward eventually reaches `null`. The base case (`height = 0`) catches that immediately and returns — which is what allows every node's `1 + max(...)` combine step, above it in the call chain, to finally execute.

### The Alternative — Level Order (BFS)

Striver explicitly points out a second valid approach: since "height" is really just "how many levels does this tree have," you can do a standard **level-order BFS**, and count how many complete levels you process before the queue empties. Each full level popped = one level of height. This works too — it's just a different traversal mechanism producing the same answer, and doesn't require recursion. We'll code the recursive version as the primary approach since Striver's transcript focuses on it, and it's the version every later Tree Properties problem builds on.

### Why Neither Approach Can Be Improved

Both the recursive and BFS approaches must, at minimum, **look at every node once** — there is no way to determine the maximum depth of a tree without examining its entire structure (a node you never visit could secretly be the deepest one). So `O(n)` time is unavoidable for both.

# Stage 3: Coding

## Approach — Recursive (Postorder Combine)

```java
class Solution {
    public int maxDepth(TreeNode root) {
        // Base case: an empty tree has height 0
        // WHY: there's nothing here to count — no node, no depth
        if (root == null) return 0;

        // Step 1: fully resolve the left subtree's height first
        int leftHeight = maxDepth(root.left);

        // Step 2: fully resolve the right subtree's height next
        int rightHeight = maxDepth(root.right);

        // Step 3: COMBINE — this node's height is 1 (itself)
        // plus whichever subtree went deeper
        return 1 + Math.max(leftHeight, rightHeight);
    }
}
```

That's the whole solution — three lines of real logic, directly translating the recurrence `height(node) = 1 + max(height(left), height(right))` into code.

---

## Alternative Approach — Level Order (BFS), for Completeness

```java
class Solution {
    public int maxDepth(TreeNode root) {
        if (root == null) return 0;

        Queue<TreeNode> queue = new LinkedList<>();
        queue.add(root);
        int depth = 0;

        // Each iteration of this outer loop processes
        // exactly one full level of the tree
        while (!queue.isEmpty()) {
            int levelSize = queue.size();
            depth++;

            // Drain exactly this level's nodes before moving on —
            // levelSize is captured BEFORE the loop starts, so
            // children added during this loop don't get processed
            // as part of the current level
            for (int i = 0; i < levelSize; i++) {
                TreeNode node = queue.poll();
                if (node.left != null) queue.add(node.left);
                if (node.right != null) queue.add(node.right);
            }
        }

        return depth;
    }
}
```

Every time the outer `while` loop completes one full pass, one entire level has been consumed — so `depth` at the end equals the number of levels, which is exactly the height.

---

## Complexity Analysis

**Time Complexity — O(n):**

Both approaches visit every node **exactly once**. In the recursive version, `maxDepth` is called once per node, does O(1) work at that node (a comparison and an addition), and returns. In the BFS version, every node is enqueued once and dequeued once. With `n` total nodes, each handled in O(1) time, total time is **O(n)** for either approach — and as established above, this cannot be improved, since determining the maximum depth requires examining every node at least once.

**Space Complexity:**

- **Recursive version — O(h), where h is the height of the tree:** The only auxiliary space is the recursion call stack, which at any point holds one frame per node on the current root-to-node path. That depth is the tree's height, `h`.
    - **Best case (balanced tree):** `h = O(log n)`.
    - **Worst case (skewed tree — a straight line of nodes, as Striver calls out explicitly):** `h = O(n)`, since the recursion stack holds all `n` nodes at once.

- **BFS version — O(n) in the worst case:** The queue can hold up to one entire level's worth of nodes at a time. For a **complete binary tree**, the last level can contain close to `n/2` nodes — so the queue's peak size is `O(n)`.

So: **both approaches are O(n) time**, and **both are O(n) space in their respective worst cases** — recursion's worst case is a skewed (linear) tree, BFS's worst case is a complete tree with a wide last level. Neither approach dominates the other in the worst case; they simply fail on *different* tree shapes, which is exactly why Striver mentions both worst cases explicitly before picking one.

---

## Why Recursive Is the Conventional Choice

Even though both have an O(n) worst case, the recursive approach is preferred in practice for one practical reason: **most binary trees encountered in real problems are reasonably balanced**, giving a call stack depth of only `O(log n)`. A perfectly skewed tree — where recursion's worst case actually triggers — is comparatively rare. The BFS version's worst case (a complete, bottom-heavy tree) is, if anything, a much more *common* shape in practice. So there's no universally "safe" choice — but recursion is simpler to write and is what the rest of Pattern 2 builds directly on top of, which is why it's the default going forward.
