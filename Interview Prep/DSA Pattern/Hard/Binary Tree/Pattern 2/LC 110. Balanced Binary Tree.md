# LC 110. Balanced Binary Tree

---

# Stage 1: Identification

**Step 1 — Which topic?**

You are given the root of a binary tree. You need to determine whether it is **height-balanced** — meaning for **every single node** in the tree, the height difference between its left and right subtree is never more than 1.

**Step 2 — Which pattern?**

Still **Pattern 2: Tree Properties** — same postorder-combine shape as LC 104. The trigger:

> "balanced", "height difference", "for every node" → **Tree Properties**

**Step 3 — Which key concept?**

**Return -1 as a sentinel for "already found unbalanced" — prune early instead of computing two separate things.**

The tricky part of this problem isn't the balance check itself — it's that you seem to need **two different pieces of information** out of one function: the **height** of a subtree (a number), and **whether it's balanced** (a boolean). The key concept is realizing you don't need two functions or two return types — you can smuggle the boolean information *inside* the height value itself, by reserving `-1` to mean "somewhere below me, balance already failed — don't bother computing anything further."

---

# Stage 2: Intuition Building

### What Does "Balanced" Actually Mean Here?

The definition, stated precisely:

> For **every node** in the tree, `|height(left subtree) - height(right subtree)| <= 1`.

This is not just a root-level check. Every single node — including ones buried deep in the tree — must satisfy this. A tree can look perfectly fine at the root and still be unbalanced three levels down.

### Two Examples, Side by Side

**Example 1 — Balanced:**

```
1 2
1 3
2 4
2 5
```

```
        1
       / \
      2   3
     / \
    4   5
```

Check every node:
```
Node 4 → no children → left height 0, right height 0 → diff 0 ✓
Node 5 → no children → left height 0, right height 0 → diff 0 ✓
Node 3 → no children → left height 0, right height 0 → diff 0 ✓
Node 2 → left = height(4) = 1, right = height(5) = 1 → diff 0 ✓
Node 1 → left = height(2) = 2, right = height(3) = 1 → diff 1 ✓
```

Every node passes → **balanced**.

**Example 2 — Not Balanced:**

```
1 2
1 3
2 4
4 5
```

```
        1
       / \
      2   3
     /
    4
   /
  5
```

Check node by node:
```
Node 5 → leaf → left 0, right 0 → diff 0 ✓
Node 3 → leaf → left 0, right 0 → diff 0 ✓
Node 4 → left = height(5) = 1, right = height(null) = 0 → diff 1 ✓
Node 2 → left = height(4) = 2, right = height(null) = 0 → diff 2 ✗  ← FAILS HERE
```

The moment we reach node 2, left height is 2 (via 4 → 5) and right height is 0 (no right child at all). The difference is 2, which breaks the rule. It doesn't matter that node 1 or node 3 look fine individually — **one failing node anywhere in the tree is enough to make the whole tree unbalanced.**

---

### The Naive Approach — And Why It's Slow

The first instinct: at every node, compute the height of its left subtree, compute the height of its right subtree, and compare. If the difference exceeds 1, return false. Otherwise, recurse into both children and check them too.

```
isBalanced(node):
    if node is null: return true
    leftHeight  = computeHeight(node.left)    ← a FULL traversal
    rightHeight = computeHeight(node.right)   ← a FULL traversal
    if |leftHeight - rightHeight| > 1: return false
    return isBalanced(node.left) AND isBalanced(node.right)
```

Why is this slow? Because `computeHeight()` is itself an `O(n)` traversal — and you are calling it **at every single node** you visit during `isBalanced`. That's an `O(n)` computation nested inside an `O(n)` traversal:

```
┌────────────────────────────────────────────────────────────────┐
│  At every node, you re-walk its entire subtree just to get     │
│  its height — even though you're about to walk that same       │
│  subtree again anyway for the recursive isBalanced() calls.    │
│                                                                │
│  Total work: O(n) nodes × O(n) height computation = O(n²)      │
│  Worst case (skewed tree): this really does blow up to O(n²)   │
└────────────────────────────────────────────────────────────────┘
```

This is confirmed by the exact same skewed-tree argument that showed up in LC 104 — a straight-line tree makes the inner height computation cost `O(n)` at the very node where it matters most, and you pay that cost `O(n)` times over.

### The Core Question That Unlocks O(n)

Look closely at what's wasteful: you already have a function — the one from LC 104 — that computes height in `O(n)` by visiting every node **exactly once**, using postorder (left height, right height, then combine). Every single node's height is computed *once* as a side effect of that recursion.

So the real question becomes:

> *"Can I get the balance check to piggyback on the exact same single pass that already computes height — instead of running a second, separate pass?"*

The obstacle is that a function can only `return` one thing. `computeHeight` returns an `int`. But `isBalanced` needs to know a `boolean`. How do you get both out of one function, one pass, one return type?

### The Trick — Repurpose `-1` as "Balance Already Failed"

This is the entire insight of the problem, and it's a clever but simple move:

> *"What if, instead of ever returning a normal height value once balance has failed, I just return `-1` — a value that can never occur as a real height — and treat that as a signal to short-circuit everything above it?"*

A real height is always `0` or a positive number. `-1` is not a value height can naturally take. That makes it a safe, unambiguous **sentinel** — something the rest of the recursion can check for and immediately recognize as "stop, don't bother computing further, unbalance was already found somewhere below."

```
┌────────────────────────────────────────────────────────────────┐
│  The SAME function that computes height now does two jobs:     │
│                                                                │
│  → If the subtree IS balanced: return its real height (≥ 0)    │
│  → If the subtree is NOT balanced: return -1 (the sentinel)    │
│                                                                │
│  One int. One return type. Two meanings, cleanly separated     │
│  by sign — because a genuine height can never be negative.     │
└────────────────────────────────────────────────────────────────┘
```

### Walking Through How the Sentinel Propagates Upward

Take the unbalanced example again:

```
        1
       / \
      2   3
     /
    4
   /
  5
```

Trace the recursive calls exactly as they'd execute, bottom-up:

```
solve(5):  leaf → leftHeight=0, rightHeight=0 → diff=0 ok → return 1

solve(4):  leftHeight = solve(5) = 1
           rightHeight = solve(null) = 0
           |1 - 0| = 1 → OK, not yet unbalanced
           → return 1 + max(1, 0) = 2

solve(2):  leftHeight = solve(4) = 2
           rightHeight = solve(null) = 0
           |2 - 0| = 2 → EXCEEDS 1 → return -1
           (this is the moment balance actually fails)

solve(3):  leaf → return 1

solve(1):  leftHeight = solve(2) = -1   ← the sentinel arrives here!

           BEFORE even computing anything with this value,
           check: is leftHeight == -1?
           YES → immediately return -1 without even
           bothering to call solve(3) or compute any max()

           (in this particular trace solve(3) may have
           already run depending on evaluation order, but
           the point is: its result is now IRRELEVANT —
           the -1 from the left side is enough to condemn
           the whole tree)
```

Final result at the root: **`-1`** → the tree is **not balanced**. The `-1` acted like a piece of bad news that gets passed up the call chain, and every level above it, the instant it sees that bad news, stops doing any further real work and just forwards the same bad news further up.

```
┌────────────────────────────────────────────────────────────────┐
│  Think of -1 as a "poison" value.                              │
│                                                                │
│  The moment ANY node produces -1, every ancestor above it      │
│  in the call chain, upon receiving -1 from a child, does       │
│  NOT compute a real height — it just passes -1 further up      │
│  immediately, without doing any additional work.               │
│                                                                │
│  This is exactly why we check "if leftHeight == -1: return     │
│  -1" BEFORE even calling the right recursion, and again        │
│  "if rightHeight == -1: return -1" BEFORE the diff check —     │
│  short-circuiting means we never waste work above a failure.   │
└────────────────────────────────────────────────────────────────┘
```

### Why This Still Uses the Exact Same Postorder Shape as LC 104

Nothing about the traversal order changed from LC 104. It's still: get left's answer, get right's answer, then combine at the current node. The **only** additions are two early-exit checks — "did left already fail?" and "did right already fail?" — inserted right before the combine step. Everything else, including the base case (`null → 0`) and the combine formula (`1 + max(left, right)`), is identical to the height function.

```
┌────────────────────────────────────────────────────────────────┐
│  LC 104 recurrence:                                            │
│      height(node) = 1 + max(height(left), height(right))       │
│                                                                │
│  LC 110 recurrence — SAME shape, two guard checks added:       │
│      leftHeight  = solve(node.left)                            │
│      if leftHeight == -1: return -1        ← NEW               │
│      rightHeight = solve(node.right)                           │
│      if rightHeight == -1: return -1       ← NEW               │
│      if |leftHeight - rightHeight| > 1: return -1  ← NEW       │
│      return 1 + max(leftHeight, rightHeight)                   │
│                                                                │
│  Two extra lines convert a height calculator into a            │
│  balance checker, in the SAME single pass.                     │
└────────────────────────────────────────────────────────────────┘
```

### Why This Achieves O(n) Instead of O(n²)

Every node is visited **exactly once**. There is no separate `computeHeight()` call anywhere — the height computation and the balance check are fused into the same single postorder traversal. Once fused, the total work is bounded by the number of nodes, exactly like LC 104: **O(n)**, not `O(n²)`.

# Stage 3: Coding

## Approach 1 — Brute Force (O(n²))

**The honest thinking:**

> "At every node, separately compute the height of its left and right subtree using a full traversal, compare them, then recurse to check the children too."

```java
class Solution {
    public boolean isBalanced(TreeNode root) {
        if (root == null) return true;

        int leftHeight = height(root.left);
        int rightHeight = height(root.right);

        if (Math.abs(leftHeight - rightHeight) > 1) return false;

        // still need to check every OTHER node too —
        // a node deeper down could independently be unbalanced
        return isBalanced(root.left) && isBalanced(root.right);
    }

    private int height(TreeNode node) {
        if (node == null) return 0;
        return 1 + Math.max(height(node.left), height(node.right));
    }
}
```

**Why this is O(n²):** `height()` is a full O(n) traversal, and it gets called at every one of the O(n) nodes visited by `isBalanced`. Worst case (a skewed tree), this becomes `O(n²)`. Establishes correctness, not efficiency.

---

## Approach 2 — Optimal: Fused Height + Balance Check via Sentinel (O(n))

**Mental workflow before writing a single line:**

```
1. Write a single recursive function solve(node) that returns an int:
   → -1 if the subtree rooted at node is NOT balanced
   → the actual height if it IS balanced (and everything below it too)

2. Base case: node == null → height 0 (empty tree, trivially balanced)

3. leftHeight = solve(node.left)
   if leftHeight == -1: return -1 immediately (don't even check right)

4. rightHeight = solve(node.right)
   if rightHeight == -1: return -1 immediately

5. if |leftHeight - rightHeight| > 1: return -1
   (THIS node itself violates the balance condition)

6. Otherwise: return 1 + max(leftHeight, rightHeight)
   (this subtree is balanced so far — pass the real height upward)

7. In the main function: call solve(root).
   → if result == -1: return false
   → else: return true
```

```java
class Solution {
    public boolean isBalanced(TreeNode root) {
        // If the fused function returns -1 anywhere, the tree
        // is unbalanced. Any non-negative result means balanced.
        return solve(root) != -1;
    }

    private int solve(TreeNode node) {
        // Base case: an empty tree has height 0,
        // and is trivially balanced
        if (node == null) return 0;

        // Step 1: resolve LEFT subtree first
        int leftHeight = solve(node.left);

        // EARLY EXIT: if the left subtree already failed,
        // don't bother computing anything further at this
        // node — just forward the failure upward immediately
        if (leftHeight == -1) return -1;

        // Step 2: resolve RIGHT subtree next
        int rightHeight = solve(node.right);

        // EARLY EXIT: same idea, for the right subtree
        if (rightHeight == -1) return -1;

        // Step 3: THIS node's own balance check —
        // even if both children were individually balanced,
        // THIS node's own left/right height difference
        // might still violate the rule
        if (Math.abs(leftHeight - rightHeight) > 1) return -1;

        // Step 4: COMBINE — everything checks out so far,
        // return the real height so the caller above can
        // use it for its own balance check
        return 1 + Math.max(leftHeight, rightHeight);
    }
}
```

---

## Complexity Analysis

**Time Complexity — O(n):**

Every node is visited **exactly once** by `solve()`. At each node, the work done is constant — two comparisons against `-1`, one absolute-difference check, one `max()`, one addition. There is no repeated re-traversal of any subtree, unlike the brute force. With `n` total nodes, each handled in O(1) time, total time is **O(n)** — matching the height computation from LC 104 exactly, since the two are now fused into a single pass.

**Space Complexity — O(h), where h is the height of the tree:**

The only auxiliary space is the recursion call stack, exactly as in LC 104 — one frame per node on the current root-to-node path.

- **Best case (balanced tree):** `h = O(log n)`.
- **Worst case (skewed tree):** `h = O(n)`, since the call stack holds all `n` nodes on the single chain at once.

So: **O(h) auxiliary space — O(log n) balanced, O(n) worst case (skewed tree)**, same bound as every recursive tree traversal so far.

## Comparing Brute Force vs Optimal

| Property | Brute Force | Fused (Optimal) |
| --- | --- | --- |
| Height computed | Separately, at every node, via a fresh O(n) call | Once per node, as a byproduct of the same traversal |
| Time | O(n²) worst case | O(n) |
| Space | O(h) — plus O(h) again inside each `height()` call | O(h) |
| Core trick | None — direct translation of the definition | Repurpose `-1` as a sentinel to smuggle a boolean out of an `int`-returning function |

## The Key Takeaway

```
┌────────────────────────────────────────────────────────────────┐
│  A subtree is unbalanced if EITHER:                            │
│    → its left or right subtree is already unbalanced, OR       │
│    → its own |leftHeight - rightHeight| > 1                    │
│                                                                │
│  THE TRICK: reuse the LC 104 height recurrence, but let the    │
│  function return -1 instead of a real height the moment        │
│  unbalance is detected ANYWHERE below the current node.        │
│                                                                │
│  -1 is a safe sentinel because heights are never negative.     │
│  Once a -1 appears, every ancestor short-circuits and just     │
│  forwards -1 upward — no further real computation happens.     │
│                                                                │
│  This fuses "compute height" and "check balance" into ONE      │
│  single postorder pass — turning O(n²) into O(n).              │
│                                                                │
│  Time  — O(n): every node visited exactly once.                │
│  Space — O(h): O(log n) balanced, O(n) worst case (skewed).    │
└────────────────────────────────────────────────────────────────┘
```
