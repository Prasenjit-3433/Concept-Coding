# LC 637. Average of Levels in Binary Tree

---

# Stage 1: Identification

**Step 1 — Which topic?**

You are given the root of a binary tree. For every level, you need to return the **average** of all node values at that level.

**Step 2 — Which pattern?**

Still **Pattern 3: Level Order Traversal**. The trigger:

> "average of each level" → need every level's values grouped together before you can average them → **BFS**

**Step 3 — Which key concept?**

**Same BFS skeleton as LC 102 — but the per-level list is replaced by a running sum and count, since the list itself is never needed.**

This is the same realization that shows up repeatedly across problem variants of a known template: LC 102 collects a *list* per level because the list is the required output. Here, the output isn't the values themselves — it's a single number derived from them. So there is no need to materialize `List<Integer> level` at all; a running `sum` and the already-known `levelSize` (the count) are sufficient to compute the answer for that level, and nothing more needs to be stored.

### The Core Question — What Does "Average of a Level" Actually Need?

An average is `sum / count`. Both quantities are things BFS already hands you for free, level by level, without any extra bookkeeping:

- `count` is exactly `levelSize` — the number of nodes snapshotted at the start of processing that level, already computed in every BFS-on-a-tree solution so far.
- `sum` is just an accumulator — add each popped node's value to a running total as you go.

Neither of these requires keeping the individual values around afterward. Once you know a level's total sum and its size, the values themselves have served their purpose and can be discarded.

```
┌────────────────────────────────────────────────────────────────────┐
│  LC 102 needed: a LIST of this level's values (that IS the         │
│                  required output)                                  │
│                                                                    │
│  LC 637 needs:  a single NUMBER derived from this level's          │
│                  values (sum / count) — no list required at all    │
│                                                                    │
│  Same BFS skeleton. Only what you accumulate per level changes.    │
└────────────────────────────────────────────────────────────────────┘
```

### Walking Through the Idea on the Example

```
Level 0: queue = [1], levelSize = 1
  pop 1, sum = 1
  average = 1 / 1 = 1.0

Level 1: queue = [2, 3], levelSize = 2
  pop 2, sum = 2
  pop 3, sum = 5
  average = 5 / 2 = 2.5

Level 2: queue = [4, 5], levelSize = 2
  pop 4, sum = 4
  pop 5, sum = 9
  average = 9 / 2 = 4.5
```

**Answer: `[1.0, 2.5, 4.5]`**

### Why `sum` Needs to Be a Wider Type Than `int`

A subtlety worth flagging explicitly: node values in these problems can individually be as large as `Integer.MAX_VALUE` (or close to it), and a level can contain a large number of nodes. Summing many such values inside a plain `int` risks **overflow** — the sum silently wraps around into a nonsense negative number, and the resulting "average" would be wrong without any visible error. Using a `long` accumulator for `sum` gives enormous headroom before that becomes a concern, at the cost of nothing.

### Why the Division Needs a Cast

`levelSum` (a `long`) divided by `levelSize` (an `int`) is **integer division** if left as-is — `5 / 2` would silently truncate to `2`, not `2.5`. The problem asks for the actual average, a `double`. Casting one side of the division to `double` before dividing forces the division itself to happen in floating point, preserving the fractional part.

### Why the Rest of the BFS Mechanics Are Completely Unchanged

Seed the queue with root, snapshot `levelSize` before draining, pop exactly that many nodes while pushing their children for the next round — all of this is identical to LC 102. The only structural change is *what gets built* per level: instead of a `List<Integer>` that gets appended to the outer answer list, a single `double` (the average) gets appended instead.

# Stage 3: Coding

## Approach — BFS, Accumulating Sum Instead of Collecting a List

**Mental workflow before writing a single line:**

```
1. Edge case: root == null → return empty list

2. Standard BFS setup: queue seeded with root

3. For each level:
   → snapshot levelSize = queue.size()
   → running sum = 0 (use long, to avoid overflow)
   → pop levelSize nodes, push their children for the next round,
     add each popped node's value into sum
   → append (double) sum / levelSize to the answer list

4. Return the answer list
```

```java
class Solution {
    public List<Double> averageOfLevels(TreeNode root) {
        List<Double> result = new ArrayList<>();

        // Nothing to traverse
        if (root == null) return result;

        Queue<TreeNode> queue = new LinkedList<>();
        queue.add(root);

        while (!queue.isEmpty()) {
            int levelSize = queue.size();

            // long, not int — guards against overflow when many
            // large values are summed within a single wide level
            long levelSum = 0;

            for (int i = 0; i < levelSize; i++) {
                TreeNode curr = queue.poll();

                if (curr.left != null) queue.add(curr.left);
                if (curr.right != null) queue.add(curr.right);

                levelSum += curr.val;
            }

            // Cast to double BEFORE dividing — otherwise this is
            // integer division and the fractional part is lost
            result.add((double) levelSum / levelSize);
        }

        return result;
    }
}
```

---

## Complexity Analysis

**Time Complexity — O(n):**

Every node is pushed onto the queue exactly once and popped exactly once, doing O(1) work at each step (a couple of null checks, one addition). With `n` total nodes, total time is **O(n)** — identical to LC 102's BFS, since the only added work per node is a single `long` addition, still O(1).

**Space Complexity — O(n) for the queue in the worst case, O(h) for the output:**

The queue can hold up to O(n) nodes at the widest level, exactly like every BFS-on-a-tree solution so far. The `result` list, however, is much smaller than in LC 102 — instead of storing every node's value, it stores exactly one `double` per level, so its size is bounded by the tree's height `h` (number of levels), not `n`. This is a genuine, if modest, space improvement over LC 102's output size — a direct consequence of not needing to materialize each level's full list of values.
