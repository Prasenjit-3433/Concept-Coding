# LC 1092. Shortest Common Supersequence

*(Continuing Pattern 7 — builds directly on LC 1143's LCS and the Print LCS backtracking technique, combined into one final synthesis problem)*

---

# Stage 1: Identification

**Step 1 — Which topic?**

You're given two strings, `str1` and `str2`. You need to construct the **shortest string** that contains **both** `str1` and `str2` as subsequences.

```
str1 = "brute"
str2 = "groot"

A valid supersequence: "bgruteoot" (just str1 + str2 concatenated, length 10)
  → does it contain "brute"? yes. does it contain "groot"? yes.
  → but it's clearly not the SHORTEST one — there's overlap being wasted

The shortest one: "bgruteot" is NOT quite right — let's use Striver's actual
answer: "gbrutoot" (or any valid reordering that's length 8)
  → contains "brute" as a subsequence ✓
  → contains "groot" as a subsequence ✓
  → length 8, and no shorter string can achieve both
```

**Step 2 — Which pattern?**

Two strings, and the question revolves entirely around what characters they share and in what order. This is **Pattern 7: LCS** — and it turns out to be the natural **capstone** problem of the pattern, combining two skills you've already fully built: the **LCS length formula** (like LC 583) and the **backtracking reconstruction** (like Print LCS).

**Step 3 — Which key concept?**

**LCS first, then reconstruct the merged string via the same backtracking walk as Print LCS.**

The key insight: minimizing the length of a supersequence is the same as **maximizing the overlap** you get to reuse between the two strings. Any character that is common to both strings — in the sense of the LCS — only needs to be written **once** in the final answer, instead of once for each string. Every other character (the ones *not* part of that shared backbone) must still appear, exactly once each, because nothing else in the problem allows you to skip a character from either original string.

So the whole problem reduces to:

```
1. Find LCS(str1, str2)              → tells you what CAN be shared
2. Reconstruct the supersequence by walking the SAME dp table
   backward — exactly like Print LCS — except now, instead of
   only recording MATCHED characters, you record EVERY character
   you pass through (matched or not), since every character from
   both strings must appear somewhere in the final answer.
```

This is not a new recurrence at all — it is the **exact same `dp[i][j]` table** from LC 1143, walked backward with the **exact same three-way branching logic** as Print LCS, with one extra rule added: what to do on a "no match" step (which Print LCS never needed to record anything for, but this problem does).

# Stage 2: Intuition Building

### Why "Just Concatenate Both Strings" Is Wasteful

The crude answer to "give me *a* string containing both as subsequences" is simply `str1 + str2` — glue them together. This trivially works: `str1` sits at the front (obviously a subsequence of itself), and `str2` sits at the back (also obviously a subsequence of itself). Length = `n + m`.

But this wastes every single character the two strings have in common. Consider `str1 = "brute"`, `str2 = "groot"`. Both contain an `r` and a `t`. If you concatenate them, you write `r` twice (once inside `"brute"`, once inside `"groot"`) and `t` twice — even though, as you'll see, **a single shared `r` and a single shared `t`, placed correctly, can simultaneously serve both strings' subsequence requirement.**

### The Core Realization — Shared Characters Need Only Appear Once

Look at `str1 = "brute"` and `str2 = "groot"` side by side:

```
str1:  b  r  u  t  e
str2:  g  r  o  o  t
```

Both strings contain `r` and `t`, and — critically — in **both** strings, the `r` comes *before* the `t` (relative order matches). That means: if you place a **single** `r` and a **single** `t` (in that order) somewhere in your final answer, that one `r` can simultaneously act as *the* `r` needed by `str1`'s subsequence check *and* the `r` needed by `str2`'s subsequence check. Same for the `t`.

This is precisely what a **common subsequence** captures — a sequence of characters that appears, in the same relative order, in both strings. And since you want to reuse as much as possible (to keep the final string as short as possible), you want the **longest** such common subsequence. That is exactly `LCS(str1, str2)`.

```
LCS("brute", "groot") = "rt"     (length 2)
```

### Building the Formula

Once you fix the shared backbone (`"rt"`, length 2), think about what's left over:

```
str1 = "brute"  →  characters NOT in the shared "rt" backbone: b, u, e   (3 characters)
str2 = "groot"  →  characters NOT in the shared "rt" backbone: g, o, o   (3 characters)
```

Every one of these leftover characters must still appear in the final answer exactly once — there's no way around writing `b`, `u`, `e` somewhere for `str1`'s sake, and no way around writing `g`, `o`, `o` somewhere for `str2`'s sake. Only the **shared** part (`"rt"`) gets to be written once instead of twice.

```
Total length = (leftover from str1) + (leftover from str2) + (shared backbone, written once)
             = (n - LCS) + (m - LCS) + LCS
             = n + m - LCS
```

Verify: `n = 5`, `m = 5`, `LCS = 2` → `5 + 5 - 2 = 8` ✓ — matches the length-8 answer Striver found by hand.

**Notice the formula is different from LC 583's `n + m - 2·LCS`.** In LC 583, the shared part was *entirely removed* from both sides (only deletions were allowed, no character was ever kept twice — the shared part contributed nothing extra to the final "equal" string beyond being counted once overall as part of both reduced strings, and the total deletions subtracted it twice). Here, the shared part is *kept once* in the final answer (not deleted at all) — so it's subtracted only **once**, since it would otherwise be double-counted by naively adding `n + m`.

### Why Concatenation Alone Doesn't Tell You *Where* to Place Things

Knowing the *length* is `n + m - LCS` doesn't yet tell you how to actually **build** the string. You need to know, character by character, which pieces of `str1` and `str2` to interleave, and in what order — while making sure the shared characters (`r`, `t`) are written down only once each, at the right moments.

This is where the connection to **Print LCS** becomes exact. Recall from Print LCS: the finished `dp[i][j]` table already encodes, at every cell, which of the two "predecessor" cells produced it — a diagonal move (on a match) or an up/left move (on a mismatch). Walking backward from `dp[n][m]` to a base-case cell traces out the entire alignment between the two strings, one decision at a time.

### The One New Rule — What to Do on a Mismatch

In Print LCS, when characters didn't match, you simply moved to whichever neighbor (`dp[i-1][j]` or `dp[i][j-1]`) was larger — and recorded **nothing**, because a mismatched character is not part of the common subsequence.

Here, a mismatched character still needs to end up in the final supersequence — it's just not part of the *shared* backbone. So the rule becomes:

```
┌───────────────────────────────────────────────────────────────────┐
│  CASE 1 — Characters match (str1[i-1] == str2[j-1])               │
│  ─────────────────────────────────────────────────                │
│  This character is part of the shared backbone — write it         │
│  down ONCE (it simultaneously serves both strings).               │
│  → Move diagonally: i--, j--                                      │
│                                                                   │
│  CASE 2 — Characters do NOT match                                 │
│  ────────────────────────────────                                 │
│  This character is NOT shared — but it still must appear in       │
│  the final answer, because it belongs to one of the two strings.  │
│                                                                   │
│  → If dp[i-1][j] > dp[i][j-1]:                                    │
│        this cell's value came from ABOVE (str1's side)            │
│        → write str1[i-1] into the answer (it has no match here)   │
│        → move UP: i--                                             │
│  → Else:                                                          │
│        this cell's value came from the LEFT (str2's side)         │
│        → write str2[j-1] into the answer                          │
│        → move LEFT: j--                                           │
│                                                                   │
│  Stop when: i == 0 OR j == 0                                      │
└───────────────────────────────────────────────────────────────────┘
```

The crucial difference from Print LCS: **every step of this walk writes something into the answer** — either a shared matched character (once) or an unshared character (from whichever string produced this cell). Print LCS only wrote something on a match; here, every single step contributes a character.


Walking through a few cells explicitly:

- `dp[2][2]`: `str1[1]='r'`, `str2[1]='r'` → match → `1 + dp[1][1] = 1 + 0 = 1`
- `dp[3][2]`: `str1[2]='u'`, `str2[1]='r'` → no match → `max(dp[2][2]=1, dp[3][1]=0) = 1`

**Final `dp[5][5] = 2`** → `LCS("brute", "groot") = 2` ("rt"), matching Striver's hand-derivation exactly.

### Tracing the Backtrack — Building the Supersequence

Start at `i = 5, j = 5` (value 2).

```
Step 1: i=5, j=5
        str1[4]='e', str2[4]='t' → NO MATCH
        compare dp[4][5]=2 vs dp[5][4]=1 → UP is bigger → move UP
        write str1[4] = 'e'   →  answer so far (reversed): "e"
        i = 4

Step 2: i=4, j=5
        str1[3]='t', str2[4]='t' → MATCH!
        write 't' (shared, written once)  →  answer so far: "et"
        move diagonally: i=3, j=4

Step 3: i=3, j=4
        str1[2]='u', str2[3]='o' → NO MATCH
        compare dp[2][4]=1 vs dp[3][3]=1 → tie, else-branch takes LEFT
        write str2[3] = 'o'   →  answer so far: "eto"
        j = 3

Step 4: i=3, j=3
        str1[2]='u', str2[2]='o' → NO MATCH
        compare dp[2][3]=1 vs dp[3][2]=1 → tie, else-branch takes LEFT
        write str2[2] = 'o'   →  answer so far: "etoo"
        j = 2

Step 5: i=3, j=2
        str1[2]='u', str2[1]='r' → NO MATCH
        compare dp[2][2]=1 vs dp[3][1]=0 → UP is bigger → move UP
        write str1[2] = 'u'   →  answer so far: "etoou"
        i = 2

Step 6: i=2, j=2
        str1[1]='r', str2[1]='r' → MATCH!
        write 'r' (shared, written once)  →  answer so far: "etoour"
        move diagonally: i=1, j=1

Step 7: i=1, j=1
        str1[0]='b', str2[0]='g' → NO MATCH
        compare dp[0][1]=0 vs dp[1][0]=0 → tie, else-branch takes LEFT
        write str2[0] = 'g'   →  answer so far: "etoourg"
        j = 0

Step 8: j == 0 → STOP main loop, but i = 1 still > 0
        remaining leftover from str1: write str1[0] = 'b'
        answer so far: "etoourgb"
        i = 0
```

Collected string (built in reverse): `"etoourgb"`. Reverse it → **`"bgruotoe"`**... let's double check against Striver's own reasoning — his trace produced `"gbrutoot"` after reversal, following his own tie-breaking choices (he chose to move UP first at certain ties where this trace chose LEFT, since ties can go either way and still be valid). Either resulting string is a **valid, equally correct** shortest common supersequence of length 8 — this is expected: **multiple correct answers exist**, exactly as Striver states in the video, because ties in the `max()` comparison can be broken either way without affecting the length.

Either reconstruction contains `"brute"` and `"groot"` as subsequences and has length exactly `n + m - LCS = 8`.

# LC 1092. Shortest Common Supersequence — Stage 3: Coding

---

## Approach — Tabulation (LCS table) + Backtracking Reconstruction

### Step 1: Build the LCS Table (identical to LC 1143)

```java
class Solution {
    public String shortestCommonSupersequence(String str1, String str2) {
        int n = str1.length();
        int m = str2.length();

        // dp[i][j] = LCS length of str1[0..i-1] and str2[0..j-1]
        int[][] dp = new int[n + 1][m + 1];

        for (int i = 1; i <= n; i++) {
            for (int j = 1; j <= m; j++) {
                if (str1.charAt(i - 1) == str2.charAt(j - 1)) {
                    dp[i][j] = 1 + dp[i - 1][j - 1];
                } else {
                    dp[i][j] = Math.max(dp[i - 1][j], dp[i][j - 1]);
                }
            }
        }

        // Step 2: backtrack from (n, m) to build the supersequence
        StringBuilder sb = new StringBuilder();
        int i = n, j = m;

        while (i > 0 && j > 0) {
            if (str1.charAt(i - 1) == str2.charAt(j - 1)) {
                // shared character — write once
                sb.append(str1.charAt(i - 1));
                i--;
                j--;
            } else if (dp[i - 1][j] > dp[i][j - 1]) {
                // came from above — str1's character has no match here
                sb.append(str1.charAt(i - 1));
                i--;
            } else {
                // came from the left — str2's character has no match here
                sb.append(str2.charAt(j - 1));
                j--;
            }
        }

        // Step 3: one string may still have leftover characters
        while (i > 0) {
            sb.append(str1.charAt(i - 1));
            i--;
        }
        while (j > 0) {
            sb.append(str2.charAt(j - 1));
            j--;
        }

        // built in reverse — flip it
        return sb.reverse().toString();
    }
}
```

## Complexity Analysis

**Time Complexity — O(n × m):**

Building the dp table costs `O(n × m)` — identical to LC 1143. The backtracking walk moves `i` or `j` down by at least 1 on every iteration, so it takes at most `O(n + m)` steps. The two leftover `while` loops at the end together add at most `O(n + m)` more. Total: `O(n × m) + O(n + m)`, which simplifies to **O(n × m)** since the table-building term dominates.

**Space Complexity — O(n × m):**

The dp table is `(n+1) × (m+1)` integers — **O(n × m)**. The `StringBuilder` holds at most `n + m` characters — **O(n + m)**, dominated by the table. No recursion stack, everything is iterative. Total: **O(n × m)**.

## Final Comparison

| Approach | Time | Space | Notes |
|---|---|---|---|
| **Tabulation + Backtracking** | **O(n × m)** | **O(n × m)** | Only approach needed — submit this |

There is no meaningful space-optimized (rolling array) version here, unlike every other Pattern 7 problem so far — because the **backtracking step needs the entire finished table** to walk through, not just the last row. Collapsing to two rolling arrays would destroy all the earlier rows before the reconstruction phase ever gets to read them.
