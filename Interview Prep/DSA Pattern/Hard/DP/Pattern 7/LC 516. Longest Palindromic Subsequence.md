# LC 516. Longest Palindromic Subsequence

*(Continuing Pattern 7 — this problem needs no new recurrence at all, just a clever reduction to LCS)*

---

# Stage 1: Identification

**Step 1 — Which topic?**

You're given a single string. A **palindrome** is a string that reads identically forwards and backwards — `"bab"`, `"aba"`, `"bbbb"` are all palindromes. You need to find a **subsequence** of the given string (order preserved, characters can be skipped) that is a palindrome, and among all such palindromic subsequences, you want the **longest** one. You only need to return its length.

```
s = "bbbab"

Some subsequences of s:      Is it a palindrome?
  "b"                          yes (trivially — single characters always are)
  "bb"                         yes
  "ba"                         no
  "bab"                        yes
  "bbbb"                       yes   ← this one is length 4
  "bbbab"                      no  (the full string itself — b b b a b, reversed is b a b b b, not equal)
```

The longest palindromic subsequence here is `"bbbb"`, length 4.

The moment you see **"find the longest subsequence satisfying some structural property"** — you're back in familiar territory: to find the best among all subsequences, you must conceptually try all of them, and once you notice overlapping subproblems in that search, it becomes Dynamic Programming.

**Step 2 — Which pattern?**

This is where it gets interesting. Every problem you've solved in **Pattern 7: LCS** so far — LC 1143, Print LCS, Longest Common Substring — started with **two strings handed to you directly**. This problem hands you only **one** string. So at first glance, it doesn't look like it belongs in this pattern at all — it looks like it should belong somewhere else, maybe a new "palindrome DP" pattern.

But it does belong here, and the reason is the entire point of this lecture: **you can manufacture a second string out of the one you're given**, and once you do, the problem becomes an LCS problem in disguise. That is still **Pattern 7: LCS** — just with an extra setup step before the familiar recurrence kicks in.

**Step 3 — Which key concept?**

**Reduction, not a new recurrence.** This is the same meta-skill you've already practiced in the 0/1 Knapsack pattern — LC 416 (Partition Equal Subset Sum) reduced itself entirely to Subset Sum with a computed target, and LC 494 (Target Sum) reduced itself to Count Partitions with a derived difference. In both of those cases, no new DP logic was written; only a mathematical transformation of the *input* was needed before calling a solver you already owned.

The exact same thing happens here:

```
Longest Palindromic Subsequence(S)  =  LCS(S, reverse(S))
```

No new state. No new base case. No new match/no-match branch. You already own the LCS solution completely from LC 1143 — this problem is a thin wrapper: build the reverse of the string, then call your existing LCS function on the original and the reverse. The only genuine work in this problem is understanding *why* that equality is true — because if you don't understand why, this looks like a magic trick rather than a reduction you could invent yourself on a new problem.

# Stage 2: Intuition Building

### Why the Brute Force Instinct Doesn't Scale

The most direct way to attack this problem is: generate every subsequence of the string, check which ones are palindromes, and keep the longest palindromic one. A string of length `n` has `2^n` subsequences, so this brute force costs roughly `O(2^n)` — for `n = 1000` (a perfectly ordinary constraint), this is hopelessly impractical. You need a recurrence, not enumeration. The question is: what recurrence?

You *could* try to invent a brand-new DP specifically for palindromic subsequences, tracking two pointers moving inward from both ends of the string and checking whether the outer characters match. That approach exists and works — but it requires designing an entirely new recurrence from scratch. The far more efficient path, and the one worth internalizing as a general skill, is to notice that this problem is secretly *already solved* by something you know.

### Discovering the Reduction — Starting From a Concrete Example, Not the Definition

Rather than starting from the abstract definition of "palindrome" and reasoning forward (which can feel like being handed a fact to accept rather than a fact you'd naturally arrive at), it's more convincing to start from an actual palindrome sitting inside a real string and watch what happens to it under reversal.

Take a slightly longer example: `S = "bbabcbcab"`. Somewhere inside this string sits the palindromic subsequence `"babcbab"` (you can check: reversed, it reads the same). Mark where its characters live inside `S`:

```
S =  b  b  a  b  c  b  c  a  b
        └──┴──┴──┴──┴──┴──┘
        the characters that make up "babcbab" are scattered
        through S at various positions, but always in this order
```

Now reverse the *entire* string `S` to get `S' = "bacbcbabb"`. Ask: what happens to the specific characters that made up `"babcbab"`?

```
┌────────────────────────────────────────────────────────────────────┐
│  A palindrome, by its own definition, reads the same forwards      │
│  and backwards. So if you take JUST those characters — the ones    │
│  spelling out "babcbab" — and reverse their order, you get the     │
│  exact same sequence of characters back: "babcbab" reversed is     │
│  still "babcbab".                                                  │
│                                                                    │
│  Meanwhile, every OTHER character in S that is NOT part of this    │
│  palindrome gets shuffled to a different relative position when    │
│  the whole string is reversed — because reversal flips the order   │
│  of everything, not just the palindrome.                           │
└────────────────────────────────────────────────────────────────────┘
```

So here is the key consequence: **the subsequence `"babcbab"`, in that exact left-to-right character order, appears in both `S` and `S' = reverse(S)`.** It appears in `S` because that's where you found it. It appears in `S'` because reversing a palindrome gives back the same string — so those same characters, still in the same relative order among themselves, survive the reversal of the whole string around them.

A sequence of characters that appears, in the same order, in two different strings is — by definition — a **common subsequence** of those two strings. So `"babcbab"` is a common subsequence of `S` and `reverse(S)`.

### From "A Common Subsequence" to "The LONGEST Common Subsequence"

This shows that *any* palindrome hiding inside `S` survives as a common subsequence of `S` and `reverse(S)`. But the problem doesn't ask for just *any* palindrome — it asks for the **longest** one. So there are two directions to check before you can trust this reduction completely:

**Direction 1 — the longest palindrome is never longer than `LCS(S, reverse(S))`.**
This is exactly the argument above: whatever the longest palindromic subsequence `P` actually is, `P` survives reversal unchanged, so `P` is *some* common subsequence of `S` and `reverse(S)`. Since `LCS(S, reverse(S))` is defined as the *longest possible* common subsequence, it must be at least as long as `P`.

**Direction 2 — `LCS(S, reverse(S))` is never longer than the longest palindrome.**
This direction is less immediately obvious, but it is also true, and it's the well-established half of this classic technique: it turns out that any common subsequence you find between `S` and `reverse(S)` can always be rearranged into a palindromic reading — it can never "beat" the true longest palindrome by exploiting the two-string comparison in some sneaky way. This is the standard result that makes this reduction a trusted technique rather than a coincidence that happens to work on easy test cases.

Putting the two directions together, the two quantities aren't just related — they are **forced to be exactly equal**:

```
length of longest palindromic subsequence(S)  ==  LCS(S, reverse(S))
```

That equality is the entire problem. Once you see it, there is nothing left to design — only to build the second string and reuse the LCS machinery you already have.

### Visualizing the Mapping on the Simpler Example

Going back to `s = "bbbab"` (the actual LeetCode example), reverse it:

```
s  = "bbbab"
s' = "babbb"    (s reversed)
```

The palindrome `"bbbb"` sits inside `s` at positions 0, 1, 2, 4 (skipping the `a`). Reversed, `"bbbb"` is still `"bbbb"` — unchanged. So those same four `b` characters, in the same left-to-right order, also appear somewhere inside `s'`. That makes `"bbbb"` a common subsequence of `s` and `s'` — and running LCS on this exact pair of strings will find it.

### What This Means Practically

You do not need to write a single new line of recurrence logic. The entire solution is:

```
1. Build t = reverse(s)
2. Run your existing LC 1143 LCS solver on the pair (s, t)
3. Return the length it computes
```

The state definition (`dp[i][j]` = LCS length of prefixes), the match/no-match recurrence, the base cases, the tabulation direction, the space optimization — every single piece is copied over from LC 1143 completely unchanged. The only genuinely new work in this entire problem is the reduction argument you just walked through.

# Stage 3: Coding

Since the recurrence itself introduces nothing new, we go straight to the space-optimized tabulation you already built for LC 1143 — just parameterized on `s` and its reverse.

## Approach — Tabulation (reusing the LC 1143 template directly)

```java
class Solution {
    public int longestPalindromeSubseq(String s) {
        int n = s.length();

        // Step 1: build the second string — the reverse of s
        // WHY: a palindrome inside s is invariant under reversal, so it
        //      survives as a common subsequence of s and reverse(s).
        //      This is the ENTIRE new idea in this problem — everything
        //      after this line is just LC 1143's LCS solver, unchanged.
        String t = new StringBuilder(s).reverse().toString();

        // Step 2: run the EXACT LC 1143 LCS tabulation on (s, t)
        // dp[i][j] = LCS length of s[0..i-1] and t[0..j-1]  (Model B shift)
        int[][] dp = new int[n + 1][n + 1];

        for (int i = 1; i <= n; i++) {
            for (int j = 1; j <= n; j++) {
                if (s.charAt(i - 1) == t.charAt(j - 1)) {
                    // Match — extend the run from the diagonal, exactly
                    // as in every LCS problem so far
                    dp[i][j] = 1 + dp[i - 1][j - 1];
                } else {
                    // No match — try dropping either side, keep the better one
                    dp[i][j] = Math.max(dp[i - 1][j], dp[i][j - 1]);
                }
            }
        }

        // Step 3: LCS(s, reverse(s)) == length of longest palindromic subsequence
        return dp[n][n];
    }
}
```

Notice the dp table here is `(n+1) × (n+1)`, not `(n+1) × (m+1)` with two different lengths — because `t` is just `s` reversed, both strings always have the exact same length `n`.

### Full Cell-by-Cell DP Table Trace

`s = "bbbab"` (n = 5), `t = reverse(s) = "babbb"`

```
                j=0    j=1(b)  j=2(a)  j=3(b)  j=4(b)  j=5(b)
i=0          [   0   ,   0   ,   0   ,   0   ,   0   ,   0   ]
i=1(b)       [   0   ,   1   ,   1   ,   1   ,   1   ,   1   ]
i=2(b)       [   0   ,   1   ,   1   ,   2   ,   2   ,   2   ]
i=3(b)       [   0   ,   1   ,   1   ,   2   ,   3   ,   3   ]
i=4(a)       [   0   ,   1   ,   2   ,   2   ,   3   ,   3   ]
i=5(b)       [   0   ,   1   ,   2   ,   3   ,   3   ,   4   ]
```

Walking through several cells explicitly, using the standard LCS rule (row `i` reads `s.charAt(i-1)`, column `j` reads `t.charAt(j-1)`):

- `dp[1][1]`: `s[0]='b'`, `t[0]='b'` → match → `1 + dp[0][0] = 1 + 0 = 1`
- `dp[2][3]`: `s[1]='b'`, `t[2]='b'` → match → `1 + dp[1][2] = 1 + 1 = 2`
- `dp[3][4]`: `s[2]='b'`, `t[3]='b'` → match → `1 + dp[2][3] = 1 + 2 = 3`
- `dp[4][2]`: `s[3]='a'`, `t[1]='a'` → match → `1 + dp[3][1] = 1 + 1 = 2`
- `dp[4][4]`: `s[3]='a'`, `t[3]='b'` → no match → `max(dp[3][4]=3, dp[4][3]=2) = 3`
- `dp[5][5]`: `s[4]='b'`, `t[4]='b'` → match → `1 + dp[4][4] = 1 + 3 = 4`

**Final answer = `dp[5][5] = 4`** ✓ — the longest palindromic subsequence of `"bbbab"` has length 4 (the palindrome being `"bbbb"`), which matches the well-known expected result for this exact input.

## Approach — Space Optimization

Exactly the same collapse as LC 1143 — row `i` in the recurrence only ever reads row `i-1` (`dp[i-1][j-1]` for a match, `dp[i-1][j]` for the "drop s1" option), plus the current row's own earlier entry (`dp[i][j-1]` for the "drop t" option). So two 1D arrays of size `n+1` replace the full 2D table, exactly as before.

```java
class Solution {
    public int longestPalindromeSubseq(String s) {
        int n = s.length();
        String t = new StringBuilder(s).reverse().toString();

        // prev[j] = dp value for row i-1 (row 0 = base case, all zeros)
        int[] prev = new int[n + 1];

        for (int i = 1; i <= n; i++) {
            // curr[j] = dp value for row i, being filled now
            int[] curr = new int[n + 1];

            for (int j = 1; j <= n; j++) {
                if (s.charAt(i - 1) == t.charAt(j - 1)) {
                    // WHY prev[j-1]: this is dp[i-1][j-1] — the diagonal
                    // neighbor, same as every LCS match case so far
                    curr[j] = 1 + prev[j - 1];
                } else {
                    // WHY prev[j]: dp[i-1][j] — row above, same column
                    // WHY curr[j-1]: dp[i][j-1] — same row, already
                    //     computed earlier in this same pass
                    curr[j] = Math.max(prev[j], curr[j - 1]);
                }
            }

            // Slide forward: current row becomes next iteration's "previous"
            prev = curr;
        }

        // prev now holds the last computed row (row n)
        return prev[n];
    }
}
```

## Complexity Analysis

**Time Complexity — O(n²):**

Building the reversed string with `StringBuilder.reverse()` costs `O(n)`. The LCS tabulation then runs on two strings that are *both* length `n` (since `t` is just `s` reversed, they share the same length by construction) — so the two nested loops each run `n` times, giving `O(n × n) = O(n²)` for the table-filling itself. The `O(n)` reversal is dominated by the `O(n²)` table fill, so overall time is **O(n²)**.

**Space Complexity — O(n) after optimization:**

The full tabulation table would be `(n+1) × (n+1)` integers — `O(n²)`. After space optimization, only two arrays of size `n+1` are kept — `prev` and `curr` — giving **O(n)**. The reversed string `t` itself is an additional `O(n)`, which doesn't change the asymptotic space.
