# LC 368. Largest Divisible Subset

---

# Stage 1: Identification

**Step 1 — Which topic?**

You are given a set of **distinct** positive integers. Find the **largest subset** such that for every pair `(a, b)` in the subset, either `a % b == 0` or `b % a == 0`.

The moment you see **"find the largest subset satisfying a pairwise constraint"** — that is the signal. To find the largest such subset, you must **try all possible subsets**. And whenever you try all possibilities with overlapping subproblems — that becomes **Dynamic Programming**.

**Step 2 — Which pattern?**

You are looking for the longest subsequence where elements satisfy a **custom pairwise constraint** — divisibility instead of strict `<`. The answer at any element depends on the best answer from previous elements.

That is **Pattern 6: LIS (Longest Increasing Subsequence)** — with divisibility replacing the ordering comparison.

**Step 3 — Which key concept?**

**Sort first, then apply LIS with divisibility — plus reconstruction via hash array.**

The critical insight Striver gives:

> The problem says you can print the subset **in any order**. So sorting the array first does not invalidate any answer. And once the array is sorted, a beautiful property emerges.
>
> **If `nums[j]` divides `nums[i]` and `nums[k]` divides `nums[j]`, then `nums[k]` also divides `nums[i]` — transitivity of divisibility.**
>
> This means: once the array is sorted, you only need to check if `nums[i] % nums[j] == 0` (does the previous element divide the current one). You never need to verify all pairs — the chain property handles it automatically.

So the problem reduces to: sort the array, then find the **Longest Divisible Subsequence** — which is structurally identical to LIS, just with `nums[i] % nums[j] == 0` replacing `nums[j] < nums[i]`.

Since the problem asks to **return the actual subset** (not just the length), we use the **hash array reconstruction** technique from Print LIS — exactly the same backtracking approach.

# Stage 2: Intuition Building

### Why Sorting Unlocks the Problem

Consider `nums = [1, 2, 4, 8, 16, 7]`.

**Without sorting:** To check if `{16, 4, 8}` is a valid subset, you must check all pairs: (16,4), (16,8), (4,8). That is expensive and hard to build into a recurrence.

**After sorting:** `[1, 2, 4, 7, 8, 16]`

Now build a chain left to right. Suppose you have the chain `[1, 4, 8]` — verified one step at a time:
- 4 % 1 == 0 ✓
- 8 % 4 == 0 ✓

Can you extend to 16? Check only: 16 % 8 == 0 ✓

That is the **only check you need**. Why? Because 8 % 4 == 0 and 4 % 1 == 0 are already verified. By transitivity: 16 is divisible by 8, 8 is divisible by 4, therefore 16 is divisible by 4 and by 1. **One check at the boundary is enough to validate the entire chain.**

This is exactly the LIS property: to extend a chain ending at `nums[j]` with `nums[i]`, you only need to check `nums[i] % nums[j] == 0`.

### Reconstruction via Hash Array

```
lastIndex = 4  (where the maximum lives)

Trace back using hash[]:
    index=4, nums[4]=16, hash[4]=3 → add 16, move to 3
    index=3, nums[3]=8,  hash[3]=1 → add 8,  move to 1
    index=1, nums[1]=4,  hash[1]=0 → add 4,  move to 0
    index=0, nums[0]=1,  hash[0]=0 → add 1,  stop (hash[i]==i is the termination)

Collected in reverse: [16, 8, 4, 1]
After reversing: [1, 4, 8, 16] ✓
```

### Why the Hash Array Termination Condition Works

When we initialize `hash[i] = i` for all `i`, it means "no predecessor found yet — I am the start of my own chain." The backtracking loop stops when `hash[lastIndex] == lastIndex` — we've reached the first element of the chain. This is the same technique from Print LIS.

### Overlapping Subproblems — Same as LIS

For `nums[i] = 16`, to compute `dp[4]`, we need `dp[0]`, `dp[1]`, `dp[2]`, `dp[3]` — all of which are reused across multiple `i` values. These are overlapping subproblems. DP with a `dp[]` array memoizes each one in O(1) after the first computation.

# Stage 3: Coding

## Approach — O(n²) DP with Hash Reconstruction

Unlike LIS, there is **no O(n log n) approach** for this problem. The binary search / patience sorting trick works for LIS because `<` is a total order. Divisibility is not — `7` and `4` are incomparable (neither divides the other). So O(n²) is the optimal and only approach here.

```java
class Solution {
    public List<Integer> largestDivisibleSubset(int[] nums) {
        int n = nums.length;

        // Step 1: Sort the array
        // WHY: After sorting, if nums[j] divides nums[i] and nums[k] divides nums[j],
        //      then nums[k] also divides nums[i] — transitivity.
        //      So we only need to check one step back in the chain.
        //      Also, for distinct positive integers, if a divides b and a != b,
        //      then a < b, so sorting puts divisors before their multiples.
        Arrays.sort(nums);

        // dp[i] = length of the longest divisible chain ending at index i
        int[] dp = new int[n];

        // hash[i] = index of the previous element in the longest chain ending at i
        // WHY initialize hash[i] = i: signals "I am the start of my chain"
        //     Used as the termination condition during backtracking
        int[] hash = new int[n];

        // Every element alone is a valid chain of length 1
        Arrays.fill(dp, 1);

        // Initialize hash[i] = i for all i (no predecessor yet)
        for (int i = 0; i < n; i++) hash[i] = i;

        // Track the index where the maximum chain length lives
        int maxLen = 1;
        int lastIndex = 0;

        // Step 2: Fill dp using LIS logic with divisibility condition
        // WHY start i from 1: index 0 is already initialized as base case
        for (int i = 1; i < n; i++) {
            for (int j = 0; j < i; j++) {

                // The one critical change from LIS:
                // Instead of: nums[j] < nums[i]
                // We check:   nums[i] % nums[j] == 0
                // WHY: nums[i] divisible by nums[j] means nums[j] divides nums[i].
                //      Since array is sorted, nums[j] <= nums[i] always, so we
                //      only need to check one direction.
                if (nums[i] % nums[j] == 0 && dp[j] + 1 > dp[i]) {
                    dp[i] = dp[j] + 1;

                    // Record the predecessor: chain ending at i came from j
                    // WHY hash[i] = j: when we backtrack from i, we go to j next
                    hash[i] = j;
                }
            }

            // Track the overall maximum and where it is
            // WHY track lastIndex: reconstruction starts from here
            if (dp[i] > maxLen) {
                maxLen = dp[i];
                lastIndex = i;
            }
        }

        // Step 3: Reconstruct the actual subset by backtracking through hash[]
        List<Integer> result = new ArrayList<>();

        // Start from lastIndex and follow hash[] pointers backward
        // WHY this termination: hash[i] == i means we've reached the chain's
        //     first element (it points to itself — no predecessor)
        while (hash[lastIndex] != lastIndex) {
            result.add(nums[lastIndex]);
            lastIndex = hash[lastIndex];
        }

        // Add the first element of the chain (the one pointing to itself)
        // WHY add separately: the while loop exits before adding it
        result.add(nums[lastIndex]);

        // The result was collected in reverse order (end → start of chain)
        // Reverse to get the chain in sorted order
        // WHY: we traversed from the longest chain's end to its beginning,
        //      so elements were added in reverse
        Collections.reverse(result);

        return result;
    }
}
```

## Complexity Analysis

**Time Complexity — O(n² + n log n):**

Two parts. First, `Arrays.sort(nums)` runs in O(n log n). Second, the two nested loops — outer runs n times, inner runs up to i times for each i. Total iterations = 0+1+2+...+(n-1) = n(n-1)/2 = O(n²). The reconstruction loop runs at most n steps. So overall: O(n log n + n²) = **O(n²)**.

Why no O(n log n) for the DP itself? The binary search trick in LIS works because `<` is a total order — every pair of elements is comparable. Divisibility is **not** a total order. For example, 7 and 4 are incomparable — neither divides the other. So you cannot maintain a sorted `tails[]` array and binary search into it. The O(n²) approach is the best possible here.

**Space Complexity — O(n):**

Three arrays of size n — `dp[]`, `hash[]`, and the result list which holds at most n elements. No recursion stack. Total: **O(n)**.

## How This Differs from LIS

| Property | LIS (LC 300) | Largest Divisible Subset (LC 368) |
|---|---|---|
| Comparison | `nums[j] < nums[i]` | `nums[i] % nums[j] == 0` |
| Sort first? | Not required | **Required** — enables transitivity |
| Return value | Length (integer) | **Actual subset** (list) |
| O(n log n) possible? | Yes — patience sorting | **No** — divisibility is not a total order |
| Reconstruction needed? | Optional | **Always required** |
