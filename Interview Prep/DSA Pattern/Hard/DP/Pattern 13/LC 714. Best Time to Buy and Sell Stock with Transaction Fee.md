# LC 714. Best Time to Buy and Sell Stock with Transaction Fee

---

# Stage 1: Identification

**Step 1 — Which topic?**

Same array of stock prices as every problem in this pattern, plus one extra input: a constant `fee`. Transactions are still **unlimited**, exactly like LC 122 — buy and sell as many times as you want, as long as you don't hold more than one stock at a time. The only new rule: **every completed transaction costs a fixed fee**, paid to the broker.

The moment you see **"unlimited transactions, but each one costs something"** — this should feel much closer to LC 122 than to LC 309. There's no forced waiting period here, no new "in-between" situation you can be stuck in. You're either holding a stock or you're not — the exact same two-state world as LC 122. The only thing that changes is *how much money changes hands* at one specific step.

**Step 2 — Which pattern?**

Still **Pattern 13: State Machine DP** — and this is the simplest possible extension of LC 122's machine. No new state is needed at all; only the arithmetic on one existing transition changes.

**Step 3 — Which key concept?**

**Reuse LC 122's exact `canBuy` two-state machine — subtract the fee at the moment of selling, since that's the moment a transaction is completed.**

```
Step 1: Represent in terms of (index, canBuy)   — identical to LC 122
Step 2: Explore all possibilities at (index, canBuy)   — identical to LC 122
Step 3: Question says maximize profit → take max of both choices   — identical to LC 122
```

The only line that changes anywhere in the whole recurrence is the **sell** transition. Everywhere else — the buy transition, the "do nothing" transitions, the base case — is copied over completely unchanged.

# Stage 2: Intuition Building

### Why This Reduces to "LC 122 Minus a Constant"

Think about *when* a fee is actually charged. The problem states you pay a fee "for each transaction" — and a transaction, by definition, only finishes at the moment you sell (a lone, unfinished buy isn't a transaction yet). So the fee belongs exactly where the transaction gets completed: **at the sell step, and nowhere else.**

Compare the two recurrences side by side:

```
LC 122 (no fee):
    sell = +prices[index] + f(index+1, 1)

LC 714 (with fee):
    sell = +prices[index] - fee + f(index+1, 1)
```

That's it. One subtraction, in one place. Every other line of LC 122's machine — the `buy` transition, both "do nothing" transitions, the base case, even the direction of tabulation — is copy-pasted without any change at all.

### Why the Fee Doesn't Need Its Own State

It's worth being explicit about why this problem *doesn't* need a third state the way LC 309 did. In LC 309, "just sold" was a genuinely different **situation** — it changed which moves were legal tomorrow (you couldn't buy). Here, paying a fee changes **how much money you have**, but it doesn't change what you're **allowed to do** next. You're still either holding a stock or not — the legal moves at every day are exactly the same shape as LC 122. Whenever a new problem constraint changes *the payoff* of an existing transition rather than *which transitions are legal*, you don't need a new state — you only need to adjust the arithmetic on that one transition.

### Walking Through It

```
prices = [1, 3, 2, 8, 4, 9]
fee    =  2
```

```
Buy day 0 (price 1), sell day 3 (price 8): raw profit = 7, minus fee = 5
Buy day 4 (price 4), sell day 5 (price 9): raw profit = 5, minus fee = 3

Total = 5 + 3 = 8
```

Compare this to what LC 122 (no fee) would have found on this same array: it would greedily take every positive zig-zag, including small ones — but here, a fee of 2 makes some of those small zig-zags **not worth taking at all**, since the fee could eat the entire profit or turn it negative. This is exactly why the recursion still needs to explore both "sell now" and "keep holding" at every day — a trade that was worth taking without a fee might no longer be worth taking with one, and you can't know that in advance without comparing.

### Step 1 — Represent in Terms of (index, canBuy)

Define, identically to LC 122:

```
f(index, canBuy) = maximum profit achievable from day 'index' onward,
                    given that 'canBuy' tells you whether you are
                    currently free to buy (1) or must sell first (0)
```

The answer we want is `f(0, 1)`.

### Step 2 — Explore All Possibilities at (index, canBuy)

**Case 1 — `canBuy == 1` (not holding anything) — unchanged from LC 122:**

```
buy    = -prices[index] + f(index + 1, 0)
notBuy = 0 + f(index + 1, 1)
```

**Case 2 — `canBuy == 0` (currently holding a stock) — the ONE changed line:**

```
sell    = prices[index] - fee + f(index + 1, 1)
                        ↑
                 the only new piece in this entire problem
notSell = 0 + f(index + 1, 0)
```

### Step 3 — Take Maximum

```
f(index, canBuy) = max(buy, notBuy)     when canBuy == 1
f(index, canBuy) = max(sell, notSell)   when canBuy == 0
```

### Base Case

```
if index == n → return 0
```

Identical reasoning to every earlier stock problem — no days left, no more profit possible, regardless of state.

### Are There Overlapping Subproblems?

Same as LC 122 — the same `(index, canBuy)` pair is reached through many different sequences of past decisions. **Overlapping subproblems confirmed** → DP applies.

### DP Table Size

```
index:  0 to n   → n+1 values
canBuy: 0 or 1   → 2 values
```

dp table: **(n+1) × 2** — exactly LC 122's shape, unchanged.

# Stage 3: Coding

## Approach 1 — Pure Recursion (Brute Force)

```java
class Solution {
    private int func(int idx, int canBuy, int[] prices, int fee) {
        // Base case: no more days left — no more profit possible
        if (idx == prices.length) return 0;

        if (canBuy == 1) {
            // Buy today: pay the price, flip state to "cannot buy"
            int buy = -prices[idx] + func(idx + 1, 0, prices, fee);
            int notBuy = 0 + func(idx + 1, 1, prices, fee);

            return Math.max(buy, notBuy);
        } else {
            // Sell today: receive the price MINUS the fee — this is the
            // ONLY new piece of logic in the entire problem. The fee is
            // charged exactly here because this is the moment a
            // transaction (buy + sell together) is actually completed.
            int sell = prices[idx] - fee + func(idx + 1, 1, prices, fee);
            int notSell = 0 + func(idx + 1, 0, prices, fee);

            return Math.max(sell, notSell);
        }
    }

    public int maxProfit(int[] prices, int fee) {
        // Start at day 0, free to buy
        return func(0, 1, prices, fee);
    }
}
```

**Time Complexity — O(2^n):**
At every day, the function makes 2 recursive calls — the "act" branch (buy or sell) and the "skip" branch. The recursion tree is a binary tree of depth n. Total nodes grow as 2^n.

**Space Complexity — O(n):**
No dp array. The recursion call stack holds one frame per day, going up to n frames deep.

## Approach 2 — Memoization (Top-Down DP)

```java
class Solution {
    private int func(int idx, int canBuy, int[] prices, int fee, int[][] dp) {
        // Base case
        if (idx == prices.length) return 0;

        // Step 1: Already computed? Return stored value instantly
        // WHY: f(idx, canBuy) never changes no matter which sequence of
        //      earlier decisions led to this exact state
        if (dp[idx][canBuy] != -1) return dp[idx][canBuy];

        int result;

        if (canBuy == 1) {
            int buy = -prices[idx] + func(idx + 1, 0, prices, fee, dp);
            int notBuy = 0 + func(idx + 1, 1, prices, fee, dp);
            result = Math.max(buy, notBuy);
        } else {
            int sell = prices[idx] - fee + func(idx + 1, 1, prices, fee, dp);
            int notSell = 0 + func(idx + 1, 0, prices, fee, dp);
            result = Math.max(sell, notSell);
        }

        // Step 2: Store before returning
        dp[idx][canBuy] = result;
        return result;
    }

    public int maxProfit(int[] prices, int fee) {
        int n = prices.length;

        // dp[idx][canBuy] = -1 means not yet computed
        int[][] dp = new int[n][2];
        for (int[] row : dp) {
            Arrays.fill(row, -1);
        }

        return func(0, 1, prices, fee, dp);
    }
}
```

**Time Complexity — O(n × 2):**
Each unique `(idx, canBuy)` pair computed exactly once. Total: **O(n)**.

**Space Complexity — O(n × 2) + O(n):**
The dp array, plus the recursion call stack going n levels deep. Total: **O(n)**.

## Approach 3 — Tabulation (Bottom-Up DP)

**Direction:** Recursion goes from day 0 forward toward day n. Tabulation goes the opposite direction — from day n backward toward day 0. Base case: all zeros at `idx == n`, already true by Java's default initialization.

```java
class Solution {
    public int maxProfit(int[] prices, int fee) {
        int n = prices.length;

        // dp[idx][canBuy] — dp[n][*] = 0 by default, no explicit fill needed
        int[][] dp = new int[n + 1][2];

        // Fill from idx = n-1 down to 0 — opposite of recursion's direction
        for (int idx = n - 1; idx >= 0; idx--) {

            // canBuy = 1
            int buy = -prices[idx] + dp[idx + 1][0];
            int notBuy = 0 + dp[idx + 1][1];
            dp[idx][1] = Math.max(buy, notBuy);

            // canBuy = 0 — the fee is subtracted right here, and ONLY here
            int sell = prices[idx] - fee + dp[idx + 1][1];
            int notSell = 0 + dp[idx + 1][0];
            dp[idx][0] = Math.max(sell, notSell);
        }

        // Answer: day 0, free to buy
        return dp[0][1];
    }
}
```

### Full Cell-by-Cell DP Table Trace

`prices = [1, 3, 2, 8, 4, 9]` (n = 6), `fee = 2`

```
Base case — idx = 6 (from Java's zero-init):
[canBuy=0]=0   [canBuy=1]=0
```

**idx = 5 (price 9):**
```
canBuy=1: buy = -9+dp[6][0]=-9,        notBuy = dp[6][1]=0 → max=0
canBuy=0: sell = 9-2+dp[6][1]=7,       notSell = dp[6][0]=0 → max=7

dp[5] = [0, 7]     (index order: [canBuy=1, canBuy=0] shown for readability below as {1:_, 0:_})
```
To keep this unambiguous, from here on each row is written explicitly as `{canBuy=1: _, canBuy=0: _}`.

```
dp[5] = {canBuy=1: 0, canBuy=0: 7}
```

**idx = 4 (price 4):**
```
canBuy=1: buy = -4+dp[5][0]=-4+7=3,     notBuy = dp[5][1]=0 → max=3
canBuy=0: sell = 4-2+dp[5][1]=2,        notSell = dp[5][0]=7 → max=7

dp[4] = {canBuy=1: 3, canBuy=0: 7}
```

**idx = 3 (price 8):**
```
canBuy=1: buy = -8+dp[4][0]=-8+7=-1,    notBuy = dp[4][1]=3 → max=3
canBuy=0: sell = 8-2+dp[4][1]=9,        notSell = dp[4][0]=7 → max=9

dp[3] = {canBuy=1: 3, canBuy=0: 9}
```

**idx = 2 (price 2):**
```
canBuy=1: buy = -2+dp[3][0]=-2+9=7,     notBuy = dp[3][1]=3 → max=7
canBuy=0: sell = 2-2+dp[3][1]=3,        notSell = dp[3][0]=9 → max=9

dp[2] = {canBuy=1: 7, canBuy=0: 9}
```

**idx = 1 (price 3):**
```
canBuy=1: buy = -3+dp[2][0]=-3+9=6,     notBuy = dp[2][1]=7 → max=7
canBuy=0: sell = 3-2+dp[2][1]=8,        notSell = dp[2][0]=9 → max=9

dp[1] = {canBuy=1: 7, canBuy=0: 9}
```

**idx = 0 (price 1):**
```
canBuy=1: buy = -1+dp[1][0]=-1+9=8,     notBuy = dp[1][1]=7 → max=8
canBuy=0: sell = 1-2+dp[1][1]=6,        notSell = dp[1][0]=9 → max=9

dp[0] = {canBuy=1: 8, canBuy=0: 9}
```

**Answer = `dp[0][1] = 8`** ✓ — matches the expected result exactly: buy day 0 (price 1), sell day 3 (price 8) for profit `8-1-2=5`, then buy day 4 (price 4), sell day 5 (price 9) for profit `9-4-2=3`, giving `5+3=8`.

**Time Complexity — O(n × 2):**
A single loop over n days, constant work per day. Total: **O(n)**.

**Space Complexity — O(n × 2):**
Only the dp array of size `(n+1) × 2`. No recursion stack.

## Approach 4 — Space Optimization (The Final Form)

`dp[idx][...]` depends only on `dp[idx + 1][...]`. Collapse to two arrays of size 2.

```java
class Solution {
    public int maxProfit(int[] prices, int fee) {
        int n = prices.length;

        // after[canBuy] = best profit from day idx+1 onward, given this state
        int[] after = new int[2];

        for (int idx = n - 1; idx >= 0; idx--) {
            int[] curr = new int[2];

            // canBuy = 1
            int buy = -prices[idx] + after[0];
            int notBuy = 0 + after[1];
            curr[1] = Math.max(buy, notBuy);

            // canBuy = 0 — fee subtracted here, exactly as in tabulation
            int sell = prices[idx] - fee + after[1];
            int notSell = 0 + after[0];
            curr[0] = Math.max(sell, notSell);

            // Slide forward: current day becomes next iteration's "after"
            after = curr;
        }

        // after now holds the last computed day (idx = 0)
        return after[1];
    }
}
```

**Time Complexity — O(n × 2):**
Same single loop, same iteration count as tabulation. Total: **O(n)**.

**Space Complexity — O(1) (technically O(2)):**
No `(n+1) × 2` array. No recursion stack. Just two arrays of size 2 — `after` and `curr` — regardless of how large n is.

## Final Comparison

| Approach | Time | Space | Notes |
|---|---|---|---|
| Pure Recursion | O(2^n) | O(n) stack | Exponential — never use |
| Memoization | O(n) | O(n) + O(n) stack | Good interview starting point |
| Tabulation | O(n) | O(n) | Better — eliminates stack |
| Space Optimization | O(n) | **O(1)** | Best — submit this |

## How This Differs From LC 122 and LC 309

| Property | LC 122 (unlimited, no fee) | LC 714 (unlimited, with fee) | LC 309 (unlimited, cooldown) |
|---|---|---|---|
| Number of states | 2 — `canBuy` | **2 — `canBuy` (unchanged)** | 3 — `rest`, `held`, `sold` |
| What changes vs. LC 122? | — | **Fee subtracted at the sell transition only** | An entirely new state added |
| Does a new SITUATION arise? | — | **No — you're still just "holding" or "not holding"** | **Yes — "just sold, can't buy yet" is a genuinely new situation** |
| Where does the new rule live? | — | **One arithmetic change, on one existing transition** | **A whole new state with its own (forced) transition** |
| DP table shape | `(n+1) × 2` | **`(n+1) × 2` (unchanged)** | `(n+1) × 3` |

## The Key Takeaway

```
┌────────────────────────────────────────────────────────────────────┐
│  LC 714 is the "quiet" extension of Pattern 13 — it looks like it  │
│  should need something new, but it doesn't, because the fee        │
│  changes a PAYOFF, not a RULE about which moves are legal.         │
│                                                                    │
│  The test to apply whenever a new constraint is bolted onto a      │
│  state machine DP:                                                 │
│                                                                    │
│      "Does this constraint create a NEW SITUATION where the        │
│       legal next moves differ from every existing state?"          │
│                                                                    │
│      If YES  → you need a new state (this was LC 309's cooldown:   │
│                'just sold' genuinely forbids buying tomorrow,      │
│                a rule no existing state could express)             │
│                                                                    │
│      If NO   → you only need to adjust the ARITHMETIC on one       │
│                existing transition (this is LC 714: you're still   │
│                only ever 'holding' or 'not holding' — the fee      │
│                just makes selling slightly less profitable)        │
│                                                                    │
│  The entire new logic in this problem is one subtraction, in one   │
│  place — the sell transition — because a fee is only ever charged  │
│  once a transaction (a matched buy + sell) is actually completed:  │
│                                                                    │
│      sell = prices[idx] - fee + f(idx+1, canBuy=1)                 │
│                                                                    │
│  Every other line — buy, both "do nothing" branches, the base      │
│  case, the direction of tabulation, the space optimization —       │
│  is copied from LC 122 completely unchanged.                       │
└────────────────────────────────────────────────────────────────────┘
```
