# LC 309. Best Time to Buy and Sell Stock with Cooldown

---

# Stage 1: Identification

**Step 1 — Which topic?**

Same array of stock prices as every problem in this pattern. One new constraint sits on top of LC 122's "unlimited transactions" rule: **after you sell a stock, you cannot buy again on the very next day** — you must sit out at least one day (a "cooldown") before you're allowed to buy anything else.

The moment you see **"unlimited transactions, but with a forced waiting period after selling"** — this should immediately tell you that LC 122's simple two-state machine (`canBuy` / `cannot buy`) is no longer enough. Those two states could only ever answer "am I holding a stock or not?" — they had no way of representing *"I just sold yesterday, so even though I'm not holding anything, I'm still not allowed to act today."* That third situation needs its own name and its own slot in the state.

**Step 2 — Which pattern?**

Still **Pattern 13: State Machine DP** — and this is the problem where the "state machine" idea in the pattern's name becomes the most literal. Instead of two states, we now need **three**, and the picture to draw before writing any code is genuinely a small diagram of circles and arrows — exactly the general advice for this whole pattern: *draw the state diagram first, the DP writes itself afterward.*

**Step 3 — Which key concept?**

**Three states: `held`, `sold`, `rest` — with cooldown modeled as its own dedicated state, not as a special jump in the index.**

```
held  →  you are CURRENTLY holding a stock (bought earlier, not yet sold)
sold  →  you just sold TODAY — this is the moment right after a sale
rest  →  you are holding nothing, and you are FREE to buy today
```

The one thing that makes this problem different from a "two-state" world is that **selling doesn't take you straight back to "free to buy."** It takes you to an intermediate state — `sold` — and from `sold` you are forced to spend exactly one day doing nothing before you land back in `rest`. That one forced day of nothing is the cooldown, made completely explicit as a state of its own.

# Stage 2: Intuition Building

### Why Two States Stop Being Enough

In LC 122, being "not holding a stock" was a single, simple situation — you were always free to buy on any day you weren't holding something. The moment cooldown exists, "not holding a stock" splits into **two genuinely different situations**:

```
Situation A: You sold a while ago (or never bought at all) — you are free to buy right now.
Situation B: You sold YESTERDAY — you are not holding anything, but you are NOT allowed to buy today.
```

A single `canBuy` flag cannot tell these two apart — both look identical from the "am I holding a stock" point of view, but they lead to completely different legal moves today. This is exactly why a third state is needed: to remember *which kind* of "not holding" you're in.

### Naming the Three States, and Drawing the Machine

Think of each day as forcing you into exactly one of three circles:

```
        buy
   ┌─────────────┐
   │             ▼
┌──────┐      ┌──────┐
│ rest │      │ held │
└──────┘      └──────┘
   ▲             │
   │             │ sell
   │             ▼
   │          ┌──────┐
   └──────────│ sold │
   (forced,   └──────┘
   one day
   later)
```

Read the arrows as the only legal transitions:

```
rest  → (buy)         → held
held  → (do nothing)  → held
held  → (sell)        → sold
sold  → (forced wait) → rest      ← this arrow is NEVER a choice — it always happens
rest  → (do nothing)  → rest
```

Notice something important: from `sold`, there is **only one possible arrow out**, and it isn't a decision you make — it's automatic. The day right after a sale, you have no choice at all; you are simply forced into a day of nothing, and the day *after that*, you land in `rest`, free again. That automatic, no-choice arrow is the entire cooldown rule, drawn as a single edge in the diagram instead of being handled as an arithmetic trick on the index.

### Building the Recursion From the Diagram

Once the diagram is drawn, translating it into a recursive function is mechanical — you simply ask, at each state, *"which arrows can I follow from here, and which one is best?"*

Define:

```
f(i, state) = maximum profit achievable from day i onward,
              given that you are ENTERING day i in the given state
```

**If `state == rest` (free to buy):**

```
Follow the "buy" arrow:      -prices[i] + f(i+1, held)
Follow the "do nothing" arrow: 0 + f(i+1, rest)
f(i, rest) = max of these two
```

**If `state == held` (currently holding):**

```
Follow the "sell" arrow:      +prices[i] + f(i+1, sold)
Follow the "do nothing" arrow: 0 + f(i+1, held)
f(i, held) = max of these two
```

**If `state == sold` (just sold, forced to wait):**

```
There is only ONE arrow out of this state — it isn't a choice.
f(i, sold) = 0 + f(i+1, rest)
```

This last line is the entire cooldown rule. There is no `max(...)` here at all, because there is nothing to choose between — being in `sold` on day `i` means day `i` is *automatically* a forced rest day, and day `i+1` is *automatically* back to `rest`.

### Base Case

```
if i == n → return 0
```

No matter which of the three states you're in, once the days run out, no further profit is possible — exactly the same reasoning as every earlier stock problem.

### The Starting Call

At day 0, you haven't bought or sold anything yet — you are free to act. So the answer we want is:

```
f(0, rest)
```

### Visualizing the Full Path on an Example

```
prices = [1, 2, 3, 0, 2]
days   =  0  1  2  3  4
```

Follow one specific good sequence of decisions through the diagram:

```
day 0 (rest, price 1):    buy   → held         (paid 1)
day 1 (held, price 2):    sell  → sold          (received 2, profit so far: +1)
day 2 (sold, price 3):    forced wait → rest    (no choice, day 2 is the cooldown)
day 3 (rest, price 0):    buy   → held          (paid 0)
day 4 (held, price 2):    sell  → sold          (received 2, profit so far: +1 + 2 = 3)

Total profit = 3
```

This matches the well-known expected answer for this exact array. Notice how day 2 was *never* a decision — the moment you sold on day 1, day 2 was locked into being a forced rest day purely by which state you were in, with no branching at all in that step.

### Why This Naturally Explains Striver's "Jump to `idx+2`" Trick

If you've seen the alternative version of this problem where selling jumps straight to `idx + 2` instead of `idx + 1`, you now have the tool to see *why* that shortcut is valid: **skipping straight to `idx+2` on a sell is exactly the same as passing through the `sold` state for one single day and then landing in `rest`, collapsed into a single step.** The three-state version simply refuses to hide that middle day — it names it, gives it its own row in the table, and lets the "no-choice" transition speak for itself. Both are correct; the three-state version is more explicit and, once internalized, generalizes far more easily to variations of this problem (e.g., a cooldown of *k* days instead of 1) than an arithmetic `+2` jump would.

### Are There Overlapping Subproblems?

The same `(i, state)` pair is reachable through many different sequences of earlier buy/sell/wait decisions. **Overlapping subproblems confirmed** → DP applies.

### DP Table Size

Two parameters:

```
i:     0 to n     → n+1 values
state: rest, held, sold → 3 values
```

dp table: **(n+1) × 3**

# Stage 3: Coding

We'll represent the three states as integers for the array index: `0 = rest`, `1 = held`, `2 = sold`.

## Approach 1 — Pure Recursion (Brute Force)

```java
class Solution {
    // state: 0 = rest (free to buy), 1 = held (holding stock), 2 = sold (forced cooldown today)
    private int func(int i, int state, int[] prices, int n) {
        // Base case: no more days left — no more profit possible, regardless of state
        if (i == n) return 0;

        if (state == 0) {
            // REST: two real choices — buy today, or keep resting
            int buy = -prices[i] + func(i + 1, 1, prices, n);   // buy → move to HELD
            int doNothing = 0 + func(i + 1, 0, prices, n);       // stay in REST

            return Math.max(buy, doNothing);

        } else if (state == 1) {
            // HELD: two real choices — sell today, or keep holding
            int sell = prices[i] + func(i + 1, 2, prices, n);    // sell → move to SOLD
            int doNothing = 0 + func(i + 1, 1, prices, n);        // stay in HELD

            return Math.max(sell, doNothing);

        } else {
            // SOLD: NO choice here — this day is automatically the cooldown day.
            // WHY no max(): there is exactly one legal arrow out of this state
            return 0 + func(i + 1, 0, prices, n);   // forced → move to REST
        }
    }

    public int maxProfit(int[] prices) {
        int n = prices.length;

        // Start at day 0, in REST — free to buy, nothing bought or sold yet
        return func(0, 0, prices, n);
    }
}
```

**Time Complexity — O(2^n):**
From `rest` and `held`, the function branches into 2 recursive calls each. The `sold` state only ever makes 1 call, but that doesn't change the worst-case exponential shape driven by the other two states. The recursion tree has depth n.

**Space Complexity — O(n):**
No dp array. The recursion call stack holds one frame per day, going up to n frames deep.

## Approach 2 — Memoization (Top-Down DP)

The same `(i, state)` pair gets reached from many different earlier decision paths. Store each result the first time it's computed.

```java
class Solution {
    private int func(int i, int state, int[] prices, int n, int[][] dp) {
        // Base case
        if (i == n) return 0;

        // Step 1: Already computed? Return stored value instantly
        // WHY: f(i, state) never changes no matter which sequence of
        //      earlier decisions led to this exact (day, state) pair
        if (dp[i][state] != -1) return dp[i][state];

        int result;

        if (state == 0) {
            int buy = -prices[i] + func(i + 1, 1, prices, n, dp);
            int doNothing = 0 + func(i + 1, 0, prices, n, dp);
            result = Math.max(buy, doNothing);

        } else if (state == 1) {
            int sell = prices[i] + func(i + 1, 2, prices, n, dp);
            int doNothing = 0 + func(i + 1, 1, prices, n, dp);
            result = Math.max(sell, doNothing);

        } else {
            result = 0 + func(i + 1, 0, prices, n, dp);
        }

        // Step 2: Store before returning
        dp[i][state] = result;
        return result;
    }

    public int maxProfit(int[] prices) {
        int n = prices.length;

        // dp[i][state] = -1 means not yet computed
        // WHY 3 for the second dimension: exactly 3 states — rest, held, sold
        int[][] dp = new int[n][3];
        for (int[] row : dp) {
            Arrays.fill(row, -1);
        }

        return func(0, 0, prices, n, dp);
    }
}
```

**Time Complexity — O(n × 3):**
Each unique `(i, state)` pair computed exactly once. There are `n × 3` unique states. Total: **O(n)**.

**Space Complexity — O(n × 3) + O(n):**
The dp array, plus the recursion call stack going n levels deep. Total: **O(n)**.

## Approach 3 — Tabulation (Bottom-Up DP)

**Direction:** Recursion goes from day 0 **forward** toward day n. Tabulation goes the **opposite direction** — from day n **backward** toward day 0.

**Base case:** every state at `i == n` is `0` — already true by Java's default array initialization, no explicit fill needed.

```java
class Solution {
    public int maxProfit(int[] prices) {
        int n = prices.length;

        // dp[i][state] — state 0=rest, 1=held, 2=sold
        // dp[n][*] = 0 for all states, already correct via Java's zero-init
        int[][] dp = new int[n + 1][3];

        // Fill from i = n-1 down to 0 — opposite of recursion's direction
        for (int i = n - 1; i >= 0; i--) {

            // state = rest
            int buy = -prices[i] + dp[i + 1][1];
            int doNothingRest = 0 + dp[i + 1][0];
            dp[i][0] = Math.max(buy, doNothingRest);

            // state = held
            int sell = prices[i] + dp[i + 1][2];
            int doNothingHeld = 0 + dp[i + 1][1];
            dp[i][1] = Math.max(sell, doNothingHeld);

            // state = sold — no max needed, exactly one legal transition
            dp[i][2] = 0 + dp[i + 1][0];
        }

        // Answer: day 0, starting in REST
        return dp[0][0];
    }
}
```

### Full Cell-by-Cell DP Table Trace

`prices = [1, 2, 3, 0, 2]` (n = 5)

```
Base case — i = 5 (all states, from Java's zero-init):
[rest=0, held=0, sold=0]
```

**i = 4 (price 2):**
```
rest: buy = -2+dp[5][held]=-2,  doNothing = dp[5][rest]=0 → max=0
held: sell = 2+dp[5][sold]=2,   doNothing = dp[5][held]=0 → max=2
sold: forced = dp[5][rest]=0    → 0

dp[4] = [rest=0, held=2, sold=0]
```

**i = 3 (price 0):**
```
rest: buy = -0+dp[4][held]=2,   doNothing = dp[4][rest]=0 → max=2
held: sell = 0+dp[4][sold]=0,   doNothing = dp[4][held]=2 → max=2
sold: forced = dp[4][rest]=0    → 0

dp[3] = [rest=2, held=2, sold=0]
```

**i = 2 (price 3):**
```
rest: buy = -3+dp[3][held]=-1,  doNothing = dp[3][rest]=2 → max=2
held: sell = 3+dp[3][sold]=3,   doNothing = dp[3][held]=2 → max=3
sold: forced = dp[3][rest]=2    → 2

dp[2] = [rest=2, held=3, sold=2]
```

**i = 1 (price 2):**
```
rest: buy = -2+dp[2][held]=1,   doNothing = dp[2][rest]=2 → max=2
held: sell = 2+dp[2][sold]=4,   doNothing = dp[2][held]=3 → max=4
sold: forced = dp[2][rest]=2    → 2

dp[1] = [rest=2, held=4, sold=2]
```

**i = 0 (price 1):**
```
rest: buy = -1+dp[1][held]=3,   doNothing = dp[1][rest]=2 → max=3
held: sell = 1+dp[1][sold]=3,   doNothing = dp[1][held]=4 → max=4
sold: forced = dp[1][rest]=2    → 2

dp[0] = [rest=3, held=4, sold=2]
```

**Answer = `dp[0][rest] = 3`** ✓ — matches the expected result exactly (buy day 0, sell day 1, cooldown day 2, buy day 3, sell day 4 → profit `1 + 2 = 3`).

**Time Complexity — O(n × 3):**
A single loop over n days, each doing a fixed, constant amount of work across the three states. Total: **O(n)**.

**Space Complexity — O(n × 3):**
Only the dp array of size `(n+1) × 3`. No recursion stack.

## Approach 4 — Space Optimization (The Final Form)

Look at the tabulation recurrence:

```
dp[i][...] depends only on dp[i + 1][...]
```

Day `i` only ever needs day `i + 1`. So instead of the full `(n+1) × 3` array, keep just **two arrays of size 3** — `after` (day `i+1`, already computed) and `curr` (day `i`, being computed).

```java
class Solution {
    public int maxProfit(int[] prices) {
        int n = prices.length;

        // after[state] = best profit from day i+1 onward, given this state
        // Base case: day n, all states give 0 — already true by default
        int[] after = new int[3];

        for (int i = n - 1; i >= 0; i--) {
            int[] curr = new int[3];

            // state = rest
            int buy = -prices[i] + after[1];
            int doNothingRest = 0 + after[0];
            curr[0] = Math.max(buy, doNothingRest);

            // state = held
            int sell = prices[i] + after[2];
            int doNothingHeld = 0 + after[1];
            curr[1] = Math.max(sell, doNothingHeld);

            // state = sold — forced transition, no max needed
            curr[2] = 0 + after[0];

            // Slide forward: current day becomes next iteration's "after"
            after = curr;
        }

        // after now holds the last computed day (i = 0)
        return after[0];
    }
}
```

**Time Complexity — O(n × 3):**
Same single loop, same iteration count as tabulation. No change — **O(n)**.

**Space Complexity — O(1) (technically O(3)):**
No `(n+1) × 3` array. No recursion stack. Just two arrays of size 3 — `after` and `curr` — regardless of how large n is.

## Final Comparison

| Approach | Time | Space | Notes |
|---|---|---|---|
| Pure Recursion | O(2^n) | O(n) stack | Exponential — never use |
| Memoization | O(n) | O(n) + O(n) stack | Good interview starting point |
| Tabulation | O(n) | O(n) | Better — eliminates stack |
| Space Optimization | O(n) | **O(1)** | Best — submit this |

## How This Differs From LC 122

| Property | LC 122 (unlimited, no cooldown) | LC 309 (unlimited, with cooldown) |
|---|---|---|
| Number of states | 2 — `canBuy`, `cannot buy` | **3 — `rest`, `held`, `sold`** |
| What happens right after a sell? | Immediately free to buy again | **Forced into `sold`, then one automatic wait day, then free** |
| Is every state a real decision? | Yes — always 2 real choices | **No — `sold` has exactly ONE forced transition, no choice at all** |
| DP table shape | `(n+1) × 2` | **`(n+1) × 3`** |

## The Key Takeaway

```
┌─────────────────────────────────────────────────────────────────────┐
│  LC 309 introduces a genuinely new idea in Pattern 13: not every    │
│  state in a state machine needs to offer a real choice.             │
│                                                                     │
│  Three states, three circles in the diagram:                        │
│      rest  → free to buy      (2 real choices: buy or wait)         │
│      held  → holding a stock  (2 real choices: sell or wait)        │
│      sold  → just sold today  (exactly 1 forced transition — no     │
│                                 max() needed at all here)           │
│                                                                     │
│  The cooldown rule is not bolted on as an index-arithmetic trick    │
│  — it is simply THE ONLY ARROW leaving the `sold` state. Selling    │
│  moves you to `sold`; from `sold`, the very next day is always,     │
│  unconditionally, a forced rest day that lands you back in `rest`.  │
│                                                                     │
│  Practical rule for recognizing when you need MORE than two         │
│  states in a state machine DP: ask "can two different histories     │
│  lead to the exact same superficial situation, but with different   │
│  legal next moves?" Here, 'not holding a stock' meant two           │
│  different things (free vs. cooling down) — that's the signal       │
│  to split one state into two, or in general, to add a new state     │
│  for every distinct 'legal moves change based on this' situation.   │
│                                                                     │
│  This is also why the popular "sell jumps to idx+2" shortcut        │
│  works: it is exactly this three-state machine with the middle      │
│  `sold`-state day collapsed into a single index jump. Both are      │
│  correct — the three-state version simply keeps every day visible,  │
│  which makes it easier to extend (e.g., to a cooldown of k days).   │
└─────────────────────────────────────────────────────────────────────┘
```
