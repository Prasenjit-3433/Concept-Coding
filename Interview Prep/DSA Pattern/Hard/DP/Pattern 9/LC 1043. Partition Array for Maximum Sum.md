# Stage 1: Identification

**Step 1 — Which topic?**

You're given an integer array and an integer `k`. You need to partition the array into contiguous pieces, where **no piece can have length greater than `k`**. Once partitioned, **every element inside a piece gets replaced by the maximum value in that piece**. You want to choose the partition boundaries such that the **sum of the resulting array is maximized**.

```
arr = [1, 15, 7, 9, 2, 5, 10]
k = 3
```

If you partition as `[1,15] | [7,9,2] | [5,10]`:
- `[1,15]` → both become `15` → contributes `30`
- `[7,9,2]` → all become `9` → contributes `27`
- `[5,10]` → both become `10` → contributes `20`
- Total = `30 + 27 + 20 = 77`

If you partition differently as `[1,15,7] | [9] | [2,5,10]`:
- `[1,15,7]` → all become `15` → contributes `45`
- `[9]` → stays `9` → contributes `9`
- `[2,5,10]` → all become `10` → contributes `30`
- Total = `45 + 9 + 30 = 84`

Same array, two different partitions, two completely different sums. The moment you see **"different ways of partitioning give different totals, find the maximum"** — that is the signal. To find the best partition, you must **try every valid partition** and pick the one with the highest sum. And whenever you try every possibility, **Recursion** is your first thought. And when that recursion has overlapping subproblems — it becomes **Dynamic Programming**.

**Step 2 — Which pattern?**

This is **Pattern 9: Interval / Partition DP** — and specifically, it's the exact same **Front Partition** shape as Palindrome Partitioning II, just solved on an array instead of a string, with a maximum-sum objective instead of a minimum-cuts objective, and with an added hard cap on piece length.

**Step 3 — Which key concept?**

**Front Partition, reused directly — fix the start, try every valid piece length up to `k`, take the max.**

```
Step 1: Express everything in terms of a single index — the position
        where the current unsolved suffix of the array begins
Step 2: Explore all possibilities — try every partition length from
        1 up to k (the piece cannot exceed k elements)
Step 3: Question says maximum → take the max across every valid choice
```

The structural skeleton is identical to Palindrome Partitioning II's front partition template. What changes:

- Instead of checking "is this piece a palindrome?" you compute "what's the maximum sum this piece can contribute?" — which is `(length of the piece) × (maximum element in the piece)`.
- Instead of an unbounded loop that scans until the end of the string, the loop is capped at exactly `k` steps — you are never allowed a longer piece, so there's no need (and no permission) to look further.
- Instead of minimizing cuts, you maximize sum — so `min()` becomes `max()`, mirroring the exact substitution Striver flagged back in Grid DP problems (`dp[i][j]` swaps between `min` and `max` while everything else about the recurrence structure stays the same).

# Stage 2: Intuition Building

### The Problem Setup

```
arr = [1, 15, 7, 9, 2, 5, 10]
idx =  0   1  2  3  4  5   6
k = 3
```

At most 3 elements per partition — you're never allowed a piece of length 4 or more.

### Step 1 — Represent in Terms of a Single Index

Following the exact same reasoning as Palindrome Partitioning II, define:

```
f(index) = maximum sum achievable by partitioning
           arr[index ... n-1] — the suffix starting at index,
           all the way to the end of the array
```

The answer you ultimately want is `f(0)` — the maximum sum for the entire array.

### Step 2 — Explore Every Valid Partition Length

Standing at `index`, you don't know in advance how large the first piece should be — maybe just 1 element is best, maybe 2, maybe the full 3 allowed. So, exactly like every DP problem in this sheet: **you don't guess, you try every possibility.**

```
Try piece length 1: [arr[index]]                     → then solve f(index+1)
Try piece length 2: [arr[index], arr[index+1]]        → then solve f(index+2)
Try piece length 3: [arr[index], arr[index+1], arr[index+2]] → then solve f(index+3)
```

You are **not** allowed to try a piece of length 4 or more — the moment the piece would exceed `k` elements, that option simply doesn't exist. This is the one genuinely new constraint compared to Palindrome Partitioning II, where the loop ran unbounded all the way to the end of the string. Here, the loop is capped.

### What Does a Piece "Contribute" to the Total Sum?

Recall the rule: once you commit to a piece, **every element inside it gets replaced by the maximum value in that piece**. So if a piece has length `len` and its maximum element is `maxVal`, the piece's contribution to the total sum is simply:

```
contribution = len × maxVal
```

You compute this by walking the candidate piece one element at a time, growing `len` by 1 at each step and updating `maxVal` to be the running maximum seen so far within the piece — exactly the way you'd track a running max in a single pass.

### The Recurrence

```
f(index) = maximum over every valid piece length L (from 1 to k, capped
           at the array boundary) of:
               (L × maxValInThatPiece) + f(index + L)
```

Or, walking a second pointer `j` from `index` up to `index + k - 1` (bounded by array length), maintaining a running length and running max as `j` advances:

```
for j = index to min(index + k - 1, n - 1):
    length++
    currMax = max(currMax, arr[j])
    candidateSum = (length × currMax) + f(j + 1)
    maxAnswer = max(maxAnswer, candidateSum)

f(index) = maxAnswer
```

### Base Case

**When does the recursion stop needing to add anything more?**

```
if index == n:  return 0
```

Running out of array — nothing left to partition, nothing left to add. Identical reasoning to Palindrome Partitioning II's base case.

### Walking Through It by Hand

```
arr = [1, 15, 7, 9, 2, 5, 10]
k = 3
```

Compare the two partitions from earlier through the lens of this recurrence, starting at `f(0)`:

**Partition `[1,15] | [7,9,2] | [5,10]`:**
```
f(0): piece [1,15], length=2, max=15 → contributes 30, then solve f(2)
f(2): piece [7,9,2], length=3, max=9 → contributes 27, then solve f(5)
f(5): piece [5,10], length=2, max=10 → contributes 20, then solve f(7)
f(7): base case → 0

Total = 30 + 27 + 20 + 0 = 77
```

**Partition `[1,15,7] | [9] | [2,5,10]`:**
```
f(0): piece [1,15,7], length=3, max=15 → contributes 45, then solve f(3)
f(3): piece [9], length=1, max=9 → contributes 9, then solve f(4)
f(4): piece [2,5,10], length=3, max=10 → contributes 30, then solve f(7)
f(7): base case → 0

Total = 45 + 9 + 30 + 0 = 84
```

Both of these are legitimate branches that `f(0)`'s loop would explore — among these and every other valid partition, `f(0)` takes the **maximum**, correctly identifying `84` as better than `77`.

### Are There Overlapping Subproblems?

The same suffix starting index can be reached as the "leftover" from multiple different earlier partition-length choices — exactly the same overlap pattern confirmed in Palindrome Partitioning II. As the array grows, `f(index)` for a fixed `index` gets asked for repeatedly through different partition paths. **Overlapping subproblems confirmed** → DP is needed.

### DP Table Size

Only **one** changing parameter: `index`, ranging from `0` to `n` (inclusive, for the base case).

```
dp array size: n + 1
```

Same clean 1D shape as Palindrome Partitioning II — front partition problems collapse to a single-index state regardless of what property you're optimizing for.

# Stage 3: Coding

## Approach 1 — Pure Recursion (Brute Force)

```java
class Solution {
    public int maxSumAfterPartitioning(int[] arr, int k) {
        int n = arr.length;
        return solve(0, arr, n, k);
    }

    private int solve(int index, int[] arr, int n, int k) {
        // Base case: no elements left — nothing more to add
        if (index == n) return 0;

        int length = 0;
        int currMax = Integer.MIN_VALUE;
        int maxAnswer = Integer.MIN_VALUE;

        // Try every valid piece length starting at index, capped at k
        // WHY Math.min(index + k, n): the piece can never exceed k
        //     elements AND can never run past the end of the array
        for (int j = index; j < Math.min(index + k, n); j++) {
            length++;

            // Track the running maximum WITHIN this candidate piece
            currMax = Math.max(currMax, arr[j]);

            // WHY length * currMax: every element in this piece gets
            //     replaced by currMax once this partition is committed
            int sum = length * currMax + solve(j + 1, arr, n, k);

            maxAnswer = Math.max(maxAnswer, sum);
        }

        return maxAnswer;
    }
}
```

**Time Complexity — Exponential:**
At every index, the function tries up to `k` different piece lengths, and each one recurses further. The recursion tree branches by a factor of up to `k` at every level, with depth up to `n`. This grows exponentially and is impractical for large arrays.

**Space Complexity — O(n):**
No dp array is used. The recursion call stack holds one frame per level — the deepest chain of calls goes from index `0` all the way to index `n`, one element at a time in the worst case (every partition of length 1), giving up to `n` frames on the stack.

## Approach 2 — Memoization (Top-Down DP)

The same suffix starting index `index` gets asked for repeatedly from different parent branches. Store each result the first time it's computed.

```java
class Solution {
    public int maxSumAfterPartitioning(int[] arr, int k) {
        int n = arr.length;

        // dp[index] = -1 means not yet computed
        int[] dp = new int[n];
        Arrays.fill(dp, -1);

        return solve(0, arr, n, k, dp);
    }

    private int solve(int index, int[] arr, int n, int k, int[] dp) {
        // Base case: no elements left
        if (index == n) return 0;

        // Step 1: Already computed? Return stored value instantly
        // WHY: f(index) = max sum for arr[index..n-1] — this never
        //      changes no matter which earlier partition choice led here
        if (dp[index] != -1) return dp[index];

        int length = 0;
        int currMax = Integer.MIN_VALUE;
        int maxAnswer = Integer.MIN_VALUE;

        for (int j = index; j < Math.min(index + k, n); j++) {
            length++;
            currMax = Math.max(currMax, arr[j]);

            int sum = length * currMax + solve(j + 1, arr, n, k, dp);
            maxAnswer = Math.max(maxAnswer, sum);
        }

        // Step 2: Store before returning
        dp[index] = maxAnswer;
        return dp[index];
    }
}
```

**Time Complexity — O(n × k):**
There are `n` unique states (one per index). For each state, the inner loop runs at most `k` times — **not** `n` times, since the loop is capped at `k` regardless of how large the array is. Total: `O(n × k)`.

**Space Complexity — O(n) + O(n):**
The dp array of size `n`, plus the recursion call stack, which can go up to `n` levels deep in the worst case (every partition of length 1, forcing the deepest possible chain of calls).

## Approach 3 — Tabulation (Bottom-Up DP)

**Direction:** Recursion goes from index `0` **forward** toward index `n` (the base case). So tabulation goes the **opposite direction** — from index `n-1` **backward** toward index `0`. Same rule as Palindrome Partitioning II.

**Base case in tabulation:** `dp[n] = 0`.

```java
class Solution {
    public int maxSumAfterPartitioning(int[] arr, int k) {
        int n = arr.length;

        // dp[index] = max sum for arr[index..n-1]
        // Size n+1 to accommodate the base case at index n
        int[] dp = new int[n + 1];

        // Base case: dp[n] = 0 — already true via Java's default zero-init
        dp[n] = 0;

        // Fill from index = n-1 down to 0 — opposite of recursion's direction
        for (int index = n - 1; index >= 0; index--) {

            int length = 0;
            int currMax = Integer.MIN_VALUE;
            int maxAnswer = Integer.MIN_VALUE;

            for (int j = index; j < Math.min(index + k, n); j++) {
                length++;
                currMax = Math.max(currMax, arr[j]);

                // WHY dp[j + 1]: same recurrence as memoization,
                //     just a table lookup instead of a recursive call
                int sum = length * currMax + dp[j + 1];
                maxAnswer = Math.max(maxAnswer, sum);
            }

            dp[index] = maxAnswer;
        }

        // Answer: max sum for the entire array, starting at index 0
        return dp[0];
    }
}
```

**Time Complexity — O(n × k):**
Two nested loops — outer runs `n` times, inner runs at most `k` times. Each cell does O(1) work. Total: `O(n × k)`.

**Space Complexity — O(n):**
Only the dp array of size `n + 1`. No recursion stack at all.

| Approach | Time | Space | Notes |
|---|---|---|---|
| Pure Recursion | Exponential | O(n) stack | Never use |

| Tabulation | O(n × k) | O(n) | Best — submit this |

## How This Differs From Palindrome Partitioning II

| Property | Palindrome Partitioning II | Partition Array for Maximum Sum |
|---|---|---|
| State shape | Single index `i` | **Single index `index` — same shape** |
| Loop bound | Unbounded — scans to end of string | **Capped at `k` — never exceeds `k` elements** |
| Validity check per piece | `s[i..j]` must be a palindrome | **No validity check — every piece is automatically valid** |
| What a piece "contributes" | `1` cut (fixed cost) | **`length × maxInPiece`** (value depends on content) |
| Objective | Minimize cuts | **Maximize sum** |
| Combine rule | `min(1 + f(j+1))` | **`max(contribution + f(j+1))`** |
| Off-by-one correction needed? | Yes — subtract 1 (pieces vs. cuts) | **No — the sum is exactly what's asked for** |
| Time complexity | O(n³) (palindrome check costs O(n)) | **O(n × k)** — no per-piece validity scan needed beyond tracking running max |
