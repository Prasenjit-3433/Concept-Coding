# LC 132. Palindrome Partitioning II — Front Partition

---

# Stage 1: Identification

**Step 1 — Which topic?**

You're given a string. You need to partition it into the fewest number of pieces such that **every piece, on its own, is a palindrome**. Return the minimum number of **cuts** required.

```
s = "bababcbadcede"
```

You already know, without any cleverness at all, that cutting every single character apart into its own piece always works — every single character is trivially a palindrome. So a valid answer **always exists**; the question is purely about minimizing the number of cuts.

The moment you see **"minimum number of cuts/partitions such that each piece satisfies some property"** — that is the signal. To find the minimum, you must **try every possible way of partitioning** and pick the best. And whenever you try every possible way, **Recursion** is your first thought. And when that recursion has overlapping subproblems — it becomes **Dynamic Programming**.

**Step 2 — Which pattern?**

This is still under the broad umbrella of **Pattern 9: Interval / Partition DP** — but it introduces a genuinely different *shape* of partitioning than Matrix Chain Multiplication. In MCM, you picked **one** split point `k` inside a range `[i, j]` and broke it into exactly two pieces: `f(i, k)` and `f(k+1, j)`. Here, you don't break the string into two pieces at a time — you peel off **one palindromic prefix** at a time, from the front, and recurse on whatever remains. Striver names this style explicitly: **Front Partition**.

**Step 3 — Which key concept?**

**Front Partition — fix the start, try every possible end for the first piece, recurse on the leftover suffix.**

Apply the same 3-part recipe used everywhere else in DP, adapted to this shape:

```
Step 1: Express everything in terms of a single index `i`
        (i = where the CURRENT unsolved suffix of the string begins)
Step 2: Explore all possibilities — try every possible END point `j`
        for the first cut, provided s[i..j] is itself a palindrome
Step 3: Question says minimum → take the min across every valid choice of j
```

The key structural difference from MCM: instead of two indices `(i, j)` describing a fixed range you're optimizing internally, here a **single index `i`** describes "everything from here to the end of the string still needs to be cut," and the loop variable `j` represents *where you're willing to end the very first piece*. This is why Striver calls it front partition — you always work from the front, commit to how big the first piece is, and hand off the rest of the string to a smaller version of the exact same problem.

# Stage 2: Intuition Building

### The Problem Setup

```
s = "bababcbadcede"
```

If you cut every character apart individually, that's `n - 1 = 12` cuts (13 characters → 13 pieces). But you can clearly do much better. For instance:

```
"bab" | "a" | "bcbadcede"... 
```

wait — `bcbadcede` is not a palindrome, so that particular split doesn't fully work in one shot; the real point is that **some pieces can be made much larger than a single character**, as long as that whole piece reads the same forwards and backwards, and the goal is to find the split that uses the **fewest pieces total** (equivalently, the fewest cuts, since cuts = pieces − 1).

### Why "Front Partition" Is the Natural Way to Think About This

Stand at the very beginning of the string. Ask yourself: **how big can I make my very first piece, such that it's still a palindrome?** You don't know the answer in advance — maybe just the first character works, maybe the first three characters work, maybe more. So, exactly like every other DP problem in this sheet, **you don't guess — you try every possibility.**

```
s = "bababcbadcede"
     0123456789...
```

Standing at index 0, walk a second pointer `j` forward one character at a time, and at each step ask: **is `s[0..j]` a palindrome?**

```
j=0: "b"      → palindrome ✓  → valid cut here, 1 piece so far, recurse on s[1..]
j=1: "ba"     → not a palindrome ✗ → skip
j=2: "bab"    → palindrome ✓  → valid cut here, 1 piece so far, recurse on s[3..]
j=3: "baba"   → not a palindrome ✗ → skip
j=4: "babab"  → palindrome ✓  → valid cut here, recurse on s[5..]
...and so on, all the way to the end of the string
```

**Every single `j` where `s[i..j]` is a palindrome is a genuinely different way to make your first cut.** Each of those choices leaves behind a different leftover suffix, and each leftover suffix is itself a smaller instance of the exact same problem: *"what's the minimum number of cuts needed to palindrome-partition the rest of this string?"* You try every valid `j`, solve the leftover recursively, and take whichever choice gives the overall minimum.

### Step 1 — Represent in Terms of a Single Index `i`

Define:

```
f(i) = minimum number of cuts needed to palindrome-partition s[i..n-1]
       (the suffix of s starting at index i, all the way to the end)
```

The answer you ultimately want is `f(0)` — the minimum cuts for the entire string.

### Step 2 — Explore All Possibilities: Every Valid `j`

At state `i`, try every `j` from `i` to `n-1`. For each `j`, check if `s[i..j]` is a palindrome. If it is, that's a legal first piece, and it costs you **1 cut**, followed by however many cuts the leftover `s[j+1..n-1]` needs:

```
if s[i..j] is a palindrome:
    candidateCost = 1 + f(j+1)
```

Try this for **every** valid `j`, and keep the minimum:

```
f(i) = min over all valid j of ( 1 + f(j+1) )
```

**Why is it always `1 +`, and not something more complex?** Because committing to `s[i..j]` as one piece is exactly **one** cut, full stop — regardless of how long that piece is. The complexity all lives in the recursive call for whatever comes after it.

### Base Case

**When does the recursion stop needing any more cuts?**

```
if i == n:  return 0
```

If `i` has walked past the last character, there's nothing left of the string to partition — zero additional cuts needed. This mirrors the base case shape from every other index-based DP problem: running out of input means the recursive contribution from this point onward is zero.

### One Subtlety Striver Flags — the Off-By-One at the Very End

Notice something about how this recursion naturally behaves: even the very **last** valid split (where `j` reaches `n-1`, i.e., the entire remaining suffix itself is one palindrome) still gets counted as "1 cut" by the formula `1 + f(j+1)`, and `f(n)` correctly returns 0. But this means the recursion, run exactly as written, counts **the number of pieces**, not the number of *cuts* — and pieces = cuts + 1. So the raw output of `f(0)` will be **one more than the actual answer**, and you must **subtract 1** at the very end before returning it. This is a one-line fix, but it's the exact kind of detail that silently produces a wrong answer if missed — worth internalizing precisely because it's easy to overlook.

### Walking Through a Small Piece for Confidence

Take the tail end of the example: `s = "dcede"` treated as its own mini-string (indices renumbered 0–4 for clarity).

```
i=0 ("dcede"):
    j=0: "d" → palindrome ✓ → 1 + f(1)
    j=1: "dc" → not palindrome ✗
    j=2: "dce" → not palindrome ✗
    j=3: "dced" → not palindrome ✗
    j=4: "dcede" → not palindrome ✗
    → only one valid split at j=0
```

So `f(0)` for `"dcede"` reduces entirely to `1 + f(1)`, and `f(1)` (suffix `"cede"`) would similarly need to be explored — the point being every state genuinely tries **all** `j` positions, and however many turn out to be valid palindromic prefixes, that many branches get explored and compared.

### Do You Need to Materialize the Substring?

A natural instinct while coding this is to build the actual substring `s[i..j]` as its own string object at every step, to check if it's a palindrome. **You don't need to.** Since `i` and `j` are just indices into the original string, you can check the palindrome property directly against the original string using the two-pointer technique — no substring extraction, no wasted memory or time copying characters.

### Are There Overlapping Subproblems?

Consider a string with a repeating structure. The suffix starting exactly at some index `i` can be reached as the "leftover" from many different earlier cut choices — different values of `j` from different earlier states can all funnel down into asking for `f(i)` at the *same* index `i`. As the string grows, this overlap compounds. **Overlapping subproblems confirmed** → DP is needed.

### DP Table Size

Only **one** changing parameter: `i`, ranging from `0` to `n` (inclusive, to accommodate the base case at `i == n`).

```
dp array size: n + 1
```

This is a refreshing simplification compared to MCM's `n × n` table — front partition problems, because they only ever track a single "starting point" state, collapse down to a clean 1D DP.

# Stage 3: Coding

## Approach 1 — Pure Recursion (Brute Force)

```java
class Solution {
    public int minCut(String s) {
        int n = s.length();

        // The raw recursion counts PIECES, not cuts — subtract 1 at the end
        // WHY: even the final valid split still contributes "1 +" to the total,
        //      so f(0) always over-counts by exactly one piece
        return solve(0, s, n) - 1;
    }

    private int solve(int i, String s, int n) {
        // Base case: no characters left to partition — zero further cuts needed
        if (i == n) return 0;

        int minCost = Integer.MAX_VALUE;

        // Try every possible endpoint j for the first piece, starting at i
        for (int j = i; j < n; j++) {

            // Only proceed if s[i..j] is itself a palindrome —
            // otherwise this is not a legal piece at all
            if (isPalindrome(s, i, j)) {
                // WHY 1 + solve(j+1, ...): this piece costs exactly 1 cut,
                //     plus however many cuts the leftover suffix needs
                int cost = 1 + solve(j + 1, s, n);
                minCost = Math.min(minCost, cost);
            }
        }

        return minCost;
    }

    // Two-pointer palindrome check directly on the original string —
    // no substring is ever materialized
    private boolean isPalindrome(String s, int i, int j) {
        while (i < j) {
            if (s.charAt(i) != s.charAt(j)) return false;
            i++;
            j--;
        }
        return true;
    }
}
```

**Time Complexity — O(2^n) in the worst case:**
At every index `i`, the function tries up to `n - i` different split points, and each valid split recurses further. In the worst case (a string with many palindromic prefixes, such as all-identical characters), the number of distinct partition choices explored grows exponentially with the length of the string. Additionally, each `isPalindrome` check costs up to O(n), adding a further multiplicative factor. This is completely impractical for long strings.

**Space Complexity — O(n):**
No dp array is used. The recursion call stack holds one frame per level — the deepest chain of calls goes from index 0 all the way to index n, one cut at a time in the worst case (every character its own piece), giving n frames on the stack.

## Approach 2 — Memoization (Top-Down DP)

The same suffix starting index `i` gets asked for repeatedly from different parent branches. Store each result the first time it's computed.

```java
class Solution {
    public int minCut(String s) {
        int n = s.length();

        // dp[i] = -1 means not yet computed
        int[] dp = new int[n];
        Arrays.fill(dp, -1);

        return solve(0, s, n, dp) - 1;
    }

    private int solve(int i, String s, int n, int[] dp) {
        // Base case: no characters left
        if (i == n) return 0;

        // Step 1: Already computed? Return stored value instantly
        // WHY: f(i) = minimum pieces needed for s[i..n-1] — this never
        //      changes no matter which earlier cut choice led here
        if (dp[i] != -1) return dp[i];

        int minCost = Integer.MAX_VALUE;

        for (int j = i; j < n; j++) {
            if (isPalindrome(s, i, j)) {
                int cost = 1 + solve(j + 1, s, n, dp);
                minCost = Math.min(minCost, cost);
            }
        }

        // Step 2: Store before returning
        dp[i] = minCost;
        return dp[i];
    }

    private boolean isPalindrome(String s, int i, int j) {
        while (i < j) {
            if (s.charAt(i) != s.charAt(j)) return false;
            i++;
            j--;
        }
        return true;
    }
}
```

**Time Complexity — O(n² × n) = O(n³) in the worst case:**
There are `n` unique states (one per index `i`). For each state, the loop over `j` runs up to `n` times, and each `isPalindrome` check inside that loop costs up to `O(n)`. Total: `O(n) × O(n) × O(n) = O(n³)`.

**Space Complexity — O(n) + O(n):**
The dp array of size `n`, plus the recursion call stack, which can go up to `n` levels deep (the worst case being every character forced into its own piece).

**Why this can still time out on stricter judges:** as Striver notes, memoization removes *repeated* work across states, but the O(n) palindrome check inside the O(n) `j`-loop, repeated across O(n) states, still leaves an O(n³) solution — combined with genuine recursion call overhead, this can be too slow for large inputs on some judges. Tabulation removes the call-stack overhead, though the O(n³) time bound itself remains (a further optimization — precomputing all palindromic substrings up front — can bring this down to O(n²), but is not what this lecture teaches).

## Approach 3 — Tabulation (Bottom-Up DP)

**Direction:** Recursion goes from index `0` **forward** toward index `n` (the base case). So tabulation goes the **opposite direction** — from index `n-1` **backward** toward index `0`.

**Base case in tabulation:** `dp[n] = 0`. In Java, this requires declaring the array with an explicit extra slot of size `n + 1`.

```java
class Solution {
    public int minCut(String s) {
        int n = s.length();

        // dp[i] = minimum pieces needed for s[i..n-1]
        // Size n+1 to accommodate the base case at index n
        int[] dp = new int[n + 1];

        // Base case: dp[n] = 0 — already true via Java's default zero-init,
        // but written explicitly for clarity
        dp[n] = 0;

        // Fill from i = n-1 down to 0 — opposite of recursion's direction
        for (int i = n - 1; i >= 0; i--) {
            int minCost = Integer.MAX_VALUE;

            for (int j = i; j < n; j++) {
                if (isPalindrome(s, i, j)) {
                    // WHY dp[j+1]: same recurrence as memoization,
                    //     just a table lookup instead of a recursive call
                    int cost = 1 + dp[j + 1];
                    minCost = Math.min(minCost, cost);
                }
            }

            dp[i] = minCost;
        }

        // dp[0] counts PIECES, not cuts — subtract 1
        return dp[0] - 1;
    }

    private boolean isPalindrome(String s, int i, int j) {
        while (i < j) {
            if (s.charAt(i) != s.charAt(j)) return false;
            i++;
            j--;
        }
        return true;
    }
}
```

### Dry Run on a Small Case

Take `s = "aab"` (n = 3) to see the table fill cleanly end to end.

```
Base case: dp[3] = 0

i = 2 ("b"):
    j=2: "b" → palindrome ✓ → cost = 1 + dp[3] = 1
    dp[2] = 1

i = 1 ("ab"):
    j=1: "a" → palindrome ✓ → cost = 1 + dp[2] = 1 + 1 = 2
    j=2: "ab" → not palindrome ✗
    dp[1] = 2

i = 0 ("aab"):
    j=0: "a" → palindrome ✓ → cost = 1 + dp[1] = 1 + 2 = 3
    j=1: "aa" → palindrome ✓ → cost = 1 + dp[2] = 1 + 1 = 2   ← best so far
    j=2: "aab" → not palindrome ✗
    dp[0] = min(3, 2) = 2

Answer = dp[0] - 1 = 2 - 1 = 1
```

Confirms correctly: `"aab"` can be split as `"aa" | "b"` — exactly **1 cut**, two pieces. ✓

**Time Complexity — O(n³):**
Same bound as memoization — `n` states, each doing an `O(n)` loop with an `O(n)` palindrome check inside. No change in the asymptotic bound, but no recursion call overhead.

**Space Complexity — O(n):**
Only the dp array of size `n + 1`. No recursion stack at all.

## Approach 4 — A Note on Further Optimization (Not Required, But Worth Knowing)

The `isPalindrome` check re-scans characters from scratch on every single call, even though many of these checks overlap heavily with each other. A well-known follow-up optimization: precompute a **2D boolean table** `isPalin[i][j]` for every substring in `O(n²)` time using the standard "palindrome expands from the inside out" DP relation (`isPalin[i][j] = (s[i] == s[j]) && isPalin[i+1][j-1]`), and then look up that table in `O(1)` inside the main loop instead of rescanning. This brings the overall time down from `O(n³)` to `O(n²)`. This is a valid and commonly-expected follow-up in interviews, but — exactly as Striver notes for this lecture — it is not the core technique being taught here, so it's flagged only as an extension rather than built out in full.

## Final Comparison

| Approach | Time | Space | Notes |
|---|---|---|---|
| Pure Recursion | O(2^n) (worst case) | O(n) stack | Exponential — never use |
| Memoization | O(n³) | O(n) + O(n) stack | Good interview starting point |
| Tabulation | O(n³) | O(n) | Better — eliminates stack |
| Tabulation + Precomputed Palindromes | O(n²) | O(n²) | Follow-up optimization, not core to this lecture |

## How This Differs From Matrix Chain Multiplication

| Property | MCM (Pattern 9, earlier) | Palindrome Partitioning II |
|---|---|---|
| State shape | Two indices `(i, j)` — a fixed range | **One index `i`** — "everything from here onward" |
| What you try at each state | A split point `k` dividing the range into TWO pieces | **An endpoint `j`** for a single first piece, of variable size |
| What happens after the split | BOTH sides get recursively solved | **Only the leftover suffix** gets recursively solved — the first piece is "done" the moment it's confirmed a palindrome |
| DP table shape | n × n | **n** (1D) |
| Named technique | Classic Interval DP | **Front Partition** |
