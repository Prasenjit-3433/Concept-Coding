# LC 322. Coin Change

---

# Stage 1: Identification

**Step 1 — Which topic?**

You are given an array of coin denominations and a target amount. You need to find the **minimum number of coins** required to make up that amount. If it is not possible, return -1.

The moment you see **"find the minimum among all possible ways to form a target"** — that is the signal. To find the minimum, you must **try all possible combinations**. And whenever you try all combinations, **Recursion** is your first thought. And when that recursion has overlapping subproblems — it becomes **Dynamic Programming**.

**Why doesn't Greedy work here?**

The greedy instinct says — always pick the largest coin that fits. Consider:

```
coins = [9, 6, 5, 1],  amount = 11
```

Greedy picks 9 (largest ≤ 11). Leftover = 2. 6 doesn't fit. 5 doesn't fit. Pick 1 twice. Total = **3 coins** (9 + 1 + 1).

But the optimal is: pick 6 + 5 = 11. Total = **2 coins**.

Why did greedy fail? **There is no uniformity** in the coin denominations. The differences between them are irregular — 9 to 6 is 3, 6 to 5 is 1, 5 to 1 is 4. Because of this irregularity, picking the biggest coin now can block access to a far better combination later. You must try all combinations.

**Step 2 — Which pattern?**

Each coin denomination can be used **any number of times** — infinite supply. There is a target constraint (amount). You want to **minimize** the number of coins used.

That is **Pattern 5: Unbounded Knapsack**.

The key structural signal:
- Items can be reused unlimited times → Unbounded
- Target constraint exists → Knapsack
- Goal is minimize count → variation of the classic maximize-value template

**Step 3 — Which key concept?**

Apply Striver's **3-step shortcut**:

```
Step 1: Represent in terms of (index, target)
Step 2: Explore all possibilities — Take or Not Take
Step 3: Question says minimum → take min of all choices
```

**The one critical rule for Unbounded Knapsack** (established in the previous problem):

> When you TAKE a coin, **stay at the same index** — don't move to index-1.
> This allows the same coin to be picked again in the next call.
> The target shrinks. The index does not.

This is the single thumb rule that separates Unbounded Knapsack from 0/1 Knapsack.

# Stage 2: Intuition Building

### The Problem Setup

```
coins = [1, 2, 3],  amount = 7
```

You have coins of denominations 1, 2, and 3 — each with infinite supply. What is the minimum number of coins to make 7?

Some valid combinations:

```
{3, 3, 1}   → 3 coins
{3, 2, 2}   → 3 coins
{2, 2, 2, 1}→ 4 coins
{3, 3, 1}   → 3 coins  ← minimum
```

The answer is **3 coins**.

### Step 1 — Represent in terms of (index, target)

Define:

```
f(index, target) = minimum number of coins needed to form 'target'
                   using coins from coins[0...index],
                   where each coin has infinite supply
```

The answer we want is `f(n-1, amount)`.

### Step 2 — Do all possible things at (index, target)

At any index, exactly two choices:

**Choice 1 — Not Take:**
Skip the coin at this index. Move to the previous index. Target stays unchanged.

```
notTake = 0 + f(index - 1, target)
```

Adding 0 because not taking a coin means not incrementing the coin count.

**Choice 2 — Take:**
Use the coin at this index. Only valid if `coins[index] <= target` (coin must not exceed what we need).

Add **1** to the coin count (we used one coin). Target shrinks by `coins[index]`.

**Stay at the same index** — infinite supply means we can pick this coin again.

```
take = Integer.MIN_VALUE   (initially invalid)
if coins[index] <= target:
    take = 1 + f(index, target - coins[index])
                  ↑
        SAME index — not index-1
        This is the ONLY difference from 0/1 Knapsack
```

**Why `Integer.MIN_VALUE` and not 0?** Because we are looking for **minimum**. An impossible take case must be made **unattractive** so `min()` never picks it. Setting it to `Integer.MIN_VALUE` does not work here though — if we add 1 to `Integer.MIN_VALUE`, it overflows. So Striver uses **1e9** as the sentinel instead of `Integer.MAX_VALUE`.

### Step 3 — Take minimum

```
f(index, target) = min(notTake, take)
```

### Base Case — When index == 0

Only coin 0 is available with infinite supply. The current target can be anything from 0 to amount. How many coins do we need?

```
If target % coins[0] == 0:
    → We can form target using (target / coins[0]) coins
    → Return target / coins[0]
Else:
    → Cannot form target with coin 0 alone
    → Return 1e9  (impossible — large sentinel so min() never picks this)
```

Why `1e9` and not `Integer.MAX_VALUE`? Because later we add 1 to the result — `1 + f(...)`. If `f(...)` returns `Integer.MAX_VALUE`, then `1 + Integer.MAX_VALUE` **overflows** to a negative number, which would be incorrectly picked as the minimum. Using `1e9` keeps all values safely within int range even after addition.

### Visualizing the Recursion Tree

```
coins = [1, 2, 3],  amount = 7

f(2, 7)
├── NOT TAKE coin[2]=3  → f(1, 7)
│   ├── NOT TAKE coin[1]=2 → f(0, 7)
│   │       7 % 1 == 0 → return 7      (7 coins of denomination 1)
│   └── TAKE coin[1]=2  → 1 + f(1, 5)  ← stays at index 1
│           └── TAKE 2  → 1 + f(1, 3)
│                   └── TAKE 2 → 1 + f(1, 1)
│                           ├── NOT TAKE → f(0, 1) → return 1
│                           └── TAKE: 2 > 1, CANNOT TAKE
│                           → min(1, INVALID) = 1
│                       → 1 + 1 = 2
│                   → 1 + 2 = 3
│               → 1 + 3 = 4
│   f(1, 7) = min(7, 4) = 4
│
└── TAKE coin[2]=3      → 1 + f(2, 4)  ← stays at index 2
        ├── NOT TAKE → f(1, 4) = 2
        └── TAKE 3   → 1 + f(2, 1)
                ├── NOT TAKE → f(1, 1) = 1
                └── TAKE: 3 > 1, CANNOT TAKE
                → 1 + 1 = 2
        f(2, 4) = min(2, 2) = 2
    → 1 + 2 = 3

f(2, 7) = min(4, 3) = 3 ✓
```

### Overlapping Subproblems

Notice `f(1, 5)`, `f(0, 7)`, `f(1, 1)` all appear in multiple branches. As n and amount grow, the explosion is massive — subproblems are revisited exponentially.

**Overlapping subproblems confirmed** → DP is needed.

### DP Table Size

Two parameters:
- `index`: 0 to n-1 → **n values**
- `target`: 0 to amount → **amount+1 values**

dp table: **n × (amount+1)**

# Stage 3: Coding

## Approach 1 — Pure Recursion (Brute Force)

```java
class Solution {
    public int coinChange(int[] coins, int amount) {
        int n = coins.length;
        int ans = solve(n - 1, amount, coins);

        // WHY this check: if the answer is >= 1e9, it means the target
        // was never reachable — no valid combination of coins exists
        // The problem asks to return -1 in this case
        if (ans >= (int) 1e9) return -1;
        return ans;
    }

    private int solve(int index, int target, int[] coins) {
        // Base case: only coin at index 0 available, infinite supply
        // How many of coin[0] do we need?
        // WHY (int)1e9 when not divisible: returning Integer.MAX_VALUE
        //     causes overflow when we add 1 to it in parent calls
        //     1e9 is safe — even 1 + 1e9 stays within int range
        if (index == 0) {
            if (target % coins[0] == 0) return target / coins[0];
            else return (int) 1e9;
        }

        // Choice 1: Not Take — skip this coin
        // Adding 0 to coin count since we're not using this coin
        // Move to previous index, target stays unchanged
        int notTake = solve(index - 1, target, coins);

        // Choice 2: Take — use this coin (only if it fits)
        // WHY stay at same index: infinite supply — can pick it again
        // WHY add 1: we used one coin here
        // WHY target - coins[index]: remaining amount after using this coin
        int take = (int) 1e9;
        if (coins[index] <= target) {
            take = 1 + solve(index, target - coins[index], coins);
        }

        // Return minimum — we want fewest coins
        return Math.min(notTake, take);
    }
}
```

**Time Complexity — Exponential:**
At every index, the function makes 2 recursive calls — one for notTake and one for take. But unlike 0/1 Knapsack, the take case **stays at the same index** and only reduces the target. So for a single coin of denomination 1 and amount 1000, the recursion can go 1000 levels deep just from the take branch of index 0. The tree is not simply binary of depth n — it branches based on both n and amount. The time complexity is exponential and cannot be cleanly expressed as 2^n. In interviews, call it **exponential**.

**Space Complexity — O(amount) for the recursion stack:**
The deepest call chain occurs when repeatedly taking the smallest denomination coin. If the smallest coin is 1 and the amount is T, the call stack goes T levels deep before hitting the base case. So auxiliary stack space is **O(amount)** in the worst case — not O(n).

## Approach 2 — Memoization (Top-Down DP)

The same state `f(index, target)` is reached from multiple branches. For example, `f(1, 3)` might be triggered via different take/notTake combinations at higher indices. Store each result the first time.

**3 steps to convert recursion to memoization:**
```
Step 0: Declare dp array of size n × (amount+1), initialize all to -1
Step 1: Before computing, check — if dp[index][target] != -1, return it  (lookup)
Step 2: After computing, store — dp[index][target] = result              (store)
```

```java
class Solution {
    public int coinChange(int[] coins, int amount) {
        int n = coins.length;
        int[][] dp = new int[n][amount + 1];
        for (int[] row : dp) {
            Arrays.fill(row, -1);
        }
        int ans = solve(n - 1, amount, coins, dp);
        if (ans >= (int) 1e9) return -1;
        return ans;
    }

    private int solve(int index, int target, int[] coins, int[][] dp) {
        // Base case: only coin[0] available, infinite supply
        if (index == 0) {
            if (target % coins[0] == 0) return target / coins[0];
            else return (int) 1e9;
        }

        // Step 1: Already computed? Return stored value instantly
        // WHY: f(1, 5) = min coins to form 5 using coins[0..1]
        //      This never changes regardless of which path reached this state
        if (dp[index][target] != -1) return dp[index][target];

        // Choice 1: Not Take
        int notTake = solve(index - 1, target, coins, dp);

        // Choice 2: Take (only if coin fits)
        // WHY 1e9 as default: prevents overflow when adding 1 to result
        int take = (int) 1e9;
        if (coins[index] <= target) {
            take = 1 + solve(index, target - coins[index], coins, dp);
        }

        // Step 2: Store before returning
        // WHY: next time solve(index, target) is called,
        //      answer is ready in O(1) — no recomputation
        dp[index][target] = Math.min(notTake, take);
        return dp[index][target];
    }
}
```

**Time Complexity — O(n × amount):**
Each unique (index, target) pair is computed exactly once. There are n × (amount+1) unique states. For each state, O(1) work is done — compute notTake and take, then take min. Total: **O(n × amount)**.

**Space Complexity — O(n × amount) + O(amount):**
Two sources of space. First, the dp array of size n × (amount+1) — that is O(n × amount). Second, the recursion call stack — the deepest chain in the take direction can go up to amount levels deep (taking denomination 1 repeatedly). Total: **O(n × amount) + O(amount)**.

## Approach 3 — Tabulation (Bottom-Up DP)

**Direction:** Recursion goes from index n-1 **downward** to index 0. Tabulation goes the **opposite direction** — from index 0 **upward** to index n-1.

**Base case in tabulation:**

When `index == 0`, for every target `t` from 0 to amount:
- If `t % coins[0] == 0` → `dp[0][t] = t / coins[0]`
- Else → `dp[0][t] = 1e9` (impossible)

**The key difference from 0/1 Knapsack in tabulation:**

In 0/1 Knapsack, the take case used `dp[i-1][w - wt[i]]` — the **previous row**.

In Unbounded Knapsack, the take case uses `dp[i][target - coins[i]]` — the **same row**, to the left.

This means when computing `dp[i][target]`, if we fill left to right, `dp[i][target - coins[i]]` is **already updated to the current row** — which is exactly what we want (allows picking the same coin again).

```java
class Solution {
    public int coinChange(int[] coins, int amount) {
        int n = coins.length;

        // dp[i][t] = minimum coins to form target t using coins[0..i]
        int[][] dp = new int[n][amount + 1];

        // Step 2: Fill base case — index = 0, only coins[0] available
        // For every target from 0 to amount, fill how many of coins[0] needed
        for (int t = 0; t <= amount; t++) {
            if (t % coins[0] == 0) {
                dp[0][t] = t / coins[0];
            } else {
                // Cannot form t with just coins[0]
                // WHY 1e9 not Integer.MAX_VALUE: adding 1 to MAX_VALUE overflows
                dp[0][t] = (int) 1e9;
            }
        }

        // Step 3: Fill from index=1 to n-1
        for (int i = 1; i < n; i++) {
            // Target goes from 0 to amount
            // WHY left to right: take case uses dp[i][t - coins[i]]
            //     which is to the LEFT — already updated in this pass
            //     This correctly allows the same coin to be used multiple times
            for (int t = 0; t <= amount; t++) {

                // Choice 1: Not Take coins[i]
                // WHY dp[i-1][t]: skip this coin, use result from previous row
                int notTake = dp[i - 1][t];

                // Choice 2: Take coins[i] — only if it fits
                // WHY dp[i][t - coins[i]] not dp[i-1][...]: same row
                //     because infinite supply — coin can be picked again
                // WHY 1e9 as default: safe sentinel for minimum computation
                int take = (int) 1e9;
                if (coins[i] <= t) {
                    take = 1 + dp[i][t - coins[i]];
                }

                dp[i][t] = Math.min(notTake, take);
            }
        }

        // Final answer: min coins for full amount using all n coins
        // WHY this check: if result >= 1e9, no valid combination exists
        int ans = dp[n - 1][amount];
        return ans >= (int) 1e9 ? -1 : ans;
    }
}
```

**Dry Run:**

```
coins = [1, 2, 3],  amount = 7,  n = 3

Step 1 — Fill index=0 (coins[0]=1):
Every t % 1 == 0 → dp[0][t] = t / 1 = t
dp[0] = [0, 1, 2, 3, 4, 5, 6, 7]
          0  1  2  3  4  5  6  7

Step 2 — Fill i=1 (coins[1]=2):
t=0: notTake=0,     take=N/A(2>0) → 0
t=1: notTake=1,     take=N/A(2>1) → 1
t=2: notTake=2,     take=1+dp[1][0]=1+0=1 → min(2,1)=1
t=3: notTake=3,     take=1+dp[1][1]=1+1=2 → min(3,2)=2
t=4: notTake=4,     take=1+dp[1][2]=1+1=2 → min(4,2)=2
t=5: notTake=5,     take=1+dp[1][3]=1+2=3 → min(5,3)=3
t=6: notTake=6,     take=1+dp[1][4]=1+2=3 → min(6,3)=3
t=7: notTake=7,     take=1+dp[1][5]=1+3=4 → min(7,4)=4

dp[1] = [0, 1, 1, 2, 2, 3, 3, 4]

Step 3 — Fill i=2 (coins[2]=3):
t=0: notTake=0,     take=N/A(3>0) → 0
t=1: notTake=1,     take=N/A(3>1) → 1
t=2: notTake=1,     take=N/A(3>2) → 1
t=3: notTake=2,     take=1+dp[2][0]=1+0=1 → min(2,1)=1
t=4: notTake=2,     take=1+dp[2][1]=1+1=2 → min(2,2)=2
t=5: notTake=3,     take=1+dp[2][2]=1+1=2 → min(3,2)=2
t=6: notTake=3,     take=1+dp[2][3]=1+1=2 → min(3,2)=2
t=7: notTake=4,     take=1+dp[2][4]=1+2=3 → min(4,3)=3

```

**Time Complexity — O(n × amount):**
Two nested loops — outer runs n-1 times, inner runs amount+1 times. Each cell does O(1) work. Total: **O(n × amount)**. No function call overhead, no recursion stack.

**Space Complexity — O(n × amount):**
Only the dp array of size n × (amount+1). No recursion stack at all.

## Approach 4 — Space Optimization (The Final Form)

Look at the recurrence:

```
dp[i][t] = min(dp[i-1][t],  1 + dp[i][t - coins[i]])
```

The notTake case uses **row i-1**. The take case uses **row i itself** (same row, to the left).

Since we fill left to right, by the time we compute `dp[i][t]`, the value `dp[i][t - coins[i]]` (to the left on the same row) is already updated. This is exactly correct for unbounded knapsack.

Now notice — to compute row i, we need row i-1 (for notTake) AND the current row being built (for take). This means we can use a **single array** and update it in place, left to right.

- When we read `prev[t]` (before updating), it still holds the row i-1 value → correct for notTake.
- When we read `prev[t - coins[i]]` (to the left), it already holds the row i value (updated this pass) → correct for take.

Both are correct with a single in-place array, filled left to right.

```
Direction rule (established in Unbounded Knapsack classic):
    0/1 Knapsack:       fill RIGHT TO LEFT  (prevent reuse)
    Unbounded Knapsack: fill LEFT TO RIGHT  (allow reuse)
```

```java
class Solution {
    public int coinChange(int[] coins, int amount) {
        int n = coins.length;

        // prev[t] = minimum coins to form target t using coins seen so far
        // Initialize with base case for index=0
        int[] prev = new int[amount + 1];

        // Base case: only coins[0] available, infinite supply
        for (int t = 0; t <= amount; t++) {
            if (t % coins[0] == 0) {
                prev[t] = t / coins[0];
            } else {
                prev[t] = (int) 1e9;
            }
        }

        // Fill from index=1 to n-1
        for (int i = 1; i < n; i++) {
            // Fill LEFT TO RIGHT — critical for correctness
            // WHY left to right: take case reads prev[t - coins[i]]
            //     which is to the left and already updated in this pass
            //     → holds current row's value → same coin can be picked again
            //     If we filled right to left, prev[t - coins[i]] would hold
            //     row i-1 value → same coin picked only once → 0/1 behavior
            for (int t = 0; t <= amount; t++) {

                // Not Take: read prev[t] BEFORE updating
                // WHY prev[t] is still row i-1 value here:
                //     we haven't written to position t yet in this pass
                //     (we're filling left to right, and this is index t)
                int notTake = prev[t];

                // Take: read prev[t - coins[i]] which is to the LEFT
                // WHY it holds row i value: already updated this pass
                //     → correctly allows the same coin to be reused
                int take = (int) 1e9;
                if (coins[i] <= t) {
                    take = 1 + prev[t - coins[i]];
                }

                // Update prev[t] in place — this now IS the current row
                prev[t] = Math.min(notTake, take);
            }
        }

        // Final answer
        int ans = prev[amount];
        return ans >= (int) 1e9 ? -1 : ans;
    }
}
```

**Time Complexity — O(n × amount):**
Two nested loops — outer runs n-1 times, inner runs amount+1 times left to right. Each iteration does O(1) work. Total: **O(n × amount)**. Same as tabulation.

**Space Complexity — O(amount):**
No n × (amount+1) array. No recursion stack. Just one array of size amount+1 — `prev`. Memory is completely independent of n. That is the key win.

| Approach | Time | Space | Notes |
|---|---|---|---|
| Pure Recursion | Exponential | O(amount) stack | Never use |
| Memoization | O(n × amount) | O(n×amount) + O(amount) stack | Good interview starting point |
| Tabulation | O(n × amount) | O(n × amount) | Better — eliminates stack |
| Space Optimization | O(n × amount) | **O(amount)** | Best — submit this |

## How This Problem Differs from Unbounded Knapsack Classic

| Property | Classic Unbounded Knapsack | LC 322 Coin Change |
|---|---|---|
| Goal | Maximize total value | **Minimize** coin count |
| What you add when taking | `val[i]` | **1** (one coin used) |
| Impossible sentinel | `-1e9` (maximizing, make bad paths repulsive) | **`+1e9`** (minimizing, make bad paths repulsive) |
| Final answer check | None needed | **If ans ≥ 1e9, return -1** |
| Base case at index 0 | `(W / wt[0]) * val[0]` | **`t / coins[0]`** (if divisible) or **`1e9`** |

The recurrence structure, the direction rules, and the space optimization logic are identical. Only Step 3 (min instead of max) and the sentinel value flip.
