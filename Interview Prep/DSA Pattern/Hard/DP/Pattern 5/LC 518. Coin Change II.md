# LC 518. Coin Change II

---

# Stage 1: Identification

**Step 1 — Which topic?**

You are given an array of coin denominations and a target amount. You need to find the **total number of ways** to make up that amount. Each coin denomination can be used **any number of times**.

The moment you see **"count the total number of ways"** — that is the signal. To count all ways, you must **try all possible combinations**. And whenever you try all combinations, **Recursion** is your first thought. And when that recursion has overlapping subproblems — it becomes **Dynamic Programming**.

**Step 2 — Which pattern?**

Each coin denomination can be used **any number of times** — infinite supply. There is a target constraint (amount). You want to **count** the number of valid combinations.

That is **Pattern 5: Unbounded Knapsack**.

**Step 3 — Which key concept?**

Apply Striver's **3-step shortcut**:

```
Step 1: Represent in terms of (index, target)
Step 2: Explore all possibilities — Take or Not Take
Step 3: Question says count all ways → SUM all choices
```

**The Unbounded thumb rule stays exactly the same:**

> When you TAKE a coin, **stay at the same index** — don't move to index-1.
> This allows the same coin to be picked again in the next call.
> The target shrinks. The index does not.

**The only change from LC 322 Coin Change:**

```
LC 322 (minimize coins):  return min(notTake, take)
LC 518 (count ways):      return notTake + take
```

This single change — min to ADD — is what converts a minimization problem into a counting problem. Everything else (state, recurrence, direction rules, space optimization) stays identical.

# Stage 2: Intuition Building

### The Problem Setup

```
coins = [1, 2, 3],  amount = 4
```

You have coins of denominations 1, 2, and 3 — each with infinite supply. In how many ways can you form 4?

```
{1, 1, 1, 1}   → 1 used four times
{1, 1, 2}      → 1 twice, 2 once
{2, 2}         → 2 twice
{1, 3}         → 1 once, 3 once
```

The answer is **4 ways**.

### Step 1 — Represent in terms of (index, target)

Define:

```
f(index, target) = number of ways to form 'target'
                   using coins from coins[0...index],
                   where each coin has infinite supply
```

The answer we want is `f(n-1, amount)`.

### Step 2 — Do all possible things at (index, target)

At any index, exactly two choices:

**Choice 1 — Not Take:**
Skip this coin. Move to the previous index. Target stays unchanged.

```
notTake = f(index - 1, target)
```

**Choice 2 — Take:**
Use this coin. Only valid if `coins[index] <= target`.
Target shrinks. **Stay at the same index** — infinite supply.

```
take = 0
if coins[index] <= target:
    take = f(index, target - coins[index])
              ↑
    SAME index — not index-1
    This is the Unbounded rule
```

### Step 3 — Sum because we are counting ways

```
f(index, target) = notTake + take
```

### Base Case — When index == 0

Only coin 0 is available with infinite supply. The current target can be anything from 0 to amount.

```
If target % coins[0] == 0:
    → We can form target using coins[0] repeatedly
    → Return 1  (exactly ONE way to do it)
Else:
    → Cannot form target with coin 0 alone
    → Return 0  (no valid way)
```

**Why return 1 and not `target / coins[0]`?**

In LC 322, we returned `target / coins[0]` because we were counting **coins used**. Here we are counting **the number of distinct ways to form the target** — and there is only ONE way to form a target using a single denomination (use it exactly `target / coins[0]` times). So return 1.

**Why return 0 when not divisible?**

If `target % coins[0] != 0`, there is no way to form target using only coin 0. So there are 0 ways.

### Visualizing the Recursion Tree

```
coins = [1, 2, 3],  amount = 4

f(2, 4):
├── NOT TAKE coin[2]=3 → f(1, 4)
│   ├── NOT TAKE coin[1]=2 → f(0, 4)
│   │       4 % 1 == 0 → return 1       ({1,1,1,1})
│   └── TAKE coin[1]=2  → f(1, 2)       (stays at index 1)
│           ├── NOT TAKE → f(0, 2)
│           │       2 % 1 == 0 → return 1    ({1,1} after taking {2})
│           └── TAKE 2   → f(1, 0)
│                   target=0: 0 % 1 == 0 → return 1   ({2,2})
│           f(1,2) = 1 + 1 = 2
│   f(1,4) = 1 + 2 = 3
│
└── TAKE coin[2]=3      → f(2, 1)       (stays at index 2)
        ├── NOT TAKE → f(1, 1)
        │   ├── NOT TAKE → f(0, 1)
        │   │       1 % 1 == 0 → return 1    ({1} after taking {3})
        │   └── TAKE 2: 2 > 1, CANNOT TAKE
        │   f(1,1) = 1
        └── TAKE 3: 3 > 1, CANNOT TAKE
        f(2,1) = 1

f(2, 4) = 3 + 1 = 4 ✓
```

### Overlapping Subproblems

Notice states like `f(0, 2)`, `f(1, 1)` appear in multiple branches. With larger inputs the explosion is massive — the same state is revisited exponentially.

**Overlapping subproblems confirmed** → DP is needed.

### DP Table Size

Two parameters:
- `index`: 0 to n-1 → **n values**
- `target`: 0 to amount → **amount+1 values**

dp table: **n × (amount+1)**

# Stage 3: Coding

## Approach 1 — Pure Recursion (Brute Force)

```java
class Solution {
    public int change(int amount, int[] coins) {
        int n = coins.length;
        return solve(n - 1, amount, coins);
    }

    private int solve(int index, int target, int[] coins) {
        // Base case: only coins[0] available, infinite supply
        // There is exactly ONE way to form a divisible target (use it target/coins[0] times)
        // There are ZERO ways to form a non-divisible target
        // WHY return 1 (not target/coins[0]): we're counting WAYS, not coins used
        //     There is only one distinct combination using a single denomination
        if (index == 0) {
            return target % coins[0] == 0 ? 1 : 0;
        }

        // Choice 1: Not Take — skip this coin
        // Move to previous index, target unchanged
        int notTake = solve(index - 1, target, coins);

        // Choice 2: Take — use this coin (only if it fits)
        // WHY stay at same index: infinite supply — can pick it again
        // WHY target - coins[index]: remaining amount after using this coin
        int take = 0;
        if (coins[index] <= target) {
            take = solve(index, target - coins[index], coins);
        }

        // SUM both choices — we are counting all valid ways
        // WHY add and not min: every valid path through notTake
        //     and every valid path through take are separate combinations
        return notTake + take;
    }
}
```

**Time Complexity — Exponential:**
At every index, the function makes 2 recursive calls. But the take case **stays at the same index** and only reduces the target. So for a single coin of denomination 1 and amount 10, the recursion can go 10 levels deep from the take branch alone — without ever moving to the previous index. This means the tree is not simply binary of depth n. It branches based on both n and amount. The time complexity is **exponential** and cannot be expressed cleanly as 2^n.

**Space Complexity — O(amount) for the recursion stack:**
The deepest call chain occurs when repeatedly taking the smallest denomination coin. If the smallest coin is 1 and the amount is T, the call stack goes T levels deep before hitting the base case. So auxiliary stack space is **O(amount)** in the worst case — not O(n).

## Approach 2 — Memoization (Top-Down DP)

The same state `f(index, target)` is reached from multiple branches. Store each result the first time.

```java
class Solution {
    public int change(int amount, int[] coins) {
        int n = coins.length;
        int[][] dp = new int[n][amount + 1];
        for (int[] row : dp) {
            Arrays.fill(row, -1);
        }
        return solve(n - 1, amount, coins, dp);
    }

    private int solve(int index, int target, int[] coins, int[][] dp) {
        // Base case: only coins[0] available
        // Exactly one way if divisible, zero ways if not
        if (index == 0) {
            return target % coins[0] == 0 ? 1 : 0;
        }

        // Step 1: Already computed? Return stored value instantly
        // WHY: f(1, 2) = ways to form 2 using coins[0..1]
        //      This never changes regardless of which path reached this state
        if (dp[index][target] != -1) return dp[index][target];

        // Choice 1: Not Take
        int notTake = solve(index - 1, target, coins, dp);

        // Choice 2: Take (only if coin fits)
        // WHY stay at same index: infinite supply
        int take = 0;
        if (coins[index] <= target) {
            take = solve(index, target - coins[index], coins, dp);
        }

        // Step 2: Store before returning
        dp[index][target] = notTake + take;
        return dp[index][target];
    }
}
```

**Time Complexity — O(n × amount):**
Each unique (index, target) pair is computed exactly once. There are n × (amount+1) unique states. For each state, O(1) work is done — compute notTake and take, then add them. Total: **O(n × amount)**.

**Space Complexity — O(n × amount) + O(amount):**
Two sources of space. First, the dp array of size n × (amount+1). Second, the recursion call stack — the deepest chain in the take direction can go up to amount levels deep. Total: **O(n × amount) + O(amount)**.

## Approach 3 — Tabulation (Bottom-Up DP)

**Direction:** Recursion goes from index n-1 **downward** to index 0. Tabulation goes the **opposite direction** — from index 0 **upward** to index n-1.

**Base case in tabulation:**

When `index == 0`, for every target `t` from 0 to amount:
- If `t % coins[0] == 0` → `dp[0][t] = 1`
- Else → `dp[0][t] = 0`

**The key direction rule — same as Unbounded Knapsack classic:**

The take case uses `dp[i][t - coins[i]]` — the **same row**, to the left.

Fill left to right so that `dp[i][t - coins[i]]` is already updated when we read it — correctly allowing the same coin to be picked again.

```java
class Solution {
    public int change(int amount, int[] coins) {
        int n = coins.length;

        // dp[i][t] = number of ways to form target t using coins[0..i]
        int[][] dp = new int[n][amount + 1];

        // Step 2: Fill base case — index = 0, only coins[0] available
        // For every target from 0 to amount:
        // exactly 1 way if divisible, 0 ways otherwise
        for (int t = 0; t <= amount; t++) {
            dp[0][t] = (t % coins[0] == 0) ? 1 : 0;
        }

        // Step 3: Fill from index=1 to n-1
        for (int i = 1; i < n; i++) {
            // Fill LEFT TO RIGHT
            // WHY: take case uses dp[i][t - coins[i]] — same row, to the left
            //      Already updated in this pass → correctly allows reuse of same coin
            //      Filling right to left would use old row i-1 value → 0/1 behavior
            for (int t = 0; t <= amount; t++) {

                // Choice 1: Not Take coins[i]
                // WHY dp[i-1][t]: skip this coin, use result from previous row
                int notTake = dp[i - 1][t];

                // Choice 2: Take coins[i] — only if it fits
                // WHY dp[i][t - coins[i]] not dp[i-1][...]: same row (Unbounded rule)
                int take = 0;
                if (coins[i] <= t) {
                    take = dp[i][t - coins[i]];
                }

                // SUM — counting ways
                dp[i][t] = notTake + take;
            }
        }

        return dp[n - 1][amount];
    }
}
```

**Dry Run:**

```
coins = [1, 2, 3],  amount = 4,  n = 3

Step 1 — Fill index=0 (coins[0]=1):
Every t % 1 == 0 → dp[0][t] = 1 for all t
dp[0] = [1, 1, 1, 1, 1]
          0  1  2  3  4

Step 2 — Fill i=1 (coins[1]=2):
t=0: notTake=dp[0][0]=1, take=N/A(2>0)    → 1
t=1: notTake=dp[0][1]=1, take=N/A(2>1)    → 1
t=2: notTake=dp[0][2]=1, take=dp[1][0]=1  → 1+1=2
t=3: notTake=dp[0][3]=1, take=dp[1][1]=1  → 1+1=2
t=4: notTake=dp[0][4]=1, take=dp[1][2]=2  → 1+2=3

dp[1] = [1, 1, 2, 2, 3]

Step 3 — Fill i=2 (coins[2]=3):
t=0: notTake=dp[1][0]=1, take=N/A(3>0)    → 1
t=1: notTake=dp[1][1]=1, take=N/A(3>1)    → 1
t=2: notTake=dp[1][2]=2, take=N/A(3>2)    → 2
t=3: notTake=dp[1][3]=2, take=dp[2][0]=1  → 2+1=3
t=4: notTake=dp[1][4]=3, take=dp[2][1]=1  → 3+1=4

dp[2] = [1, 1, 2, 3, 4]

Answer = dp[2][4] = 4 ✓
```

**Time Complexity — O(n × amount):**
Two nested loops — outer runs n-1 times, inner runs amount+1 times. Each cell does O(1) work. Total: **O(n × amount)**. No function call overhead, no recursion stack.

**Space Complexity — O(n × amount):**
Only the dp array of size n × (amount+1). No recursion stack.

## Approach 4 — Space Optimization (The Final Form)

Look at the recurrence:

```
dp[i][t] = dp[i-1][t]  +  dp[i][t - coins[i]]
            ↑                     ↑
        previous row          same row, to the left
```

Since we fill left to right, both values are correctly accessible from a single array:
- `prev[t]` before updating still holds the row i-1 value → correct for notTake.
- `prev[t - coins[i]]` (to the left) already holds the row i value (updated this pass) → correct for take.

So we update `prev` in place, left to right — one array, no extra curr needed.

```java
class Solution {
    public int change(int amount, int[] coins) {
        int n = coins.length;

        // prev[t] = number of ways to form target t using coins seen so far
        // Initialize with base case for index=0
        int[] prev = new int[amount + 1];

        // Base case: only coins[0] available
        for (int t = 0; t <= amount; t++) {
            prev[t] = (t % coins[0] == 0) ? 1 : 0;
        }

        // Fill from index=1 to n-1
        for (int i = 1; i < n; i++) {
            // Fill LEFT TO RIGHT — critical for correctness
            // WHY left to right: take case reads prev[t - coins[i]]
            //     which is to the left and already updated this pass
            //     → holds current row i value → same coin can be picked again
            //     Filling right to left would give 0/1 behavior (each coin once)
            for (int t = 0; t <= amount; t++) {

                // Not Take: prev[t] before updating = row i-1 value
                // WHY: we haven't written to position t yet in this left-to-right pass
                int notTake = prev[t];

                // Take: prev[t - coins[i]] to the left = already row i value
                // WHY: already updated earlier in this same left-to-right pass
                //      This correctly represents picking the same coin again
                int take = 0;
                if (coins[i] <= t) {
                    take = prev[t - coins[i]];
                }

                // Update in place — prev[t] now holds row i's answer
                prev[t] = notTake + take;
            }
        }

        return prev[amount];
    }
}
```

**Time Complexity — O(n × amount):**
Two nested loops — outer runs n-1 times, inner runs amount+1 times left to right. Each iteration does O(1) work. Total: **O(n × amount)**. Same as tabulation.

**Space Complexity — O(amount):**
No n × (amount+1) array. No recursion stack. Just one array of size amount+1. Memory is completely independent of n.

## Comparing All Three Unbounded Knapsack Problems So Far

| Problem | Step 3 Action | Base case at index 0 | Impossible sentinel |
|---|---|---|---|
| Classic Unbounded Knapsack | **max** (maximize value) | `(W / wt[0]) * val[0]` | `-1e9` |
| LC 322 Coin Change | **min** (minimize coins) | `t / coins[0]` if divisible, else `+1e9` | `+1e9` |
| LC 518 Coin Change II | **sum** (count ways) | `1` if divisible, else `0` | `0` |

The recurrence structure, the Unbounded thumb rule (stay at same index), and the left-to-right fill direction are **identical** across all three. Only Step 3 and the base case return value change.
