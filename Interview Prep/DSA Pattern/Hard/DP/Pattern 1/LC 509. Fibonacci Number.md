# LC 509. Fibonacci Number

---

# Stage 1: Identification

**Step 1 — Which topic?**

You are asked to find the nth Fibonacci number. The nth Fibonacci depends on the (n-1)th and (n-2)th Fibonacci. This means **the answer to a larger problem depends on answers to smaller versions of the same problem** — that is the hallmark of **Dynamic Programming**.

**Step 2 — Which pattern?**

Look at the input: a single number `n`. Look at what you're computing: a single value that depends on a few previous values. No grid, no two sequences, no tree — just a **single sequence** where each answer depends on a constant number of previous answers.

That is the clearest possible signal for **Pattern 1: 1D DP (Linear)**.

**Step 3 — Which key concept?**

The recurrence is `f(n) = f(n-1) + f(n-2)`. This is the **base template** of 1D DP — the simplest possible recurrence where the current state depends on the two immediately preceding states.

Every other 1D DP problem is a variation of this structure. Master this and you have the foundation.

---

# Stage 2: Intuition Building

### Why does naive recursion fail here?

Let's say you're asked for `f(5)`. You think — easy, just call `f(4) + f(3)`. And `f(4)` calls `f(3) + f(2)`. And so on.

Draw the recursion tree for `f(5)`:

```
                    f(5)
                  /      \
              f(4)          f(3)
             /    \        /    \
          f(3)   f(2)   f(2)   f(1)
         /   \   /  \   /  \
       f(2) f(1) f(1) f(0) f(1) f(0)
       /  \
     f(1) f(0)
```

Notice something deeply wrong here: **f(3) is computed twice. f(2) is computed three times.**

These are called **overlapping subproblems** — you are solving the same problem over and over. For `f(5)` it looks manageable. But for `f(50)`, the number of redundant calls explodes exponentially. Time complexity of pure recursion: **O(2^n)**. Completely impractical.

### The key insight — if a subproblem's answer never changes, why recompute it?

`f(2)` is always 1. No matter how many times you call it, the answer is always 1. So the first time you compute `f(2)`, **store the answer**. The next time someone asks for `f(2)`, just return the stored value instantly. No recomputation.

This idea — *store and reuse* — is the entire soul of Dynamic Programming.

### The three approaches Striver teaches

There are three levels of solving any DP problem. Each one builds on the previous:

```
Recursion + Memoization     →    Tabulation    →    Space Optimization
(Top-down, O(n) time,            (Bottom-up,        (O(1) space,
 O(n) space)                      O(n) time,         O(n) time)
                                  O(n) space,
                                  no recursion stack)
```

Let's walk through each one.

# Stage 3: Coding

## Approach 1 — Pure Recursion (Brute Force)

**The thinking:** Just write the recurrence directly. Trust the base cases.

```java
class Solution {
    public int fib(int n) {
        // Base cases: f(0) = 0, f(1) = 1
        if (n <= 1) return n;
        
        // Recurrence: f(n) = f(n-1) + f(n-2)
        return fib(n - 1) + fib(n - 2);
    }
}
```

**What's wrong:** For `n = 5`, `f(3)` is computed twice. For `n = 50`, the tree explodes. Same subproblem solved again and again.

| | Complexity | Reason |
|---|---|---|
| **Time** | O(2^n) | Every call spawns two more — exponential tree |
| **Space** | O(n) | Recursion stack depth goes up to n |

---

## Approach 2 — Memoization (Top-Down DP)

**The thinking:** Keep the recursion. But before computing anything, check: *have I solved this subproblem before?* If yes, return the stored answer. If no, compute it, store it, then return it.

**The 3 steps to convert any recursion to memoization:**

```
Step 0: Declare a dp array of size (n+1), initialize all to -1
        (-1 means "not yet computed")

Step 1: Before computing, check — if dp[n] != -1, return dp[n]
        (this is the "lookup" step)

Step 2: After computing, store — dp[n] = answer
        (this is the "store" step)
```

```java
class Solution {
    public int fib(int n) {
        // Step 0: Create dp array, -1 means not yet computed
        int[] dp = new int[n + 1];
        Arrays.fill(dp, -1);
        
        return solve(n, dp);
    }
    
    private int solve(int n, int[] dp) {
        // Base cases — same as pure recursion
        if (n <= 1) return n;
        
        // Step 1: If already computed, return stored value
        // WHY: f(2) is always 1 — no point recomputing it
        if (dp[n] != -1) return dp[n];
        
        // Step 2: Compute and store before returning
        // WHY: Store so future calls for same n are O(1)
        dp[n] = solve(n - 1, dp) + solve(n - 2, dp);
        
        return dp[n];
    }
}
```

**What the tree looks like now:**

```
f(5) → f(4) → f(3) → f(2) → f(1) [returns 1]
                              f(0) [returns 0]
                    dp[2] = 1, stored ✓
              f(1) [returns 1]
       dp[3] = 2, stored ✓
       f(2) → dp[2] already computed → returns 1 instantly ✓
  dp[4] = 3, stored ✓
  f(3) → dp[3] already computed → returns 2 instantly ✓
dp[5] = 5 ✓
```

Every subproblem solved exactly once. No redundant work.

| | Complexity | Reason |
|---|---|---|
| **Time** | O(n) | Each subproblem solved exactly once |
| **Space** | O(n) + O(n) | dp array + recursion call stack |

---

## Approach 3 — Tabulation (Bottom-Up DP)

**The thinking:** Flip the direction. Instead of starting from `f(n)` and going down to base cases, start from the base cases and build up to `f(n)`.

**The recipe to convert memoization to tabulation:**

```
Step 1: Same dp array, same size
Step 2: Write the base cases directly into the array
Step 3: Look at the recurrence — figure out which index it starts from
        (recurrence uses i-1 and i-2, so it's valid from i=2 onwards)
Step 4: Fill the array from that index up to n using the recurrence
```

```java
class Solution {
    public int fib(int n) {
        // Edge case: f(0) = 0, f(1) = 1
        if (n <= 1) return n;
        
        // Step 1: Declare dp array
        int[] dp = new int[n + 1];
        
        // Step 2: Fill base cases
        // WHY: These are the starting truths everything else builds on
        dp[0] = 0;
        dp[1] = 1;
        
        // Step 3: Fill from i=2 to n using the recurrence
        // WHY start from 2: recurrence needs i-1 and i-2,
        // both of which must already be filled
        for (int i = 2; i <= n; i++) {
            dp[i] = dp[i - 1] + dp[i - 2];
        }
        
        // Answer to the original problem
        return dp[n];
    }
}
```

**No recursion stack.** Everything is computed iteratively. Cleaner and uses less space than memoization.

| | Complexity | Reason |
|---|---|---|
| **Time** | O(n) | Single loop from 2 to n |
| **Space** | O(n) | dp array of size n+1 |

---

## Approach 4 — Space Optimization (The Final Form)

**The thinking:** Look at the recurrence: `dp[i] = dp[i-1] + dp[i-2]`.

To compute `dp[i]`, you only need the **previous two values**. You do not need the entire array. So why keep the entire array around?

```
At any point i, you only need:
    prev2  =  dp[i-2]
    prev1  =  dp[i-1]
    curr   =  dp[i]   =  prev1 + prev2

After computing curr, shift the window:
    prev2 = prev1
    prev1 = curr
    move to i+1
```

Visualizing the window sliding:

```
i=2:  prev2=dp[0]=0,  prev1=dp[1]=1,  curr = 0+1 = 1
      shift: prev2=1, prev1=1

i=3:  prev2=1, prev1=1, curr = 1+1 = 2
      shift: prev2=1, prev1=2

i=4:  prev2=1, prev1=2, curr = 1+2 = 3
      shift: prev2=2, prev1=3

i=5:  prev2=2, prev1=3, curr = 2+3 = 5
      answer = 5 ✓
```

```java
class Solution {
    public int fib(int n) {
        // Base cases
        if (n <= 1) return n;
        
        // Only two variables needed — no array at all
        int prev2 = 0;  // dp[0] = f(0)
        int prev1 = 1;  // dp[1] = f(1)
        
        for (int i = 2; i <= n; i++) {
            int curr = prev1 + prev2;
            // WHY: This is just the recurrence dp[i] = dp[i-1] + dp[i-2]
            //      written with variables instead of array indices
            
            // Slide the window forward
            prev2 = prev1;
            // WHY: What was dp[i-1] becomes dp[i-2] in the next iteration
            
            prev1 = curr;
            // WHY: What was just computed becomes dp[i-1] in the next iteration
        }
        
        // prev1 now holds dp[n] = f(n)
        return prev1;
    }
}
```

| | Complexity | Reason |
|---|---|---|
| **Time** | O(n) | Single loop, same as tabulation |
| **Space** | **O(1)** | Only two variables, no array |

---

## Final Comparison

| Approach | Time | Space | Notes |
|---|---|---|---|
| Pure Recursion | O(2^n) | O(n) | Exponential — never use |
| Memoization | O(n) | O(n) + O(n) stack | Good starting point in interview |
| Tabulation | O(n) | O(n) | Better — no recursion stack |
| Space Optimization | O(n) | **O(1)** | Best — submit this |

## The Key Takeaway for Pattern Recognition

```
┌─────────────────────────────────────────────────────────────┐
│  Signal for 1D DP:                                          │
│  Single sequence, answer at position i depends on a         │
│  CONSTANT number of previous positions.                     │
│                                                             │
│  The 3-step conversion from Recursion → Memoization:        │
│  Step 0: Declare dp array, fill with -1                     │
│  Step 1: Check dp[n] != -1 → return dp[n]  (lookup)         │
│  Step 2: dp[n] = computed answer            (store)         │
│                                                             │
│  Then: Memoization → Tabulation → Space Optimization        │
│  This 3-level progression is the template for every         │
│  1D DP problem that follows.                                │
└─────────────────────────────────────────────────────────────┘
```
