# LC 62. Unique Paths

---

# Stage 1: Identification

**Step 1 — Which topic?**

You are given an m × n grid. You start at the top-left cell (0, 0) and need to reach the bottom-right cell (m-1, n-1). You can only move **right** or **down**. You need to count the total number of unique paths.

The moment you see **"count the total number of unique paths"** — that is the signal. To count all ways, you must **try all possible ways**. And whenever you try all possible ways, **Recursion** is your first thought. And when that recursion has overlapping subproblems — it becomes **Dynamic Programming**.

**Step 2 — Which pattern?**

The input is a 2D grid. You have two changing parameters — the row index `i` and the column index `j`. The answer at any cell depends on answers from other cells in the grid.

That is **Pattern 3: 2D / Grid DP**.

**Step 3 — Which key concept?**

Apply Striver's **3-step shortcut** — but adapted for 2D:

```
Step 1: Express everything in terms of (i, j) — row and column index
Step 2: Do all possible things at (i, j) — explore all valid moves
Step 3: Question says count all ways → sum up all results
```

The key insight: instead of going **forward** from (0,0) to (m-1, n-1), go **backward** from (m-1, n-1) to (0, 0). At each cell you ask — how many ways can I reach here from (0,0)?

---

# Stage 2: Intuition Building

### The Problem Setup

```
m = 3, n = 3

(0,0) → → → (0,2)
  ↓           ↓
(1,0)       (1,2)
  ↓           ↓
(2,0) → → → (2,2)  ← destination
```

Only **right** and **down** moves are allowed. How many distinct paths from (0,0) to (2,2)?

### Step 1 — Represent in terms of (i, j)

Define:

```
f(i, j) = number of unique ways to reach (i, j) from (0, 0)
```

So the answer we want is `f(m-1, n-1)`.

Striver goes **top-down** — start from (m-1, n-1) and recurse backward. Since we can only move right or down going forward, going backward means we can only move **left** or **up**.

### Step 2 — Do all possible things at (i, j)

At any cell (i, j), we could have arrived from:
- The cell **above** → (i-1, j) (we moved down to get here)
- The cell to the **left** → (i, j-1) (we moved right to get here)

So:
```
f(i, j) = f(i-1, j) + f(i, j-1)
```

### Step 3 — Sum up because we are counting ways

We sum the results of both directions because every path from above AND every path from the left gives us a unique path to (i, j).

### Base Cases

**When do we return 1?**
When we reach (0, 0) — we have found a complete valid path. Count it.
```
if i == 0 AND j == 0 → return 1
```

**When do we return 0?**
When we go out of bounds — the row or column goes negative. That path is invalid.
```
if i < 0 OR j < 0 → return 0
```

### Visualizing the Recursion Tree (m=3, n=3)

```
f(2,2) asks → f(1,2) + f(2,1)

f(1,2) asks → f(0,2) + f(1,1)
f(2,1) asks → f(1,1) + f(2,0)
                ↑
           OVERLAP! f(1,1) computed twice
```

The more rows and columns you add, the more the overlapping explodes. For a 3×3 grid, f(1,1) is computed multiple times. For large grids this becomes completely unmanageable.

**Overlapping subproblems confirmed** → DP is needed.

### DP Table Size

Two parameters:
- `i`: ranges from 0 to m-1 → **m values**
- `j`: ranges from 0 to n-1 → **n values**

So we need an **m × n** dp table.

# Stage 3: Coding

## Approach 1 — Pure Recursion (Brute Force)

```java
class Solution {
    public int uniquePaths(int m, int n) {
        return solve(m - 1, n - 1);
    }

    private int solve(int i, int j) {
        // Base case: reached the starting cell — one valid path found
        if (i == 0 && j == 0) return 1;

        // Base case: went out of bounds — this is not a valid path
        if (i < 0 || j < 0) return 0;

        // Move came from above (moved down to reach here)
        int up = solve(i - 1, j);

        // Move came from left (moved right to reach here)
        int left = solve(i, j - 1);

        // Sum all ways — we are counting
        return up + left;
    }
}
```

**Time Complexity — O(2^(m+n)):**
At every cell, the function makes 2 recursive calls — one going up and one going left. The recursion tree is like a binary tree. The depth of the tree is the path length, which is (m-1) + (n-1). In the worst case, the total number of nodes in this tree grows as 2^(m+n). For m=n=100, this is astronomically large — completely impractical.

**Space Complexity — O(m+n):**
No dp array is allocated. But the **recursion call stack** holds frames. The deepest chain of calls goes from (m-1, n-1) all the way down to (0, 0). The path length is (m-1) + (n-1). That is how many frames are on the stack at once. So call stack uses O(m+n) space.

## Approach 2 — Memoization (Top-Down DP)

The same subproblems are solved repeatedly. For example, `f(1,1)` might be called from both `f(2,1)` and `f(1,2)`. Store each result the first time it is computed.

**3 steps to convert recursion to memoization:**
```
Step 0: Declare dp array of size m × n, initialize all to -1
Step 1: Before computing, check — if dp[i][j] != -1, return it   (lookup)
Step 2: After computing, store — dp[i][j] = result                (store)
```

```java
class Solution {
    public int uniquePaths(int m, int n) {
        // Step 0: dp[i][j] = -1 means not yet computed
        int[][] dp = new int[m][n];
        for (int[] row : dp) {
            Arrays.fill(row, -1);
        }
        return solve(m - 1, n - 1, dp);
    }

    private int solve(int i, int j, int[][] dp) {
        // Base case: reached origin — one valid path
        if (i == 0 && j == 0) return 1;

        // Base case: out of bounds — invalid path
        if (i < 0 || j < 0) return 0;

        // Step 1: Already computed? Return stored value instantly
        // WHY: f(1,1) = ways to reach (1,1) from (0,0) — this never changes.
        //      No reason to recompute it.
        if (dp[i][j] != -1) return dp[i][j];

        int up   = solve(i - 1, j, dp);
        int left = solve(i, j - 1, dp);

        // Step 2: Store before returning
        // WHY: Next time solve(i, j) is called, answer is ready in O(1)
        dp[i][j] = up + left;
        return dp[i][j];
    }
}
```

**Time Complexity — O(m × n):**
Without memoization, the same cell like (1,1) might be recomputed many times. With memoization, each unique (i, j) pair is computed **exactly once**. There are m × n unique cells. For each cell, we do O(1) work — just add up and left. Total: O(m × n).

**Space Complexity — O(m × n) + O(m + n):**
Two sources of space. First, the dp array of size m × n — that is O(m×n). Second, the **recursion call stack** — even with memoization, the first chain of calls still goes (m-1)+(n-1) levels deep. So stack uses another O(m+n). Total: O(m×n) + O(m+n).

## Approach 3 — Tabulation (Bottom-Up DP)

Flip the direction. Instead of starting from (m-1, n-1) and going backward, start from (0, 0) and build forward. No recursion stack at all.

**What does bottom-up mean here?**
In recursion (top-down), you start at (m-1, n-1), go **down** into smaller subproblems, and accumulate answers on the way back up.

In tabulation (bottom-up), you start at (0, 0) — the base case — and **build upward** to (m-1, n-1). You fill small answers first and use them to fill bigger answers.

**The recipe:**
```
Step 1: Declare dp array of size m × n
Step 2: Fill base case — dp[0][0] = 1
Step 3: Express all states in nested for loops
Step 4: Copy the recurrence — dp[i][j] = up + left
        (handle out-of-bounds by treating them as 0)
```

```java
class Solution {
    public int uniquePaths(int m, int n) {
        int[][] dp = new int[m][n];

        for (int i = 0; i < m; i++) {
            for (int j = 0; j < n; j++) {

                // Base case: origin has exactly 1 way to reach itself
                if (i == 0 && j == 0) {
                    dp[i][j] = 1;
                    continue;
                }

                // How many ways came from above?
                // WHY check i > 0: if i == 0, there is no row above
                int up = 0;
                if (i > 0) up = dp[i - 1][j];

                // How many ways came from the left?
                // WHY check j > 0: if j == 0, there is no column to the left
                int left = 0;
                if (j > 0) left = dp[i][j - 1];

                // Total ways to reach (i, j)
                dp[i][j] = up + left;
            }
        }

        // Answer: total ways to reach bottom-right corner
        return dp[m - 1][n - 1];
    }
}
```

**Dry Run (m=3, n=3):**
```
Fill row by row, left to right:

i=0: dp[0][0]=1,  dp[0][1]=0+1=1,  dp[0][2]=0+1=1
i=1: dp[1][0]=1+0=1, dp[1][1]=1+1=2, dp[1][2]=1+2=3
i=2: dp[2][0]=1+0=1, dp[2][1]=1+2=3, dp[2][2]=3+3=6

Answer = dp[2][2] = 6 ✓

Grid looks like:
1  1  1
1  2  3
1  3  6
```

**Time Complexity — O(m × n):**
Two nested for loops — outer runs m times, inner runs n times. Each cell does O(1) work. Total: O(m × n). Same as memoization but no function call overhead and no recursion stack.

**Space Complexity — O(m × n):**
Only the dp array of size m × n. No recursion stack whatsoever. Already an improvement over memoization.

## Approach 4 — Space Optimization (The Final Form)

Look at the tabulation code carefully:

```
dp[i][j] = dp[i-1][j] + dp[i][j-1]
```

To compute any cell in row `i`, you only ever look at:
- The cell **directly above** from row `i-1` → `dp[i-1][j]`
- The cell **to the left** in the same row → `dp[i][j-1]`

You never need rows before `i-1`. So why keep the entire m × n array?

**The key observation:**
When computing row `i`, you only need row `i-1`. After computing row `i`, row `i-1` is never needed again.

So keep just **one array of size n** representing the previous row. Compute the current row into a temporary array of size n. Then slide forward — make temp the new previous.

```
Visualizing the sliding:

Row 0 (prev): [1, 1, 1]
                         ← used to compute row 1

Row 1 (curr): [1, 2, 3]
                         ← curr becomes new prev

Row 2 (curr): [1, 3, 6]

Answer = curr[n-1] = 6
```

```java
class Solution {
    public int uniquePaths(int m, int n) {
        // prev[j] = number of ways to reach (previous row, j)
        // Initialize as all zeros
        int[] prev = new int[n];

        for (int i = 0; i < m; i++) {
            // curr[j] = number of ways to reach (current row i, column j)
            int[] curr = new int[n];

            for (int j = 0; j < n; j++) {
                // Base case: origin
                if (i == 0 && j == 0) {
                    curr[j] = 1;
                    continue;
                }

                // Ways coming from above (previous row, same column)
                // WHY prev[j]: prev holds the previous row's answers
                int up = 0;
                if (i > 0) up = prev[j];

                // Ways coming from left (same row, previous column)
                // WHY curr[j-1]: we already computed this cell in current row
                int left = 0;
                if (j > 0) left = curr[j - 1];

                curr[j] = up + left;
            }

            // Slide forward: current row becomes the new previous row
            // WHY: When i increases by 1, what was 'curr' becomes 'prev'
            prev = curr;
        }

        // prev now holds the last computed row (row m-1)
        // Answer is at the last column
        return prev[n - 1];
    }
}
```

**Time Complexity — O(m × n):**
Still two nested loops with the same iteration count. No change in time complexity — O(m × n).

**Space Complexity — O(n):**
No m × n array. No recursion stack. Just two arrays of size n — `prev` and `curr` — regardless of how large m is. Whether m is 3 or 3 million, the memory used depends only on n. That is O(n).

## Final Comparison

| Approach | Time | Space | Notes |
|---|---|---|---|
| Pure Recursion | O(2^(m+n)) | O(m+n) stack | Exponential — never use |
| Memoization | O(m × n) | O(m×n) + O(m+n) stack | Good interview starting point |
| Tabulation | O(m × n) | O(m × n) | Better — eliminates stack |
| Space Optimization | O(m × n) | **O(n)** | Best — submit this |
