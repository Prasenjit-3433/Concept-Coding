# LC 64. Minimum Path Sum

---

# Stage 1: Identification

**Step 1 — Which topic?**

You are given an m × n grid filled with non-negative integers. You start at (0, 0) and need to reach (m-1, n-1). You can only move **right** or **down**. Find the path that gives the **minimum sum** of all numbers along the way.

The moment you see **"find the minimum among all possible paths"** — that is the signal. To find the minimum, you must **try all possible paths** and pick the best. And whenever you try all possible paths, **Recursion** is your first thought. And when that recursion has overlapping subproblems — it becomes **Dynamic Programming**.

**Why doesn't Greedy work here?**

Consider this grid:
```
10  8
2  100
```

Greedy from (0,0): move right to 8 (smaller than 2 below), then down to 100. Total = 10 + 8 + 100 = 118.

But the optimal path: move down to 2, then right to 100... wait, both paths hit 100 here. Let's try another:

```
1   1   100
1   100   1
100   1   1
```

Greedy would go right (1), right (100) and get stuck with huge cost. Optimal path goes down, down, right, right, up which doesn't exist since only right/down are allowed — but going down first always beats going right first here. The point is: **what looks cheap now may force you into an expensive cell later.** There is no uniformity guarantee in the values. You must try all paths.

**Step 2 — Which pattern?**

Input is a 2D grid. Two changing parameters — row index `i` and column index `j`. The answer at any cell depends on answers from neighboring cells above and to the left.

That is **Pattern 3: 2D / Grid DP**.

**Step 3 — Which key concept?**

Apply Striver's 3-step shortcut adapted for 2D:

```
Step 1: Express in terms of (i, j)
Step 2: Explore all moves — going backward means up and left
Step 3: Question says minimum → take min of all results
```

The only difference from LC 62 (count ways) and LC 63 (count ways with obstacles) is **Step 3** — instead of summing, we take the **minimum**.

# Stage 2: Intuition Building

### The Problem Setup

```
grid = [
  [1, 3, 1],
  [1, 5, 1],
  [4, 2, 1]
]
```

You want the path from (0,0) to (2,2) with the smallest sum.

```
Possible paths (right/down only):
1→3→1→1→1 = 7
1→3→5→1→1 = 11  ← not minimum
1→1→5→1→1 = 9   ← also not minimum
1→1→4→2→1 = 9   ← not minimum
1→3→1→1→1 = 7   ← minimum path
1→1→1→1→1 = ... wait, let's verify:
  Right, Right, Down, Down: 1→3→1→1→1 = 7 ✓
  Down, Right, Right, Down: 1→1→5→1→1 = 9
  Down, Down, Right, Right: 1→1→4→2→1 = 8

Answer = 7
```

### Step 1 — Represent in terms of (i, j)

Define:
```
f(i, j) = minimum cost to reach (i, j) from (0, 0)
```

So the answer we want is `f(m-1, n-1)`.

Going **top-down** (Striver's style): start from (m-1, n-1) and recurse backward. Since the forward moves are right and down, going backward means **up** and **left**.

### Step 2 — Do all possible things at (i, j)

From (i, j), we could have arrived from:
- **Above** → (i-1, j): someone moved down to reach us
- **Left** → (i, j-1): someone moved right to reach us

At the current cell, we always add `grid[i][j]` to our path cost — the current cell is part of every path that passes through it.

```
f(i, j) = grid[i][j] + min(f(i-1, j), f(i, j-1))
```

### Step 3 — Take minimum

We take the **minimum** because the question asks for the minimum path sum. This is the only structural difference from LC 62 where we summed (because we were counting all ways, not optimizing).

### Base Cases

**When do we return `grid[0][0]`?**
When we reach the origin (0, 0). The origin cell itself is always part of the path, so we include its cost.
```
if i == 0 AND j == 0 → return grid[0][0]
```

**When do we return infinity?**
When we go out of bounds. We're looking for the minimum, so an out-of-bounds path must be so expensive it's never chosen. Return `Integer.MAX_VALUE` (or a very large number like 1e9) so the `min()` never picks it.
```
if i < 0 OR j < 0 → return Integer.MAX_VALUE
```

This is the critical difference from counting problems (where out-of-bounds returns 0). Here out-of-bounds must return something that makes the path **unattractive** — so infinity.

### Visualizing the Recursion (3×3 grid)

```
f(2,2) = grid[2][2] + min(f(1,2), f(2,1))
              1      + min(  ?  ,    ?  )

f(1,2) = grid[1][2] + min(f(0,2), f(1,1))
f(2,1) = grid[2][1] + min(f(1,1), f(2,0))
                               ↑
                       OVERLAP: f(1,1) called from both
```

**Overlapping subproblems confirmed** → DP is needed.

### DP Table Size

Two parameters, same as before:
- `i`: 0 to m-1 → **m values**
- `j`: 0 to n-1 → **n values**

dp table: **m × n**

# Stage 3: Coding

## Approach 1 — Pure Recursion (Brute Force)

```java
class Solution {
    public int minPathSum(int[][] grid) {
        int m = grid.length;
        int n = grid[0].length;
        return solve(m - 1, n - 1, grid);
    }

    private int solve(int i, int j, int[][] grid) {
        // Base case: out of bounds
        // Return a very large value so min() never picks this path
        // WHY not 0: returning 0 would make out-of-bounds paths look free,
        //            and they'd always be chosen incorrectly as the minimum
        if (i < 0 || j < 0) return Integer.MAX_VALUE;

        // Base case: reached origin — include this cell's cost
        // WHY grid[0][0]: origin is always part of the path
        if (i == 0 && j == 0) return grid[0][0];

        // Came from above (moved down to reach here)
        int up = solve(i - 1, j, grid);

        // Came from left (moved right to reach here)
        int left = solve(i, j - 1, grid);

        // Current cell cost + minimum of both incoming paths
        return grid[i][j] + Math.min(up, left);
    }
}
```

**Time Complexity — O(2^(m+n)):**
At every cell, the function makes 2 recursive calls. The recursion tree is binary with depth (m-1)+(n-1). The total number of nodes in this tree grows as 2^(m+n). For a 100×100 grid, this is completely impractical.

**Space Complexity — O(m+n):**
No dp array is allocated. The **recursion call stack** holds one frame per level. The deepest chain goes from (m-1, n-1) all the way back to (0, 0) — that is (m-1)+(n-1) frames deep. Stack uses O(m+n) space.

## Approach 2 — Memoization (Top-Down DP)

The same cell like (1,1) is computed multiple times across different branches. Store the result the first time it is computed.

```java
class Solution {
    public int minPathSum(int[][] grid) {
        int m = grid.length;
        int n = grid[0].length;

        // dp[i][j] = -1 means not yet computed
        int[][] dp = new int[m][n];
        for (int[] row : dp) {
            Arrays.fill(row, -1);
        }
        return solve(m - 1, n - 1, grid, dp);
    }

    private int solve(int i, int j, int[][] grid, int[][] dp) {
        // Base case: out of bounds
        // Return very large value — min() will never pick this
        if (i < 0 || j < 0) return Integer.MAX_VALUE;

        // Base case: reached origin
        if (i == 0 && j == 0) return grid[0][0];

        // Step 1: Already computed? Return stored value instantly
        // WHY: f(1,1) = min cost to reach (1,1) from (0,0)
        //      This never changes no matter when you call it
        if (dp[i][j] != -1) return dp[i][j];

        int up   = solve(i - 1, j, grid, dp);
        int left = solve(i, j - 1, grid, dp);

        // Step 2: Store before returning
        dp[i][j] = grid[i][j] + Math.min(up, left);
        return dp[i][j];
    }
}
```

**Time Complexity — O(m × n):**
Each unique (i, j) pair is computed exactly once. There are m × n unique cells. For each cell, O(1) work is done — one min(), one addition. Total: O(m × n).

**Space Complexity — O(m × n) + O(m + n):**
Two sources of space. First, the dp array of size m × n. Second, the recursion call stack which goes (m-1)+(n-1) levels deep. Total: O(m×n) + O(m+n).

## Approach 3 — Tabulation (Bottom-Up DP)

No recursion stack. Start from (0, 0) and build forward to (m-1, n-1).

**One important difference from LC 62:**
In LC 62, out-of-bounds returned 0 (didn't add anything to the count). Here, out-of-bounds should effectively be ignored — we model this by initializing `up` and `left` to `Integer.MAX_VALUE` and only assigning them when the index is valid.

But there is a subtle overflow trap: if `up = Integer.MAX_VALUE` and we do `grid[i][j] + up`, we get integer overflow. So use a large safe value like `(int) 1e9` instead.

```java
class Solution {
    public int minPathSum(int[][] grid) {
        int m = grid.length;
        int n = grid[0].length;
        int[][] dp = new int[m][n];

        for (int i = 0; i < m; i++) {
            for (int j = 0; j < n; j++) {

                // Base case: origin
                if (i == 0 && j == 0) {
                    dp[i][j] = grid[0][0];
                } else {
                    // Cost coming from above
                    // WHY (int)1e9 when out of bounds: we want this to be
                    // so expensive that min() always prefers a valid path.
                    // Using Integer.MAX_VALUE risks overflow when we add grid[i][j]
                    int up   = (i > 0) ? dp[i - 1][j] : (int) 1e9;
                    int left = (j > 0) ? dp[i][j - 1] : (int) 1e9;

                    dp[i][j] = grid[i][j] + Math.min(up, left);
                }
            }
        }

        return dp[m - 1][n - 1];
    }
}
```

**Dry Run (3×3 grid):**
```
grid:               dp filled row by row:
[1, 3, 1]
[1, 5, 1]           i=0: dp[0][0]=1,    dp[0][1]=1+3=4,    dp[0][2]=4+1=5
[4, 2, 1]
                    i=1: dp[1][0]=1+1=2, dp[1][1]=min(4,2)+5=7, dp[1][2]=min(5,7)+1=6

                    i=2: dp[2][0]=2+4=6, dp[2][1]=min(7,6)+2=8, dp[2][2]=min(6,8)+1=7

Answer = dp[2][2] = 7 ✓
```

**Time Complexity — O(m × n):**
Two nested for loops, each cell visited exactly once with O(1) work. Total: O(m × n). No function call overhead, no recursion stack.

**Space Complexity — O(m × n):**
Only the dp array of size m × n. No recursion stack at all.

## Approach 4 — Space Optimization (The Final Form)

Same observation as LC 62 and LC 63:

```
dp[i][j] = grid[i][j] + min(dp[i-1][j], dp[i][j-1])
```

To compute row `i`, we only need row `i-1`. So keep just one array of size n for the previous row, and compute each current row into a fresh array of size n.

```java
class Solution {
    public int minPathSum(int[][] grid) {
        int m = grid.length;
        int n = grid[0].length;

        // prev[j] = minimum cost to reach (previous row, column j)
        int[] prev = new int[n];

        for (int i = 0; i < m; i++) {
            // curr[j] = minimum cost to reach (current row i, column j)
            int[] curr = new int[n];

            for (int j = 0; j < n; j++) {
                if (i == 0 && j == 0) {
                    curr[j] = grid[0][0];
                } else {
                    // Cost from above: previous row, same column
                    // WHY prev[j]: prev holds previous row's answers
                    // WHY 1e9 when i == 0: row 0 has no row above it
                    int up   = (i > 0) ? prev[j] : (int) 1e9;

                    // Cost from left: same row, previous column
                    // WHY curr[j-1]: already computed this iteration
                    // WHY 1e9 when j == 0: column 0 has no column to the left
                    int left = (j > 0) ? curr[j - 1] : (int) 1e9;

                    curr[j] = grid[i][j] + Math.min(up, left);
                }
            }

            // Slide forward: current row becomes new previous row
            // WHY: next iteration needs this row as its "above"
            prev = curr;
        }

        // prev now holds the last computed row (row m-1)
        return prev[n - 1];
    }
}
```

**Time Complexity — O(m × n):**
Two nested loops, same iteration count as tabulation. Each cell does O(1) work. Total: O(m × n).

**Space Complexity — O(n):**
No m × n array. No recursion stack. Just two arrays of size n — `prev` and `curr`. Memory depends only on the number of columns.

## Final Comparison

| Approach | Time | Space | Notes |
|---|---|---|---|
| Pure Recursion | O(2^(m+n)) | O(m+n) stack | Exponential — never use |
| Memoization | O(m × n) | O(m×n) + O(m+n) stack | Good interview starting point |
| Tabulation | O(m × n) | O(m × n) | Better — eliminates stack |
| Space Optimization | O(m × n) | **O(n)** | Best — submit this |

## Comparing All Three Grid DP Problems So Far

| Problem | Step 3 Action | Out-of-bounds returns | Base case at (0,0) |
|---|---|---|---|
| LC 62 Unique Paths | **Sum** (counting ways) | 0 | 1 |
| LC 63 Unique Paths II | **Sum** + obstacle → 0 | 0 | 1 (if no obstacle) |
| LC 64 Minimum Path Sum | **Min** (optimizing cost) | 1e9 (large) | grid[0][0] |

This table is the heart of the pattern. The recurrence structure is identical across all three. What changes is Step 3 (sum vs min) and what out-of-bounds returns (0 for counting, large for minimizing).

## The Key Takeaway

```
┌──────────────────────────────────────────────────────────────────┐
│  The 3-step shortcut for all Grid DP problems:                   │
│                                                                  │
│  Step 1: Express in terms of (i, j)                              │
│  Step 2: Explore — backward means up and left                    │
│  Step 3: Count → sum | Minimum → min | Maximum → max             │
│                                                                  │
│  What out-of-bounds should return:                               │
│  Counting problems → 0  (don't add invalid paths to count)       │
│  Minimizing problems → very large number (1e9)                   │
│                          (make invalid paths unattractive)       │
│  Maximizing problems → very small number (-1e9)                  │
│                          (make invalid paths unattractive)       │
│                                                                  │
│  What (0,0) base case should return:                             │
│  Counting → 1 (one valid path reaches origin)                    │
│  Optimizing → grid[0][0] (origin cell is always in the path)     │
│                                                                  │
│  Space optimization rule: whenever dp[i][j] uses only            │
│  dp[i-1][j] and dp[i][j-1], replace m×n array with               │
│  two arrays of size n (prev and curr).                           │
└──────────────────────────────────────────────────────────────────┘
```
