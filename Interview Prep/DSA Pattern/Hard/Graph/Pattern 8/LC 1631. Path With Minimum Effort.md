# LC 1631. Path With Minimum Effort

---

## Stage 1: Identification

**Step 1 — Which topic?**

You're given a 2D grid where you move between adjacent cells (top-left to bottom-right), and the "cost" of a move is defined by height differences. Movement between adjacent cells on a grid is always an implicit graph problem. Topic: **Graph**.

**Step 2 — Which pattern?**

The problem asks for a route that minimizes the **maximum absolute difference** encountered along the path — not the sum of differences. The keyword combination is:

> "minimum effort", "route", "source to destination", weighted movement → shortest-path family → **Dijkstra** (Pattern 8)

The trigger Striver uses explicitly: *whenever you hear shortest path / minimum path between a source and destination, Dijkstra is the first algorithm to try.*

**Step 3 — Which key concept?**

**`Dijkstra with a redefined edge weight — minimizing the path's maximum edge, not the path's sum`**

This is the real insight of the problem. Standard Dijkstra minimizes **sum of edge weights** along a path. Here, a path's "cost" (called *effort*) is defined completely differently:

```
effort(path) = max(|height[cell_i] - height[cell_i+1]|) over every consecutive pair in the path
```

You are not summing anything — you're taking the **maximum single-step jump** in the whole path, and you want the path that makes this maximum as small as possible. This is sometimes called a **minimax path** problem. The algorithm structure stays identical to Dijkstra; only the **relaxation formula** changes.

---

## Stage 2: Intuition Building

### The Core Question

Before touching any code, ask:

> *"When I extend a known path to a new cell, what does the new path's effort become?"*

If the effort so far (getting to the current cell) is `E`, and the new step to the neighbour has an absolute height difference of `D`, then the effort of the extended path is:

```
new_effort = max(E, D)
```

Not `E + D`. Not `D` alone. The **whole path's effort is decided by its single worst step** — everything else is irrelevant. This is the fundamental shift from standard Dijkstra:

```
┌───────────────────────────────────────────────────────────────┐
│  Standard Dijkstra:  new_dist = dist[curr] + edgeWeight       │
│  This problem:        new_effort = max(effort[curr], D)       │
│                                                               │
│  Both are still "path cost so far, extended by one more       │
│  step" — only the combining operation changes: + becomes max  │
└───────────────────────────────────────────────────────────────┘
```

### Why Does Dijkstra's Greedy Guarantee Still Hold?

Dijkstra's core promise is: *"once you pop the minimum-effort cell from the priority queue, its effort value is final — it can never improve later."* Does that promise survive when we swap `+` for `max`?

Yes — and here's why, reasoned from first principles. All height differences are non-negative (they're absolute values). So `max(E, D) >= E` always — extending a path can never *decrease* its effort, only keep it the same or increase it. This is the exact same non-negativity property that makes standard Dijkstra correct (`dist + weight >= dist` since weight ≥ 0). Since the "combine" operation is monotonic and never decreases, popping the minimum from the priority queue still guarantees that value is final. **Once you pop the destination cell, you are guaranteed it holds the true minimum possible effort** — no future path can ever produce something smaller, because every future exploration only sees effort values that are equal or larger from this point onward.

```
┌───────────────────────────────────────────────────────────────┐
│  Dijkstra requires: combining an edge with a path never       │
│  makes the path "cheaper."                                    │
│                                                               │
│  Sum version:  dist + weight ≥ dist         (weight ≥ 0)      │
│  Max version:  max(effort, D) ≥ effort      (D ≥ 0)           │
│                                                               │
│  Both hold → Dijkstra's greedy correctness carries over       │
│  unchanged. Only the update formula is different.             │
└───────────────────────────────────────────────────────────────┘
```

### Early Termination — The Moment You Pop the Destination

Since the priority queue always pops the minimum-effort cell next, the moment the destination cell is popped, you know for certain no smaller effort will ever be found for it later. You can **return immediately** instead of draining the entire queue. This is the same early-exit reasoning used any time Dijkstra's destination is a single fixed target rather than "all nodes."

### No Explicit Adjacency List — Grid Deltas Again

Same technique as LC 1091: since moves are only in 4 directions (no diagonals this time — the problem doesn't allow them), generate neighbours on the fly:

```
dr = [-1, 0, 1, 0]
dc = [0, 1, 0, -1]
```

### The Key Insight to Carry

```
┌───────────────────────────────────────────────────────────────┐
│  This is Dijkstra, with ONE formula change:                   │
│                                                               │
│  Standard:  if dist[curr] + wt < dist[adjNode]                │
│  Here:      if max(effort[curr], |h[curr]-h[adj]|)            │
│                  < effort[adjNode]                            │
│                                                               │
│  Why still correct? Because max(...) ≥ effort[curr] always    │
│  (heights differences are non-negative), preserving the       │
│  exact non-negativity property Dijkstra's greedy relies on.   │
│                                                               │
│  Early exit the moment destination is POPPED — its effort     │
│  is guaranteed final at that point.                           │
└───────────────────────────────────────────────────────────────┘
```

## Stage 3: Coding

### Brute Force

> "Try every path from (0,0) to (n-1,m-1) via DFS/backtracking. For each complete path, compute its effort (max absolute difference along the way). Return the minimum across all paths."

- Explore all 4 directions recursively, track max difference so far, backtrack
- Exponential — paths can revisit combinatorially many routes even with a visited set per-path, worst case `O(4^(n*m))`
- Correct but impractical. Establishes the baseline only. No code needed.

---

### Better — Binary Search on the Answer + BFS/DFS Feasibility Check

Worth a brief mention since it's a well-known alternate approach for this exact problem (though not what Striver's transcript covers): binary search on the possible effort value `E`, and for each candidate `E`, check via BFS/DFS whether a path exists using only edges with difference `≤ E`. This works because "can we reach the destination using effort ≤ E" is monotonic in `E`. Complexity: `O(n*m*log(maxHeight))`. We won't code this — Dijkstra is the intended and cleaner approach here, matching the pattern sheet's Key Concept.

---

### Optimal — Dijkstra with Max-Based Relaxation

**Mental workflow before writing a single line:**

```
1. n = rows, m = columns
2. effort[][] = 2D array, initialized to (int)1e9 for every cell
   effort[0][0] = 0   (source needs zero effort to reach itself)

3. minHeap seeded with (0, 0, 0)  → (effort=0, row=0, col=0)

4. Dijkstra loop:
   → pop (currEffort, row, col)
   → if (row, col) == destination → return currEffort   (EARLY EXIT)
   → for each of the 4 directions (dr[]/dc[]):
       newRow = row + dr[i], newCol = col + dc[i]
       if in bounds:
          D = |heights[row][col] - heights[newRow][newCol]|
          newEffort = max(currEffort, D)
          if newEffort < effort[newRow][newCol]:
             effort[newRow][newCol] = newEffort
             push (newEffort, newRow, newCol) into minHeap

5. (Fallback — won't be hit since grid is always fully connected)
   return effort[n-1][m-1]
```

```java
import java.util.*;

class Solution {

    // Pair class: bundles effort and coordinates together.
    // Implements Comparable so PriorityQueue orders by
    // effort automatically — smallest effort surfaces first.
    static class Cell implements Comparable<Cell> {
        int effort;
        int row;
        int col;

        Cell(int effort, int row, int col) {
            this.effort = effort;
            this.row = row;
            this.col = col;
        }

        public int compareTo(Cell other) {
            return Integer.compare(this.effort, other.effort);
        }
    }

    public int minimumEffortPath(int[][] heights) {
        int n = heights.length;
        int m = heights[0].length;

        // effort[][] tracks the minimum possible "path effort"
        // (max absolute height difference so far) to reach each cell.
        // (int)1e9 as infinity — same overflow-safety reasoning as always.
        int[][] effort = new int[n][m];
        for (int[] row : effort) {
            Arrays.fill(row, (int) 1e9);
        }

        // Source needs zero effort to "reach" itself
        effort[0][0] = 0;

        // Min-heap ordered by effort — always explore the
        // currently cheapest-effort cell next
        PriorityQueue<Cell> minHeap = new PriorityQueue<>();
        minHeap.add(new Cell(0, 0, 0));

        // 4-directional deltas (no diagonals in this problem)
        int[] dr = {-1, 0, 1, 0};
        int[] dc = {0, 1, 0, -1};

        while (!minHeap.isEmpty()) {
            Cell curr = minHeap.poll();
            int currEffort = curr.effort;
            int row = curr.row;
            int col = curr.col;

            // EARLY EXIT: the moment the destination is popped,
            // its effort value is guaranteed final. Dijkstra's
            // greedy property holds because max(...) never
            // decreases a path's effort — heights differences
            // are always non-negative.
            if (row == n - 1 && col == m - 1) {
                return currEffort;
            }

            for (int i = 0; i < 4; i++) {
                int newRow = row + dr[i];
                int newCol = col + dc[i];

                // Bounds check
                if (newRow < 0 || newRow >= n || newCol < 0 || newCol >= m) {
                    continue;
                }

                // The "edge weight" — absolute height difference
                int diff = Math.abs(heights[row][col] - heights[newRow][newCol]);

                // KEY FORMULA CHANGE from standard Dijkstra:
                // extending the path takes the MAX of the
                // effort so far and this new step's difference —
                // not the SUM.
                int newEffort = Math.max(currEffort, diff);

                // Relaxation condition — same shape as always,
                // just with the redefined newEffort
                if (newEffort < effort[newRow][newCol]) {
                    effort[newRow][newCol] = newEffort;
                    minHeap.add(new Cell(newEffort, newRow, newCol));
                }
            }
        }

        // Fallback — grid is always connected in this problem,
        // so this line is never actually reached
        return effort[n - 1][m - 1];
    }
}
```

## Complexity Analysis

### Time Complexity — O(n·m·log(n·m))

The grid has `n × m` cells, so total nodes `V = n·m`. Each cell has exactly 4 possible edges (up/down/left/right), so total edges `E ≈ 4·n·m = O(n·m)`. This is standard Dijkstra complexity: `O(E log V)`.

```
V = n·m
E = 4·n·m → O(n·m)

Total: O(E log V) = O(n·m · log(n·m))
```

Each successful relaxation triggers one heap push, costing `O(log(heap size))`, and heap size is bounded by `O(E) = O(n·m)`. So `log(n·m)` per operation, across `O(n·m)` relaxations in the worst case.

### Space Complexity — O(n·m)

```
effort[][] array   → O(n·m)
minHeap            → O(n·m) worst case (one entry per cell relaxation)
─────────────────────────────
Total: O(n·m)
```

No explicit adjacency list is stored (grid neighbours generated on the fly via `dr[]`/`dc[]`), so there's no separate `O(V+E)` adjacency term like in explicit-graph Dijkstra problems.
