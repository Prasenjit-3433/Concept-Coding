# LC 1976. Number of Ways to Arrive at Destination

---

## Stage 1: Identification

**Step 1 — Which topic?**

You're given cities (intersections) connected by roads with travel times, and you want to know something about the shortest route between a fixed source and a fixed destination. Cities as nodes, roads as weighted undirected edges — this is a **weighted graph**. Topic: **Graph**.

**Step 2 — Which pattern?**

The keyword "shortest amount of time" immediately triggers **Dijkstra** (Pattern 8) — weighted graph, non-negative edge weights, minimum cost from a source. But look closer at what's actually being asked:

> Not "what is the shortest time" — but **"in how many distinct ways can you achieve that shortest time?"**

This is a new flavor within Pattern 8 that hasn't come up yet: **Dijkstra + Counting**, where the algorithm doesn't just track the minimum distance to each node, it also tracks *how many distinct shortest paths* reach each node.

**Step 3 — Which key concept?**

**`Dijkstra with a Parallel "Ways" Array — Counting Shortest Paths via Predecessor Summation`**

The core mechanism: alongside `dist[]`, maintain a `ways[]` array. Every time you discover a node via an edge that matches its current shortest distance exactly, you don't overwrite the count — you **add** to it. Every time you discover a *strictly better* distance, you **reset and inherit** the count from the node you came from. This is structurally similar to the "parent array" trick from path reconstruction, except instead of remembering *one* parent, you're summing contributions from *every* predecessor that lies on some shortest path.

---

## Stage 2: Intuition Building

### The Wrong Instinct — and Why It's Wrong

The first instinct most people have: *"If three different edges lead into the destination and all three give the shortest distance, the answer is 3."*

This is wrong, and the reason is genuinely important — not just a technicality.

Imagine a node `X` is reached via two completely different shortest paths (2 ways to reach `X`). Now `X` has one single edge leading into the destination that also happens to lie on the shortest path. If you just count "1 edge = 1 way," you'd say "1 way arrives via `X`." But that's wrong — `X` itself was reachable in 2 different ways, so anything that goes *through* `X` inherits **both** of those ways.

```
┌────────────────────────────────────────────────────────────────┐
│  Counting shortest paths is NOT "count how many edges point    │
│  into the destination on a shortest path."                     │
│                                                                │
│  It's: "count how many ways EACH predecessor was reached,      │
│  and SUM those counts forward."                                │
│                                                                │
│  ways[destination] = Σ ways[u]  for every u whose edge to      │
│                       destination lies on a shortest path      │
└────────────────────────────────────────────────────────────────┘
```

This is the exact same idea as counting paths in a DAG using DP: `ways[node] = sum of ways[predecessor]` over every predecessor that contributes to the shortest route. Dijkstra just gives you the *order* in which to process nodes so that every predecessor's `ways[]` value is finalized before you use it.

---

### The Core Rule — Two Situations When Relaxing an Edge

You're at node `curr`, popped with its now-finalized `dist[curr]` and `ways[curr]`. You look at a neighbour `adjNode` via an edge of weight `adjWt`. Ask:

> *"Does going through `curr` change what I know about `adjNode`?"*

There are exactly two situations that matter (a third — the edge makes things worse — is simply discarded, same as always):

**Situation 1 — Strictly Better Distance Found**

```
if (dist[curr] + adjWt < dist[adjNode]):
    dist[adjNode] = dist[curr] + adjWt
    ways[adjNode] = ways[curr]     ← RESET, don't add
```

This is the first time (or a strictly better time) `adjNode` has been reached. Every previous count for `adjNode` is now obsolete — it belonged to a *longer* path that no longer matters. So you don't add to the old count, you **overwrite** it entirely with whatever `curr` brought.

**Situation 2 — Equal Distance Found (a second shortest path discovered)**

```
if (dist[curr] + adjWt == dist[adjNode]):
    ways[adjNode] += ways[curr]     ← ADD, don't overwrite
```

This is the situation the wrong instinct misses. `adjNode` was *already* known to be reachable in `dist[adjNode]` time via some other route. Now you've found *another* route, of the exact same length, through `curr`. Both routes are equally valid shortest paths — so `adjNode`'s way-count grows by however many ways `curr` itself could be reached.

```
┌────────────────────────────────────────────────────────────────┐
│  Strictly better distance → ways[adjNode] = ways[curr]         │
│      (throw away old count — it belonged to a longer path)     │
│                                                                │
│  Equal distance found     → ways[adjNode] += ways[curr]        │
│      (this is a genuinely new shortest path — accumulate)      │
└────────────────────────────────────────────────────────────────┘
```

### Why Does Dijkstra's Processing Order Make This Safe?

This is the same guarantee that made the parent-array path reconstruction work: **when a node is popped from the priority queue, its `dist[]` value is final — nothing will ever beat it again.** That means by the time you use `ways[curr]` to update a neighbour, `ways[curr]` itself is *also* final — every possible shortest path into `curr` has already been counted and folded in. You're never reading a half-finished count.

This is exactly the same "process predecessors before dependents" guarantee that made DAG shortest-path and topological sort correct — Dijkstra's greedy popping order provides it naturally here too, just driven by distance instead of an explicit topo order.

### Initial Configuration

Same skeleton as every Dijkstra problem, plus one new array:

```
dist[]  = (int)1e9 for all nodes, dist[src] = 0
ways[]  = 0 for all nodes, ways[src] = 1
          ↑
          There is exactly ONE way to be at the source
          before you've moved anywhere: doing nothing.

minHeap = [(0, src)]
```

### The Key Insight to Carry

```
┌───────────────────────────────────────────────────────────────────┐
│  NUMBER OF WAYS TO ARRIVE — the pattern                           │
│                                                                   │
│  Standard Dijkstra tracks: shortest distance to each node         │
│  This problem ALSO tracks: how many shortest paths reach it       │
│                                                                   │
│  Relaxation now has two branches instead of one:                  │
│    strictly shorter → ways[adjNode] = ways[curr]     (reset)      │
│    exactly equal     → ways[adjNode] += ways[curr]    (accumulate)│
│                                                                   │
│  Why safe: Dijkstra pops nodes in increasing distance order,      │
│  so ways[curr] is fully finalized (all its predecessors           │
│  already processed) before it's used to update anyone else.       │
│                                                                   │
│  Final answer: ways[destination] % (1e9 + 7)                      │
└───────────────────────────────────────────────────────────────────┘
```

## Stage 3: Coding

### Brute Force

> "Find every possible path from source to destination via DFS. Track the minimum total time across all paths. Then count how many of those paths achieve exactly that minimum."

- Enumerate all paths (exponential — a dense graph can have exponentially many simple paths)
- Two full passes: one to find the minimum, one to count paths matching it
- Correct but hopelessly impractical for real constraints (`n` up to `200`, edges up to `n(n-1)/2`). Establishes the baseline only. No code needed.

---

### Optimal — Dijkstra + Parallel Ways Array

**Mental workflow before writing a single line:**

```
1. Build adjacency list (weighted, undirected)
   → for edge [u, v, time]: add both u→v and v→u

2. Initialize:
   → dist[] = (int)1e9 for all nodes, dist[src] = 0
   → ways[] = 0 for all nodes, ways[src] = 1
   → minHeap = {(0, src)}

3. Dijkstra loop:
   → pop (currDist, currNode)
   → for each (adjNode, adjWt) in adj[currNode]:
       newDist = currDist + adjWt
       if newDist < dist[adjNode]:
           dist[adjNode] = newDist
           ways[adjNode] = ways[currNode]           ← reset
           push (newDist, adjNode) into minHeap
       else if newDist == dist[adjNode]:
           ways[adjNode] = (ways[adjNode] + ways[currNode]) % MOD   ← accumulate

4. Return ways[n-1] % MOD
```

### Full Java Implementation

```java
import java.util.*;

class Solution {

    static final int MOD = 1_000_000_007;

    // Pair class: bundles distance and node together.
    // Implements Comparable so PriorityQueue orders by
    // distance automatically — smallest distance surfaces first.
    static class Pair implements Comparable<Pair> {
        long dist;
        int node;

        Pair(long dist, int node) {
            this.dist = dist;
            this.node = node;
        }

        public int compareTo(Pair other) {
            return Long.compare(this.dist, other.dist);
        }
    }

    public int countPaths(int n, int[][] roads) {

        // ─────────────────────────────────────────
        // STEP 1: Build adjacency list
        // Weighted undirected graph → add both directions
        // Each entry: [neighbourNode, edgeWeight]
        // ─────────────────────────────────────────
        List<List<long[]>> adj = new ArrayList<>();
        for (int i = 0; i < n; i++) {
            adj.add(new ArrayList<>());
        }

        for (int[] road : roads) {
            int u = road[0], v = road[1];
            long wt = road[2];
            adj.get(u).add(new long[]{v, wt});
            adj.get(v).add(new long[]{u, wt});
            // WHY both directions: this is an undirected graph —
            // you can travel either way on every road
        }

        // ─────────────────────────────────────────
        // STEP 2: Initialize dist[] and ways[]
        // dist[i] = shortest known travel time to node i
        // ways[i] = number of distinct shortest paths to node i
        //
        // Use long for dist to avoid any overflow risk while
        // summing edge weights across the graph (up to 200 nodes,
        // weights up to 1e9 each per constraints).
        // ─────────────────────────────────────────
        long[] dist = new long[n];
        long[] ways = new long[n];
        Arrays.fill(dist, Long.MAX_VALUE / 2); // safe "infinity"

        dist[0] = 0;
        ways[0] = 1;
        // WHY ways[0] = 1: there is exactly ONE way to be
        // standing at the source before making any move —
        // doing nothing. Every other node starts at 0 ways
        // because we haven't reached them yet.

        // ─────────────────────────────────────────
        // STEP 3: Min-heap — Dijkstra, seeded with source
        // ─────────────────────────────────────────
        PriorityQueue<Pair> minHeap = new PriorityQueue<>();
        minHeap.add(new Pair(0, 0));

        while (!minHeap.isEmpty()) {
            Pair curr = minHeap.poll();
            long currDist = curr.dist;
            int currNode = curr.node;

            // Standard stale-entry guard: if this popped distance
            // is worse than what we already know, it's an old
            // leftover entry — skip it. (Necessary here because
            // unlike plain Dijkstra, we must not double-count ways
            // by processing a stale entry as if it were fresh.)
            if (currDist > dist[currNode]) continue;

            for (long[] adjacent : adj.get(currNode)) {
                int adjNode = (int) adjacent[0];
                long adjWt = adjacent[1];
                long newDist = currDist + adjWt;

                if (newDist < dist[adjNode]) {
                    // Strictly shorter path found — the old ways
                    // count belonged to a longer route and is now
                    // obsolete. Overwrite, don't accumulate.
                    dist[adjNode] = newDist;
                    ways[adjNode] = ways[currNode];
                    minHeap.add(new Pair(newDist, adjNode));

                } else if (newDist == dist[adjNode]) {
                    // Exactly as short as the best known path —
                    // this is a genuinely NEW shortest path.
                    // Accumulate, don't overwrite.
                    ways[adjNode] = (ways[adjNode] + ways[currNode]) % MOD;
                }
                // else: newDist > dist[adjNode] → strictly worse, discard
            }
        }

        return (int) (ways[n - 1] % MOD);
    }
}
```

## Complexity Analysis

### Time Complexity — O(E log V)

Identical structural cost to standard Dijkstra — the `ways[]` bookkeeping adds only `O(1)` work per relaxation attempt (either an overwrite or a modular addition), which doesn't change the asymptotic class.

```
Each edge examined a bounded number of times across all heap pops → O(E)
Each push/pop on the heap costs O(log V) (heap size bounded by O(E) = O(V²) in dense case, so log(E) = O(log V))

Total: O(E log V)
```

### Space Complexity — O(V + E)

```
Adjacency list        → O(V + E)
dist[] and ways[]      → O(V) each
minHeap                → O(E) worst case
─────────────────────────────
Total: O(V + E)
```
