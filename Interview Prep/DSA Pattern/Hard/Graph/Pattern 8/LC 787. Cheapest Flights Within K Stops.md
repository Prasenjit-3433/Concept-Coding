# LC 787. Cheapest Flights Within K Stops

## Part 1 of 2 — Identification + Intuition (Why Standard Dijkstra Fails)

---

## Stage 1: Identification

**Step 1 — Which topic?**

You're given cities connected by flights with costs, and you need the cheapest route from a source to a destination. Cities as nodes, flights as directed weighted edges — this is a **directed weighted graph**. Topic: **Graph**.

**Step 2 — Which pattern?**

"Cheapest price", "source to destination" — this screams shortest path. The trigger:

> "cheapest cost", "minimum price from source to destination" → **Dijkstra territory** (Pattern 8)

But there's a twist baked into the problem that doesn't exist in any Dijkstra problem so far: **"at most K stops."** This constraint is going to break something fundamental about how Dijkstra works — and figuring out exactly *what* it breaks is the entire point of this problem.

**Step 3 — Which key concept?**

**`Dijkstra fails here — State-Space Expansion (node + stops-used) with a Level-by-Level Queue`**

This is a genuinely new pattern within Pattern 8. In every Dijkstra problem so far, a node's shortest distance — once finalized — is finalized forever, and you never need to revisit that node with a worse distance. Here, that assumption **breaks**. A node might have a *cheaper* known cost but *too many stops already used* to be useful going forward, while a *more expensive* path to the same node might still have stops to spare and lead to a better final answer. So the state you track is no longer just "node" — it becomes **"node, reached using this many stops."**

One clarification worth locking in first: the **source and destination themselves are not counted as stops** — only the intermediate cities you pass through count. So "at most 1 stop" means: direct flight, OR exactly one layover city.

### The First Instinct — "Let's Just Try Plain Dijkstra"

The natural first move: apply standard Dijkstra exactly as taught before. Priority queue ordered by distance, seeded with `(dist=0, node=src)`. Let's actually run it and see where it goes wrong — this is far more convincing than being told upfront that it fails.

```
INITIAL
minHeap = [(0, node=0)]
dist[] = [0, ∞, ∞, ∞, ∞]

POP (0, node=0)
  → node 1: dist = 0+5 = 5 < ∞ → dist[1]=5, push (5,1)
  → node 3: dist = 0+2 = 2 < ∞ → dist[3]=2, push (2,3)

minHeap = [(2,3), (5,1)]

POP (2, node=3)
  → node 1: dist = 2+2 = 4 < dist[1]=5 → dist[1]=4, push (4,1)
    (this is a BETTER path to node 1, so standard Dijkstra
     happily overwrites the old 5 with 4)

minHeap = [(4,1), (5,1)]

POP (4, node=1)   ← this is the stale-free, "best" entry for node 1
  → node 2: dist = 4+5 = 9 < ∞ → dist[2]=9, push (9,2)
  → node 4: dist = 4+1 = 5 < ∞ → dist[4]=5, push (5,4)

minHeap = [(5,1), (5,4), (9,2)]

POP (5, node=1)   ← STALE entry (dist[1] is already 4, not 5)
  → Standard Dijkstra logic: this entry no longer helps —
    every relaxation attempt from here will fail because
    dist[1] is already 4, and 5 > 4. So it gets silently
    discarded, exactly like every other stale-entry situation
    we've seen before.

... eventually dist[2] settles at 9, via path 0→3→1→2
```

Standard Dijkstra reports: **cheapest cost to reach node 2 is 9, via path `0 → 3 → 1 → 2`.**

### But Wait — Count the Stops on That Path

`0 → 3 → 1 → 2` passes through **two intermediate cities (3 and 1)** — that's **2 stops**. But we said `k = 1`. This path is **not even allowed**!

What about the discarded path? The stale entry `(5, node=1)` that Dijkstra threw away — that represents reaching node 1 via `0 → 1` directly, with cost 5, using **0 stops**. From there:

```
0 → 1 → 2:  cost = 5 + 5 = 10, using exactly 1 stop (node 1)
```

Cost 10, using 1 stop — **this is a valid path under the k=1 constraint**, and it's the actual answer. But standard Dijkstra never returns 10. It returns 9, from a path that isn't even legal here — and it threw away the very entry `(5, node=1)` that would have led to the correct legal answer, because that entry looked "worse" by pure distance.

### The Core Realization

```
┌────────────────────────────────────────────────────────────────┐
│  Standard Dijkstra's entire correctness rests on ONE promise:  │
│                                                                │
│    "Once I've found the cheapest way to reach a node,          │
│     I never need to consider a costlier way to reach           │
│     that same node again — it can only make things worse."     │
│                                                                │
│  That promise is TRUE when a node has no other property        │
│  that matters besides its distance.                            │
│                                                                │
│  But here, reaching node 1 has a SECOND dimension: how many    │
│  stops did it cost? A cheaper arrival at node 1 might have     │
│  used up MORE stops than a costlier arrival — and stops are    │
│  a hard budget that limits what you can do NEXT.               │
│                                                                │
│  So "cheapest cost to reach node 1" is NOT enough information  │
│  to make decisions from. You need "cheapest cost to reach      │
│  node 1 USING EXACTLY THIS MANY STOPS."                        │
└────────────────────────────────────────────────────────────────┘
```

This is why Dijkstra discarding the `(5, node=1)` entry was the fatal mistake — it wasn't stale at all. It was a **different state** entirely: `(node=1, stops=0)` is not the same state as `(node=1, stops=1)`, even though both are "at node 1." One has stops left to spend, the other has already spent its only stop getting there.

### The Fix — Expand the State

Instead of tracking just `node`, track the pair `(node, stopsUsedSoFar)`. The queue now carries **three pieces of information**: `stops used, node, distance so far`. Because the state space has grown, a node can legitimately be "visited" multiple times — once for every distinct stop-count it can be reached with — and every one of those visits might still be useful, unlike ordinary Dijkstra where a second visit to a node is always pointless.

### Does This Mean We Need a Priority Queue Again?

Look at how the "stops" value grows during exploration: you start at 0 stops, and every single edge you take increases the stop count by exactly `+1`. This is **identical in spirit** to the unit-weight BFS realization from LC 1091 — a value increasing by a fixed `+1` per edge means a plain FIFO queue processes states in increasing order of stops automatically, level by level. You don't need a min-heap to sort by stops — the queue sorts itself.

```
┌─────────────────────────────────────────────────────────────────┐
│  Why plain Queue, not Priority Queue, this time?                │
│                                                                 │
│  The priority queue's job in Dijkstra is to always surface      │
│  the globally cheapest next state. But here, what we actually   │
│  need to control is "process states level-by-level in stops,    │
│  cheapest edges accounted for along the way" — and the ordering │
│  constraint that matters (stops = level) increases by exactly   │
│  +1 per edge. Just like unit-weight BFS, that self-sorts        │
│  in a plain queue.                                              │
│                                                                 │
│  We still track distance (cost) at every state — we just don't  │
│  need a heap to prioritize by it. We prioritize by stops        │
│  (via FIFO order) and let the relaxation condition on distance  │
│  do the rest.                                                   │
└─────────────────────────────────────────────────────────────────┘
```

### The New Relaxation Rule — With a Stop Budget

When popping `(stops, node, dist)`:

1. **If `stops > k` already** → this path used up too many intermediate stops to be legal. Abandon it — don't explore further from here.
2. **For each neighbour `adjNode` via edge weight `adjWt`:**
   ```
   newDist = dist + adjWt
   if newDist < distArray[adjNode]:
       distArray[adjNode] = newDist
       push (stops + 1, adjNode, newDist) into queue
   ```
3. **Never stop early just because you reached the destination once** — a later state (with more stops spent, but possibly still within budget) might reach the destination at an even lower cost. This is explicitly the trap Striver calls out: reaching the destination is not a signal to terminate, only to record a candidate answer.

### Why Do We Still Keep a `distArray[]` at All, Given States Can Repeat?

The array isn't there to say "never revisit a node" (which was its old job in Dijkstra) — it's there purely as a **pruning heuristic**: if the current path to `adjNode` isn't even an improvement over some previously found cost (regardless of stops), there is no point pushing it — a costlier arrival, even with stops to spare, is strictly worse than a cheaper arrival, since more stops only ever gives you *equal or more* flexibility, never less. So the array still prunes useless states, just not on the "one visit per node" basis anymore.

### The Key Insight to Carry

```

│  CHEAPEST FLIGHTS WITHIN K STOPS — the pattern break               │
│                                                                    │
│  Standard Dijkstra state  : node                                   │
│  This problem's state     : (node, stopsUsedSoFar)                 │
│                                                                    │
│  Why the old state is insufficient:                                │
│    A cheaper arrival at a node may have exhausted the stop         │
│    budget, while a costlier arrival may still have stops to        │

│                                                                    │

```

## Part 2 of 2 — Full Workflow, Implementation, Trace & Complexity

### The Complete Mental Workflow

```
1. Build adjacency list (directed, weighted)
   → for each flight [u, v, cost]: adjList.get(u).add(Edge(v, cost))

2. dist[] = (int)1e9 for all nodes, dist[src] = 0

3. Queue seeded with Tuple(stops=0, node=src, cost=0)

4. While queue not empty:
   → pop Tuple(currStops, currNode, currCost)
   → if currStops > k: abandon this path, continue to next in queue
      (this path has already used more intermediate stops than allowed —
       going further would only use even more, so it's dead)
   → for each Edge(adjNode, adjCost) in adjList[currNode]:
       newCost = currCost + adjCost
       if newCost < dist[adjNode]:
           dist[adjNode] = newCost
           push Tuple(currStops + 1, adjNode, newCost)

5. After queue empties:
   if dist[dst] == (int)1e9 → return -1
   else → return dist[dst]
```

Notice step 4's `continue` is checked **after popping, before exploring neighbours** — so a state that has exactly `k` stops still gets to explore its neighbours one final time (landing at `stops = k+1`, which represents "used the flight that lands me at the destination, having passed through exactly `k` intermediate cities"). Only a state that already exceeds `k` gets cut off. This lines up exactly with the problem's "at most k stops" semantics.

### Full Java Implementation

```java
import java.util.*;

class Edge {
    int node;
    int cost;

    public Edge(int node, int cost) {
        this.node = node;
        this.cost = cost;
    }
}

class Tuple {
    int stops;
    int node;
    int cost;

    public Tuple(int stops, int node, int cost) {
        this.stops = stops;
        this.node = node;
        this.cost = cost;
    }
}

class Solution {
    public int findCheapestPrice(int n, int[][] flights, int src, int dst, int k) {

        // ─────────────────────────────────────────
        // STEP 1: Build the adjacency list
        // Directed graph → edge only in one direction
        // ─────────────────────────────────────────
        List<List<Edge>> adjList = new ArrayList<>();
        for (int node = 0; node < n; node++) {
            adjList.add(new ArrayList<>());
        }

        for (int[] flight : flights) {
            int u = flight[0];
            int v = flight[1];
            int cost = flight[2];
            adjList.get(u).add(new Edge(v, cost));
        }

        // ─────────────────────────────────────────
        // STEP 2: Initialize dist[]
        // (int)1e9 as infinity — same overflow-safe
        // reasoning used throughout Pattern 8
        // ─────────────────────────────────────────
        int[] dist = new int[n];
        Arrays.fill(dist, (int) 1e9);
        dist[src] = 0;

        // ─────────────────────────────────────────
        // STEP 3: Plain Queue — NOT a PriorityQueue
        // WHY: stops increases by exactly +1 per edge,
        // so the queue naturally processes states in
        // increasing order of stops, level by level —
        // identical reasoning to unit-weight BFS.
        // ─────────────────────────────────────────
        Queue<Tuple> queue = new LinkedList<>();
        queue.add(new Tuple(0, src, 0));

        // ─────────────────────────────────────────
        // STEP 4: Level-by-level state expansion
        // ─────────────────────────────────────────
        while (!queue.isEmpty()) {
            Tuple curr = queue.poll();
            int currNode = curr.node;
            int currCost = curr.cost;
            int currStops = curr.stops;

            // Stop budget exhausted — this path cannot
            // legally extend any further
            if (currStops > k) continue;

            for (Edge adjacent : adjList.get(currNode)) {
                int adjNode = adjacent.node;
                int adjCost = adjacent.cost;

                // Relaxation condition — same shape as
                // every Dijkstra variant so far, but now
                // pushing a NEW STATE (stops+1, adjNode)
                // rather than just marking adjNode "done"
                if (currCost + adjCost < dist[adjNode]) {
                    dist[adjNode] = currCost + adjCost;
                    queue.add(new Tuple(currStops + 1, adjNode, dist[adjNode]));
                }
            }
            // IMPORTANT: no early exit even if currNode == dst.
            // A later state — reached with more stops spent,
            // but still within budget — might update dist[dst]
            // to something even cheaper.
        }

        return dist[dst] != (int) 1e9 ? dist[dst] : -1;
    }
}
```

## Complexity Analysis

### Time Complexity — O(N + E·K)

This is meaningfully different from standard Dijkstra's `O(E log V)`, and it's worth deriving carefully rather than reusing the old formula on autopilot.

There is **no priority queue here**, so there is no `log V` factor anywhere — that term is gone entirely, exactly as Striver points out.

What replaces it is the **state expansion**. In standard Dijkstra, each node is processed a bounded number of times because once its shortest distance is finalized, later pushes are stale and cheaply discarded. Here, a node can legitimately be pushed and processed once for **every distinct stop-level** it gets reached at, up to `k+1` levels (stops = 0, 1, 2, ..., k). So instead of each edge being relaxed a small constant number of times overall, each edge can be relaxed up to `O(K)` times — once per stop-level at which its source node might be popped.

```
Total edges = E
Each edge can trigger a relaxation attempt at every stop level, up to K+1 levels
→ Total relaxation attempts ≈ O(E · K)

Building the adjacency list → O(E)
Final dist[] lookup → O(1)

Overall Time: O(E · K)   (dominant term; O(N) for setup is absorbed)
```

### Space Complexity — O(N + E)

```
Adjacency list  → O(N + E)
dist[] array    → O(N)
Queue           → O(N · K) in the worst case, since each node can
                   have a queued state at every stop level

Overall Space: O(N + E) for the graph structures,
               with queue occupancy bounded by O(N·K) in the worst case
```
