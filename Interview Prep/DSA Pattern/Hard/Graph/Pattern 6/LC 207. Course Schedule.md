# Stage 1: Identification

**Step 1 — Which topic?**

You are given tasks with prerequisites — meaning "to do task A, you must first complete task B." This is a **dependency/ordering** problem on a set of items. The moment you see *"X must come before Y"*, your brain should jump to **Graph**.

**Step 2 — Which pattern?**

Look at what the problem is really asking:
- Can all tasks be finished? → Is a valid ordering possible?
- What is that ordering? → Give the actual sequence.

A valid ordering exists **only if there are no circular dependencies** (cycles). And finding a linear ordering where all dependencies come before dependents — that is the exact definition of **Topological Sort** (Pattern 6 in our Graph sheet).

The trigger here is classic:
> "prerequisites", "must be done before", "ordering", "dependencies" → **Topological Sort**

**Step 3 — Which key concept?**

Two valid approaches exist:
- DFS + Stack (detects cycle via 3-color marking)
- **Kahn's Algorithm — BFS with in-degree** ✓ (Striver's preferred approach here)

We use **Kahn's Algorithm** because:
- It naturally detects cycles (if processed count < n, a cycle exists)
- For Course Schedule II, it directly gives us the ordering — no reversal needed
- It is more intuitive for "prerequisite" style problems

---

# Stage 2: Intuition Building

### The Core Question

Before thinking about any algorithm, ask yourself this:

> *"Which task can I safely do first — without violating any prerequisite?"*

The answer is simple: **any task that has no prerequisites at all.** Nobody needs to happen before it.

This is exactly the in-degree = 0 idea from Kahn's algorithm. A task with in-degree 0 has no incoming edges — no task needs to precede it.

---

### Building the Graph

The prerequisites are given as pairs. Let's understand the edge direction carefully — this is where Course Schedule I and II differ slightly in input format.

**Course Schedule I** — pair `[1, 0]` means *"to take course 1, you must first take course 0"*
So the edge goes: `0 → 1` (0 must come before 1)

**Course Schedule II** — pair `[0, 1]` means *"to take course 0, you must first finish course 1"*
So the edge goes: `1 → 0` (1 must come before 0)

The graph structure and algorithm are identical — only the edge direction from the input pair flips. Striver points this out explicitly in the lecture.

### Concrete Example — When answer is YES

```
n = 4
prerequisites = [[1,0], [2,1], [3,2]]   (Course Schedule I format)
```

Paste into csacademy.com (directed graph):
```
0 1
1 2
2 3
```

In-degrees:
```
Node 0 → in-degree 0  (no prerequisites)
Node 1 → in-degree 1  (needs 0)
Node 2 → in-degree 1  (needs 1)
Node 3 → in-degree 1  (needs 2)
```

Processing step by step:

```
Queue starts with: [0]   (only node with in-degree 0)

Step 1: Pop 0 → processed = [0]
        Neighbor 1: in-degree 1→0 → push 1
        Queue: [1]

Step 2: Pop 1 → processed = [0, 1]
        Neighbor 2: in-degree 1→0 → push 2
        Queue: [2]

Step 3: Pop 2 → processed = [0, 1, 2]
        Neighbor 3: in-degree 1→0 → push 3
        Queue: [3]

Step 4: Pop 3 → processed = [0, 1, 2, 3]
        No neighbors.
        Queue: []
```

Processed count = 4 = n → **No cycle → All courses can be finished → return true**
The ordering `[0, 1, 2, 3]` is the answer for Course Schedule II.

### Concrete Example — When answer is NO (cycle exists)

```
n = 3
prerequisites = [[1,0], [2,1], [0,2]]   (Course Schedule I format)
```

Paste into csacademy.com:
```
0 1
1 2
2 0
```

In-degrees:
```
Node 0 → in-degree 1  (needs 2)
Node 1 → in-degree 1  (needs 0)
Node 2 → in-degree 1  (needs 1)
```

Nobody has in-degree 0. Queue starts **empty**.

```
Queue: []   → nothing to process
Processed count = 0 ≠ n = 3
```

**Cycle detected → Impossible to finish all courses → return false / return []**

This is the elegant cycle detection bonus of Kahn's algorithm — nodes inside a cycle can never reach in-degree 0 because they are all waiting on each other. They never enter the queue. They never get processed.

```
│  If processed count == n  →  no cycle  →  YES              │

```

## Brute Force Approach

**The honest brute force thinking:**

> "Can I finish all courses? Let me try every possible ordering of all n courses and check if any of them satisfies all prerequisites."

- Generate all permutations of n courses → O(n!) orderings
- For each ordering, check if every prerequisite pair is satisfied → O(n! × m) where m = number of prerequisites
- If any ordering works → return true / return that ordering

**Why this is terrible:**
- n = 20 already gives 20! ≈ 2.4 × 10¹⁸ orderings
- Completely impractical — just establishes the baseline

No code needed for this — the approach is obvious and the problem constraints (n up to 2000, prerequisites up to 5000) make it immediately clear we need something smarter.

---

## Better Approach — Cycle Detection via DFS

**The thinking:**

> "I don't need to find the ordering yet. I just need to know if a cycle exists. DFS with 3-color marking detects cycles in directed graphs."

This directly solves **Course Schedule I** (yes/no answer). Striver mentions it in the lecture — you can use DFS cycle detection. But he chooses Kahn's because Course Schedule II needs the actual ordering, and Kahn's gives it naturally.

**3-color DFS logic:**
- WHITE (0) = not visited
- GRAY (1) = currently in DFS stack (being processed)
- BLACK (2) = fully processed

If during DFS you reach a GRAY node → cycle detected → return false.

```java
class Solution {
    // 0 = unvisited, 1 = visiting (in stack), 2 = fully done
    private int[] state;
    private List<List<Integer>> adj;

    public boolean canFinish(int numCourses, int[][] prerequisites) {
        state = new int[numCourses];
        adj = new ArrayList<>();
        for (int i = 0; i < numCourses; i++) {
            adj.add(new ArrayList<>());
        }

        // Build graph: pair [a, b] means b → a (b must come before a)
        for (int[] pre : prerequisites) {
            adj.get(pre[1]).add(pre[0]);
        }

        // Try DFS from every unvisited node
        // (handles disconnected components)
        for (int i = 0; i < numCourses; i++) {
            if (state[i] == 0) {
                if (hasCycle(i)) return false;
            }
        }
        return true;
    }

    private boolean hasCycle(int node) {
        state[node] = 1; // mark as currently visiting

        for (int neighbor : adj.get(node)) {
            if (state[neighbor] == 1) return true;  // back edge → cycle
            if (state[neighbor] == 0) {
                if (hasCycle(neighbor)) return true;
            }
            // state == 2 means fully processed → safe, skip
        }

        state[node] = 2; // mark as fully done
        return false;
    }
}
```

**Complexity:**
- Time: O(V + E) — every node and edge visited once
- Space: O(V + E) — adjacency list + recursion stack

**Limitation:** Gives yes/no only. To get the actual ordering for Course Schedule II, you would need to push nodes onto a stack at the end of each DFS call and then reverse — which is exactly the DFS + Stack topological sort. Kahn's does this more cleanly.

## Optimal Approach — Kahn's Algorithm (BFS with In-degree)

This is Striver's chosen approach. It solves **both problems** with the same code — just a small difference in what you return.

**The complete mental workflow before writing a single line:**

```
1. Build adjacency list from prerequisites
   → edge direction: b → a for pair [a, b]
      (b must be done before a)

2. Compute in-degree for every node
   → in-degree[node] = how many prerequisites it has

3. Push all nodes with in-degree 0 into queue
   → these courses have no prerequisites, safe to take first

4. BFS:
   → pop a node, add to result (this course is now "done")
   → for each neighbor: reduce its in-degree by 1
   → if neighbor's in-degree becomes 0, push to queue
      (all its prerequisites are now done)

5. After BFS ends:
   → if result.size() == n: no cycle, all courses doable
   → if result.size() < n: cycle exists, impossible
```

---

### Course Schedule I — Can you finish all courses?

```java
class Solution {
    public boolean canFinish(int numCourses, int[][] prerequisites) {

        // Step 1: Build adjacency list
        // pair [a, b] means: to take a, must finish b first
        // so edge goes b → a
        List<List<Integer>> adj = new ArrayList<>();
        for (int i = 0; i < numCourses; i++) {
            adj.add(new ArrayList<>());
        }
        for (int[] pre : prerequisites) {
            adj.get(pre[1]).add(pre[0]);
        }

        // Step 2: Compute in-degree for every node
        int[] inDegree = new int[numCourses];
        for (int i = 0; i < numCourses; i++) {
            for (int neighbor : adj.get(i)) {
                inDegree[neighbor]++;
            }
        }
        // WHY: in-degree tells us how many courses must be
        // completed before this one. Only when all of them
        // are done (in-degree drops to 0) can we take it.

        // Step 3: Push all courses with no prerequisites
        Queue<Integer> queue = new LinkedList<>();
        for (int i = 0; i < numCourses; i++) {
            if (inDegree[i] == 0) {
                queue.add(i);
            }
        }

        // Step 4: BFS
        int processedCount = 0;

        while (!queue.isEmpty()) {
            int course = queue.poll();
            processedCount++;
            // This course is now "completed"

            for (int neighbor : adj.get(course)) {
                inDegree[neighbor]--;
                // WHY: this course is done, so its contribution
                // to neighbor's prerequisites is removed

                if (inDegree[neighbor] == 0) {
                    queue.add(neighbor);
                }
                // WHY: all prerequisites of neighbor are now
                // completed, so it's safe to take it
            }
        }

        // Step 5: Cycle check
        // If not all courses were processed → cycle exists
        return processedCount == numCourses;
    }
}
```

## Dry Run on Example

```
numCourses = 4
prerequisites = [[1,0],[2,0],[3,1],[3,2]]
```

Graph edges (b → a for each [a,b]):
```
0 1
0 2
1 3
2 3
```

In-degrees:
```
Node 0 → 0
Node 1 → 1  (needs 0)
Node 2 → 1  (needs 0)
Node 3 → 2  (needs 1 and 2)
```

```
Queue: [0]

Pop 0 → order = [0], idx = 1
  neighbor 1: in-degree 1→0 → push 1
  neighbor 2: in-degree 1→0 → push 2
Queue: [1, 2]

Pop 1 → order = [0,1], idx = 2
  neighbor 3: in-degree 2→1
Queue: [2]

Pop 2 → order = [0,1,2], idx = 3
  neighbor 3: in-degree 1→0 → push 3
Queue: [3]

Pop 3 → order = [0,1,2,3], idx = 4
Queue: []

idx == numCourses → return [0, 1, 2, 3]
```

## Complexity Analysis

| | Complexity | Reason |
|---|---|---|
| **Time** | O(V + E) | Every node enqueued/dequeued once (V). Every edge processed once when reducing in-degree (E). |
| **Space** | O(V + E) | Adjacency list O(V+E), in-degree array O(V), queue O(V), result O(V). |
