# Stage 1: Identification

**Step 1 — Which topic?**

You're given an `n × n` binary grid and asked to find the largest group of connected `1`s, with the option to flip **at most one** `0` into a `1`. Movement between adjacent grid cells is always an implicit graph — each cell is a node, each valid adjacency is an edge. Topic: **Graph**.

**Step 2 — Which pattern?**

Look at what's actually happening as you consider flipping different `0`s: each hypothetical flip potentially **merges multiple existing components together**, and the components you're merging change depending on which cell you pick. You are repeatedly asking *"if I connect this cell to its neighbors, how big does the resulting group get?"* — this is exactly the "components merging dynamically" trigger:

> "merge groups", "check component size", "dynamically changing connectivity" → **Disjoint Set Union (Pattern 11)**

**Step 3 — Which key concept?**

**`Precompute Land Components via DSU, Then Probe Every Water Cell Using a Root-Deduplication Set`**

This is a two-phase problem, and each phase does something you've already seen before in this pattern — just combined in a new way:

- **Phase 1** is the exact same "flatten grid cell to a single node ID" + "union adjacent land cells" mechanism from Number of Islands II. Nothing new here — build the components that already exist, once, up front.
- **Phase 2** is new: for every water cell, look at its (up to 4) land neighbors, and ask "what is the total size if I merge myself with all of these?" The twist that makes this a distinct key concept: a single water cell can have **multiple neighbors that already belong to the exact same component** (imagine a `0` sitting in the middle of a ring of `1`s — all 4 neighbors belong to one component). If you naively summed every neighbor's component size, you would **count that one component's size multiple times**, wildly overcounting. The fix is a `Set` that stores only **ultimate parents** — since a set can never contain a duplicate, you can only ever count a given component's size once, no matter how many directions it touches you from.

# Stage 2: Intuition Building

### The Core Question

Before touching any code, ask the most direct question:

> *"If I convert one specific water cell into land, what is the size of the connected component it becomes part of?"*

The cell itself contributes `1`. Then, look in all four directions — up, down, left, right. Any direction that already has land belongs to **some existing component**, and that entire component's size gets absorbed into the new, bigger component. So the total is:

```
newSize = 1 (for the flipped cell itself)
        + size of every DISTINCT component touching it from the 4 directions
```

The word **distinct** is doing all the work in that sentence, and it's the entire reason this problem needs more care than a plain "sum the four neighbors' sizes."

---

### Building the Intuition With a Clean Example

```
1 1 0
1 1 0
0 0 1
```

Paste-able as a grid (row by row, top to bottom).

Two land components exist right now:
- Top-left block `{(0,0),(0,1),(1,0),(1,1)}` — size **4**
- Bottom-right single cell `{(2,2)}` — size **1**

Water cells: `(0,2)`, `(1,2)`, `(2,0)`, `(2,1)`.

**Try flipping `(1,2)`:**
```
neighbours: (0,2)=water, (2,2)=LAND(size 1), (1,1)=LAND(size 4)
newSize = 1 + 1 + 4 = 6
```

**Try flipping `(2,1)`:**
```
neighbours: (2,0)=water, (2,2)=LAND(size 1), (1,1)=LAND(size 4)
newSize = 1 + 1 + 4 = 6
```

**Try flipping `(2,0)`:**
```
neighbours: (1,0)=LAND(size 4), (2,1)=water
newSize = 1 + 4 = 5
```

**Try flipping `(0,2)`:**
```
neighbours: (0,1)=LAND(size 4), (1,2)=water
newSize = 1 + 4 = 5
```

Maximum across all candidates: **6**. This is the entire algorithm, mechanically — the only remaining question is how to do it *correctly* and *efficiently*, which is exactly where the edge case below comes in.

---

### The Edge Case That Breaks a Naive Sum

Now consider a deliberately adversarial grid — a ring of land surrounding a single water cell in the middle:

```
1 1 1
1 0 1
1 1 1
```

The 8 outer land cells all connect to each other (going around the ring), forming **one single component of size 8**. The center cell `(1,1)` is water.

Look at `(1,1)`'s four neighbors:
```
top    (0,1) → land, ultimate parent = P
bottom (2,1) → land, ultimate parent = P
left   (1,0) → land, ultimate parent = P
right  (1,2) → land, ultimate parent = P
```

**All four directions point back to the exact same component**, because the ring is fully connected. If you naively summed `size[top] + size[bottom] + size[left] + size[right]`, you'd compute `8 + 8 + 8 + 8 = 32` — wildly wrong. Then adding 1 for the flipped cell gives 33, when the true answer for this flip is `8 + 1 = 9`.

```
┌──────────────────────────────────────────────────────────────────┐
│  THE FIX                                                         │
│                                                                  │
│  Never sum sizes directly off the four raw neighbours.           │
│  Instead, for each of the four neighbours that is land,          │
│  compute its ULTIMATE PARENT and drop that into a Set.           │
│                                                                  │
│  A Set can never hold a duplicate value — so no matter how       │
│  many of the 4 directions belong to the same component, that     │
│  component's root only ever gets recorded ONCE.                  │
│                                                                  │
│  Once all 4 directions are checked, sum size[root] for every     │
│  DISTINCT root left in the set, then add 1 for the flipped       │
│  cell itself.                                                    │
└──────────────────────────────────────────────────────────────────┘
```

This is exactly why the algorithm asks for `findUltParent(neighbor)` — not just "is this cell land?" — before deciding whether to count it: the deduplication only works if you're comparing *roots*, not raw neighbor coordinates.

---

### Why We Need the `hasZero` Flag

One more subtlety, easy to miss: what if the entire grid is already all `1`s? Then there is no water cell to flip at all — the "at most one" flip option simply goes unused, and the answer is just the whole grid's size, `m × n`. If you don't special-case this, the water-scanning loop in Phase 2 never executes even once (since there's no water), and `max` would incorrectly stay at whatever default you initialized it to (or worse, 0). Tracking whether **any** water cell was ever encountered tells you whether Phase 2 actually produced a meaningful answer, or whether you need to fall back to `m*n`.

---

### The Key Insight to Carry

```
┌──────────────────────────────────────────────────────────────────────┐
│  MAKING A LARGE ISLAND — the pattern                                 │
│                                                                      │
│  Phase 1 — build what already exists:                                │
│      flatten every land cell to nodeId = row*n + col                 │
│      union every land cell with its land neighbours                  │
│      (identical mechanism to Number of Islands II, done ONCE,        │
│       not per-operation, since the grid isn't dynamic here)          │
│                                                                      │
│  Phase 2 — probe every water cell:                                   │
│      for each water cell, look at its ≤4 land neighbours             │
│      collect their ULTIMATE PARENTS into a Set (deduplication!)      │
│      totalSize = 1 + sum of size[root] for every DISTINCT root       │
│      track the max totalSize seen across all water cells             │
│                                                                      │
│  Edge case: if the grid has NO water cells at all, the answer        │
│  is simply m*n — Phase 2 never gets a chance to run meaningfully     │
└──────────────────────────────────────────────────────────────────────┘
```

# Stage 3: Coding

### Brute Force

> "For every single water cell, temporarily flip it to land, then run a full DFS/BFS from that cell to measure the size of the resulting connected component. Track the maximum across all such flips, then flip it back."

- `m × n` water cells to try, each triggering a fresh `O(m·n)` traversal to measure the resulting island size
- Total: `O((m·n)²)` — for grids up to `500×500` (LeetCode's constraint), this is far too slow
- Correct, but establishes the baseline only. No code needed — the DSU approach below removes the repeated-traversal cost entirely by precomputing every component's size exactly once, up front.

---

### Better

There is no meaningful intermediate tier here, the same way LC 947 had none. The moment you recognize "components exist, and flipping a cell merges some subset of them," the natural move **is** DSU — precompute every component's size once, then answer each hypothetical flip in `O(1)` neighbor-lookups instead of a fresh traversal. A DFS-based variant (flood-fill and cache each component's ID + size in a hash map, then do the same neighbor-probing) is a valid alternative that reaches the same complexity as the DSU version — but it doesn't introduce a genuinely different technique worth its own tier, so we go straight to the optimal DSU solution.

---

### Optimal — DSU: Precompute, Then Probe With Deduplication

**Mental workflow before writing a single line:**

```
1. m = rows, n = columns
   Initialize DisjointSet(m*n)

2. PHASE 1 — build existing land components:
   for every cell (i, j):
       if grid[i][j] == 0: skip (water contributes nothing yet)
       for each of the 4 directions:
           if the neighbour is in bounds AND is land:
               union(nodeId(i,j), nodeId(adjRow,adjCol))

3. PHASE 2 — probe every water cell:
   hasZero = false
   max = 0
   for every cell (i, j):
       if grid[i][j] == 1: skip (only water is a flip candidate)
       hasZero = true

       Set<Integer> roots = {}
       for each of the 4 directions:
           if the neighbour is in bounds AND is land:
               roots.add(findUltParent(nodeId(adjRow,adjCol)))

       totalSize = 1                       // the flipped cell itself
       for each root in roots:
           totalSize += size[root]
       max = Math.max(max, totalSize)

4. return hasZero ? max : m*n
```

### Full Java Implementation

```java
class DisjointSet {
    public List<Integer> parent = new ArrayList<>();
    public List<Integer> size = new ArrayList<>();

    public DisjointSet(int n) {
        for(int i=0; i<=n; i++) {
            parent.add(i);
            size.add(1);
        }
    }

    public int findUltParent(int node) {
        if (node == parent.get(node)) {
            return node;
        }

        int ultParent = findUltParent(parent.get(node));
        parent.set(node, ultParent);
        return parent.get(node);
    }

    public void unionBySize(int u, int v) {
        int ultParentU = findUltParent(u);
        int ultParentV = findUltParent(v);

        if (ultParentU == ultParentV) return;

        if (size.get(ultParentU) < size.get(ultParentV)) {
            parent.set(ultParentU, ultParentV);
            size.set(ultParentV, size.get(ultParentV) + size.get(ultParentU));
        } else {
            parent.set(ultParentV, ultParentU);
            size.set(ultParentU, size.get(ultParentU) + size.get(ultParentV));
        }
    }
}

class Solution {
    private boolean isValidCell(int i, int j, int[][] grid) {
        int m = grid.length, n = grid[0].length;

        return (0 <= i && i < m) &&
        (0 <= j && j < n);
    }

    public int largestIsland(int[][] grid) {
        int m = grid.length, n = grid[0].length;

        DisjointSet dsu = new DisjointSet(m*n-1);
        int[][] dir = {{0, 1}, {1, 0}, {-1, 0}, {0, -1}};

        // ─────────────────────────────────────────
        // PHASE 1: Build every EXISTING land component
        // up front — this happens exactly once, unlike
        // Number of Islands II where unions happened
        // incrementally per operator. Here the grid is
        // static, so we just union the whole thing in
        // one pass before touching any water cell.
        // ─────────────────────────────────────────
        for(int i=0; i<m; i++) {
            for(int j=0; j<n; j++) {

                // ignore if water
                if (grid[i][j] == 0) continue;

                for(int k=0; k<4; k++) {
                    int adjRow = i + dir[k][0];
                    int adjCol = j + dir[k][1];

                    if (isValidCell(adjRow, adjCol, grid) && grid[adjRow][adjCol] == 1) {
                        int currNode = i * n + j;
                        int adjNode = adjRow * n + adjCol;

                        dsu.unionBySize(currNode, adjNode);
                    }
                }
            }
        }

        // Now trying out making one cell as land
        Set<Integer> st = new HashSet<>();
        int max = 0;

        // edge case detection: all cell 1's
        boolean hasZero = false;

        // ─────────────────────────────────────────
        // PHASE 2: Probe every water cell. For each one,
        // ask "what would my new component size be if I
        // flipped THIS cell to land?"
        //
        // WHY a Set here, specifically of ULTIMATE PARENTS:
        // a water cell can have multiple neighbours that
        // belong to the SAME already-existing component
        // (e.g. a 0 surrounded on multiple sides by one
        // connected ring of land). Summing raw neighbour
        // sizes would double/triple/quadruple count that
        // one component. A Set of roots guarantees each
        // distinct component is counted EXACTLY once,
        // no matter how many directions it touches from.
        // ─────────────────────────────────────────
        for(int i=0; i<m; i++) {
            for(int j=0; j<n; j++) {

                // ignore if land
                if (grid[i][j] == 1) continue;

                hasZero = true;

                for(int k=0; k<4; k++) {
                    int adjRow = i + dir[k][0];
                    int adjCol = j + dir[k][1];

                    if (isValidCell(adjRow, adjCol, grid) && grid[adjRow][adjCol] == 1) {
                        int adjNode = adjRow * n + adjCol;

                        // store the ROOT, not the raw neighbour —
                        // this is what makes deduplication work
                        st.add(dsu.findUltParent(adjNode));
                    }
                }

                int totalSize = 1; // for the flipped cell itself
                for(int node : st) {
                    totalSize += dsu.size.get(node);
                }
                max = Math.max(max, totalSize);
                st.clear();
            }
        }

        // If every cell was already land, Phase 2 never ran
        // meaningfully — fall back to the whole grid's size.
        return hasZero ? max : m*n;
    }
}
```

### Workflow Trace on the Ring Example

```
grid =
1 1 1
1 0 1
1 1 1

m=3, n=3

PHASE 1 — union every land cell with its land neighbours.
All 8 outer cells chain together as they're each other's
neighbours going around the ring. After Phase 1, every one
of those 8 nodes shares ONE ultimate parent — call it P.
size[P] = 8.

PHASE 2 — only water cell is (1,1):
  hasZero = true
  neighbours of (1,1):
    top    (0,1) → land → findUltParent = P → st.add(P)
    bottom (2,1) → land → findUltParent = P → st.add(P)  (already in set, no-op)
    left   (1,0) → land → findUltParent = P → st.add(P)  (already in set, no-op)
    right  (1,2) → land → findUltParent = P → st.add(P)  (already in set, no-op)

  st = {P}   ← only ONE entry, despite 4 directions all being land

  totalSize = 1 + size[P] = 1 + 8 = 9
  max = 9

No more water cells → loop ends.

hasZero = true → return max = 9
```

**Answer: 9** — exactly the corrected value from the intuition-building walkthrough, confirming the Set correctly prevented the `32`-style overcounting a naive sum would have produced.

## Complexity Analysis

### Time Complexity — O(m · n)

Let's derive this the way we always do, phase by phase.

**Phase 1 — building components:**
```
Outer double loop over every cell     → O(m·n)
For each land cell, check 4 neighbours, possibly union → O(4) = O(1) per cell,
  each union call costs O(4α) ≈ O(1) amortized (near-constant DSU operation)

Phase 1 total: O(m·n)
```

**Phase 2 — probing every water cell:**
```
Outer double loop over every cell again → O(m·n)
For each water cell, check 4 neighbours → O(4) = O(1) per cell,
  each findUltParent() call is O(4α) ≈ O(1)
  Set insertions are O(1) average, and the set holds AT MOST 4 entries
    (bounded by the 4 directions) — so summing over the set is also O(4) = O(1)

Phase 2 total: O(m·n)
```

```
Overall Time: O(m·n) + O(m·n) = O(m·n)
```

The `4α` (inverse Ackermann) factor from every DSU operation is, as established throughout Pattern 11, effectively a constant for any grid size you'll realistically encounter — so it doesn't change the asymptotic class here either.

### Space Complexity — O(m · n)

```
DisjointSet (parent[] + size[])   → O(m·n)
Set<Integer> per water cell        → O(4) = O(1) at any instant (cleared each iteration)
─────────────────────────────
Total: O(m·n)
```
