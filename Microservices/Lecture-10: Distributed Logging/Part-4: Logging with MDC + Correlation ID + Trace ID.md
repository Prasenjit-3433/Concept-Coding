# Step 1 — What is MDC? How does it work internally?

---

## The Problem MDC Solves

Imagine you have a payment service. A request comes in, and your code logs multiple events:

```
log.info("payment initiated");
log.info("payment processed");
log.info("payment successful");
```

These logs look like this in your log file:

```
INFO - payment initiated
INFO - payment processed
INFO - payment successful
```

Now here's the problem — what if you want **every single log statement** to automatically carry extra context like `payment_id=P123` or `user_id=U1234`... **without manually passing those values into every single log.info() call?**

That's exactly what **MDC** solves.

---

## What is MDC?

**MDC = Mapped Diagnostic Context**

It is simply a **per-thread key-value map** that lives inside your logging framework (Logback / Log4j2).

- "Per-thread" means every thread has **its own separate MDC map**
- You put data into it once → the logging framework **automatically attaches that data to every log event** generated by that thread
- You never have to pass context manually into each `log.info()` call

```java
MDC.put("payment_id", "P123");
MDC.put("user_id", "U1234");

log.info("payment is successful"); // MDC data auto-attached here
log.info("payment failed");        // MDC data auto-attached here too
```

---

## How Does MDC Work Internally?

This is the most important part. Let's trace exactly what happens step by step when you call `log.info(...)`.

```
┌─────────────────────────────────────────────────────────────────┐
│                        YOUR CODE                                │
│                                                                 │
│   MDC.put("payment_id", "P123");                                │
│   MDC.put("user_id",    "U1234");                               │
│   log.info("payment is successful");   ← SLF4J interface call   │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│                  LOGBACK (SLF4J Implementation)                 │
│                                                                 │
│  Step 1: Converts log statement → ILoggingEvent object          │
│                                                                 │
│   ILoggingEvent {                                               │
│     message    : "payment is successful"                        │
│     level      : INFO                                           │
│     loggerName : com.concepts.PaymentController                 │
│     mdcPropertyMap : {                                          │
│        "payment_id" : "P123",    ← copied from MDC map          │
│        "user_id"    : "U1234"    ← copied from MDC map          │
│     }                                                           │
│   }                                                             │
│                                                                 │
│  Step 2: Logger Level Check                                     │
│    Logger level = INFO                                          │
│    Log statement level = INFO  → ✅ ACCEPTED                     │
│                                                                 │
│  Step 3: Sends ILoggingEvent to Appender(s)                     │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│                        APPENDER                                 │
│                                                                 │
│  Formats the ILoggingEvent using either:                        │
│                                                                 │
│  Option A → Pattern Encoder (plain text)                        │
│    - Use %X      → prints ALL MDC values                        │
│      output: payment_id=P123, user_id=U1234                     │
│    - Use %X{payment_id} → prints ONLY that key's VALUE          │
│      output: P123   (note: key name NOT printed, only value)    │
│                                                                 │
│  Option B → JSON Encoder (LogstashEncoder)                      │
│    - includeMdc=true (this is DEFAULT, no need to set it)       │
│    - MDC fields auto appear as JSON key:value pairs             │
│      output: { "payment_id": "P123", "user_id": "U1234" }       │
│                                                                 │
│  Writes final output                                            │
└─────────────────────────────────────────────────────────────────┘
```

> **Key insight from the instructor:** Even though you're just calling `log.info("payment is successful")` — with no extra parameters — the MDC data still shows up in the log. This happens because when Logback converts your log statement into an `ILoggingEvent` object, it **copies the current thread's MDC map** into the event's `mdcPropertyMap` field. The appender then reads this field during formatting.

## Implementation Code

### Controller

```java
@RestController
public class PaymentController {

    Logger log = LoggerFactory.getLogger(PaymentController.class);

    @GetMapping("/payments")
    public String getPayments() {

        // Put context into MDC (key-value)
        MDC.put("payment_id", "P123");
        MDC.put("user_id", "U1234");

        // Logging framework automatically adds MDC data
        // with each log statement — no need to pass manually
        log.info("payment is successful");

        MDC.clear(); // Important! (explained in Step 2)

        return "successfully fetched all payments";
    }
}
```

### logback-spring.xml — Three Appender Configurations

```xml
<!-- Appender 1: Print only a specific MDC value -->
<appender name="CONSOLE_WITH_MDC"
          class="ch.qos.logback.core.ConsoleAppender">
    <encoder>
        <!-- %X{payment_id} prints ONLY the value of payment_id key -->
        <pattern>%d %level %logger - %msg - %X{payment_id}%n</pattern>
    </encoder>
</appender>

<!-- Appender 2: Print ALL MDC values -->
<appender name="CONSOLE_WITH_ALL_MDC"
          class="ch.qos.logback.core.ConsoleAppender">
    <encoder>
        <!-- %X prints ALL key=value pairs from MDC -->
        <pattern>%d %level %logger - %msg - %X%n</pattern>
    </encoder>
</appender>

<!-- Appender 3: JSON output — MDC included by default -->
<appender name="CONSOLE_WITH_JSON"
          class="ch.qos.logback.core.ConsoleAppender">
    <encoder class="net.logstash.logback.encoder.LogstashEncoder">
        <includeMdc>true</includeMdc> <!-- true by default, no need to write -->
    </encoder>
</appender>

<!-- Wire all 3 appenders to PaymentController logger -->
<logger name="com.concepts.PaymentController"
        level="INFO"
        additivity="false">
    <appender-ref ref="CONSOLE_WITH_MDC"/>
    <appender-ref ref="CONSOLE_WITH_ALL_MDC"/>
    <appender-ref ref="CONSOLE_WITH_JSON"/>
</logger>
```

**Appender 1** (`%X{payment_id}` — only value, no key name):

**Appender 2** (`%X` — all MDC values as key=value):


## Quick Cheat Sheet

| What you want | Pattern to use | Output format |
|---|---|---|
| All MDC values | `%X` | `key1=val1, key2=val2` |
| One specific MDC value | `%X{keyName}` | `val1` (only value, no key) |
| JSON with MDC | `LogstashEncoder` + `includeMdc=true` | `"key1": "val1"` |

The appender reads this field during formatting. That's why MDC data appears in every log statement without you doing anything extra.

# Step 2 — Log Pollution: What it is, Why it Happens & How to Prevent it

---

## The Problem — Why do we even need `MDC.clear()`?

At the end of Step 1, you saw `MDC.clear()` in the code. Let's understand **why it's critically important.**

Remember: MDC is a **per-thread key-value map.** Every thread has its own MDC map.

Now in modern applications (especially Spring Boot), we don't create a new thread for every request. Instead, Spring Boot uses a **ThreadPoolExecutor** — a pool of pre-created threads that are **reused** across multiple requests.

Here's where the problem begins...

---

## What is Log Pollution?

> **Log Pollution** = When logs of one request contain MDC data that actually belongs to a completely different (previous) request — because the same thread was reused without clearing its MDC.

---

## How Log Pollution Happens — Step by Step

```
┌──────────────────────────────────────────────────────────────────┐
│                        THREAD POOL                               │
│                                                                  │
│                    ┌──────────┐  ┌──────────┐                    │
│                    │ Thread-1 │  │ Thread-2 │                    │
│                    └──────────┘  └──────────┘                    │
└──────────────────────────────────────────────────────────────────┘

STEP 1: Request-A (for user1) arrives
        → picks Thread-1 from pool
        → MDC.put("user_id", "user1")
        → does its work, logs events

   Thread-1 MDC:
   ┌─────────────────────┐
   │  user_id = user1    │  ← set by Request-A
   └─────────────────────┘

STEP 2: Request-A completes
        → Thread-1 goes BACK to the pool
        → BUT MDC is NOT cleared ❌

   Thread-1 MDC still has:
   ┌─────────────────────┐
   │  user_id = user1    │  ← still sitting here!
   └─────────────────────┘

STEP 3: Request-B (for user2) arrives
        → picks Thread-1 again from pool (same thread!)
        → MDC.put("user_id", "user2")
        → does its work, logs events

   BUT WAIT — Thread-1 MDC now has:
   ┌─────────────────────┐
   │  user_id = user1    │  ← leftover from Request-A ❌
   │  user_id = user2    │  ← set by Request-B
   └─────────────────────┘

RESULT: Logs for Request-B (user2) will show user1's data too!
        → This is LOG POLLUTION ☠️
```

> **The instructor's exact words:** *"You are processing a request for user2 but in the logs you will see user1. That's log pollution."*

---

## How to Prevent Log Pollution — `MDC.clear()`

The fix is simple: **always clear the MDC when the request finishes.**

```
┌──────────────────────────────────────────────────────────────────┐
│                        THREAD POOL                               │
│                    ┌──────────┐  ┌──────────┐                    │
│                    │ Thread-1 │  │ Thread-2 │                    │
│                    └──────────┘  └──────────┘                    │
└──────────────────────────────────────────────────────────────────┘

STEP 1: Request-A (user1) picks Thread-1
        → MDC.put("user_id", "user1")
        → does work, logs events
        → MDC.clear() ✅  ← clears before returning thread

   Thread-1 MDC after clear:
   ┌─────────────────────┐
   │       EMPTY         │  ← clean slate
   └─────────────────────┘

STEP 2: Thread-1 goes back to pool — MDC is clean ✅

STEP 3: Request-B (user2) picks Thread-1
        → MDC.put("user_id", "user2")
        → logs only have user2's data ✅

   Thread-1 MDC:
   ┌─────────────────────┐
   │  user_id = user2    │  ← only Request-B data. Clean! ✅
   └─────────────────────┘
```

---

## Implementation — The Right Way to Use MDC

The safest pattern is to wrap your MDC usage in a **try-finally block**, so the clear always runs — even if an exception is thrown:

```java
@RestController
public class PaymentController {

    Logger log = LoggerFactory.getLogger(PaymentController.class);

    @GetMapping("/payments")
    public String getPayments() {

        MDC.put("payment_id", "P123");
        MDC.put("user_id", "U1234");

        try {
            log.info("payment is successful");
            // ... more business logic
            return "successfully fetched all payments";

        } finally {
            // Always runs — even if exception occurs
            // Prevents log pollution for the next request
            // that picks up this thread
            MDC.clear(); // ✅ Clean up after yourself
        }
    }
}
```

> **Why `finally`?** If you just put `MDC.clear()` at the end of the method normally, and an exception is thrown before it — the clear never runs. The `finally` block **always executes**, so the MDC is guaranteed to be cleaned up no matter what.

---

## A Note on "Where" to Clear MDC

The instructor also points out that in real production applications, you won't be calling `MDC.put()` and `MDC.clear()` inside your controller methods directly. You'll do it in a **Filter** — which is the single entry and exit point for every HTTP request. This is the cleanest approach, and we'll see the full implementation in **Step 4** when we build the Correlation ID Filter.

The pattern in the filter looks exactly the same:

```java
try {
    MDC.put("correlationId", someUniqueId);
    filterChain.doFilter(request, response); // your entire request runs here
} finally {
    MDC.clear(); // guaranteed cleanup when request exits
}
```

---

## Summary — MDC Lifecycle in a Request

```
Request arrives
      │
      ▼
┌─────────────────────────┐
│  MDC.put(key, value)    │  ← Set context at entry point
└────────────┬────────────┘
             │
             ▼
┌─────────────────────────┐
│  Business Logic Runs    │  ← All log.info/error/warn calls
│  log.info("...")        │    automatically carry MDC data
│  log.error("...")       │
└────────────┬────────────┘
             │
             ▼
┌─────────────────────────┐
│  MDC.clear()            │  ← ALWAYS in finally block
│  (in finally block)     │    Prevents log pollution
└─────────────────────────┘
      │
      ▼
Thread returns to pool — clean MDC ✅
```

---

## Interview Tips ⚡

> **Q: What is log pollution and how do you prevent it?**
> A: Log pollution happens when a thread from the thread pool is reused for a new request, but the MDC from the previous request was never cleared. The new request's logs then carry stale data from the old request. Prevention: always call `MDC.clear()` in a `finally` block when the request is done.

> **Q: Why use `finally` for `MDC.clear()`?**
> A: Because if an exception is thrown before the clear, a plain `MDC.clear()` at the end of the method will never execute. `finally` guarantees it always runs.

> **Q: Why does this problem exist in Spring Boot specifically?**
> A: Spring Boot uses `ThreadPoolExecutor` by default, meaning threads are reused across requests. If MDC isn't cleared, the next request using the same thread will inherit the previous request's MDC data.

# Step 3 — MDC & Async Threads: The Problem + TaskDecorator Solution

---

## The Problem — MDC Doesn't Cross Thread Boundaries

So far we know:
- MDC is a **per-thread** key-value map
- Every thread has its **own separate MDC**

Now here's a very common real-world scenario — you have a parent thread handling a request, and it calls an `@Async` method, which **spins up a new (child) thread.**

The question is: **does the child thread automatically get the parent thread's MDC data?**

**The answer is NO.** ❌

When a new thread is created, it starts with a **completely empty MDC** — it has no knowledge of what the parent thread put into its MDC.

---

## The Solution — TaskDecorator

> **Important note from instructor:** `TaskDecorator` is a feature of the **Spring framework** — it has nothing to do with the logging framework (Logback/Log4j2). It just happens to be the tool we use to solve the MDC propagation problem.

### What is TaskDecorator?

`TaskDecorator` is simply a **wrapper around a Runnable task.**

Before a task (Runnable) is submitted to the executor queue to be picked up by a child thread, `TaskDecorator` gives you a chance to **wrap it with extra logic** — in our case, copying the parent MDC into the child thread's MDC.

---

## How @Async Works Internally — Full Flow

This is the most important diagram of this step. Understanding this flow makes `TaskDecorator` crystal clear.

```
PARENT THREAD
     │
     │  paymentService.processPayment()  ← @Async call
     │
     ▼
┌─────────────────────────────────────────┐
│           Spring AOP Proxy              │
│   intercepts the @Async method call     │
└──────────────────┬──────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────┐
│      Creates a Runnable Task            │
│                                         │
│   Runnable task = () ->                 │
│     paymentService.processPayment()     │
│                                         │
│   (Not yet submitted to queue.          │
│    Still running on PARENT thread)      │
└──────────────────┬──────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────┐
│   Is TaskDecorator set?                 │
│                                         │
│   if (taskDecorator != null) {          │
│       decorate(runnable) ← called here  │  ← Still PARENT thread
│   }                                     │
└──────────────────┬──────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────┐
│         Our MdcTaskDecorator            │  ← Still PARENT thread
│                                         │
│  Step 1: Read parent MDC                │
│    contextMap = MDC.getCopyOfContextMap │

│                                         │

│    }                    this runs on ─┘ │
│                         CHILD thread    │
└──────────────────┬──────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────┐
│       Submitted to Executor Queue       │
└──────────────────┬──────────────────────┘
                   │
                   ▼

│                                         │
│    Executes the WRAPPED Runnable:       │
│                                         │

│                                         │

│       log.info(...) ← MDC data present  │

```

> **The instructor's key insight:** The `decorate()` method runs on the **parent thread** — so at that moment you still have access to the parent MDC. You read it, capture it in a variable, and then wrap the original Runnable with logic that sets this captured data into whatever child thread eventually picks up the task.

---

## Full Implementation Code

### Step 1: Create the MdcTaskDecorator

```java
@Component
public class MdcTaskDecorator implements TaskDecorator {

    @Override
    public Runnable decorate(Runnable runnable) {

        /*
         IMPORTANT: This entire method runs on the PARENT thread.
         So we have full access to parent thread's MDC right now.
        */

        // Step 1: Capture parent thread's MDC map
        Map<String, String> contextMap = MDC.getCopyOfContextMap();

        /*
         Step 2: Return a NEW Runnable (wrapper around original).
         This new Runnable is what the CHILD thread will execute.

         The wrapper does 3 things:
           a) Set parent MDC into child thread's MDC
           b) Run the actual task
           c) Clear child thread's MDC (prevent log pollution)
        */
        return () -> {
            if (contextMap != null) {
                // (a) Copy parent MDC into child thread's MDC
                MDC.setContextMap(contextMap);
            }
            try {
                // (b) Run the actual @Async method
                runnable.run();
            } finally {
                // (c) Always clean up child thread's MDC
                MDC.clear();
            }
        };
    }
}
```

### Step 2: Register TaskDecorator (Custom ThreadPoolExecutor)

> **Note from instructor:** If you are using Spring Boot's **default executor** (no custom ThreadPoolExecutor defined), Spring Boot **automatically picks up** your `MdcTaskDecorator` if it's registered as a `@Component` — you don't need to do anything extra.
>
> But if you have a **custom ThreadPoolExecutor**, you need to explicitly set it like this:

```java
@Configuration
@EnableAsync
public class AsyncConfig implements AsyncConfigurer {

    @Autowired
    private MdcTaskDecorator mdcTaskDecorator;

    @Override
    public Executor getAsyncExecutor() {

        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(8);
        executor.setMaxPoolSize(16);
        executor.setQueueCapacity(100);
        executor.setThreadNamePrefix("async-thread-");

        // Register our TaskDecorator here
        executor.setTaskDecorator(mdcTaskDecorator); // ✅

        executor.initialize();
        return executor;
    }
}
```

## Interview Tips ⚡

> **Q: Why doesn't `@Async` automatically propagate MDC to the child thread?**
> A: Because MDC is per-thread. When `@Async` creates a new thread, that thread starts with a completely empty MDC. It has no knowledge of the parent thread's data.

> **Q: How do you propagate MDC from parent thread to child thread in Spring?**
> A: Using `TaskDecorator`. It's a Spring framework feature (not a logging framework feature) that wraps the Runnable task before it's submitted to the executor queue. Since `decorate()` runs on the parent thread, we can read the parent MDC there, capture it, and inject it into the child thread's MDC inside the wrapped Runnable.

> **Q: Why do we call `MDC.clear()` inside the TaskDecorator's Runnable?**
> A: Because child threads also come from a thread pool and can be reused. If we don't clear the MDC after the child thread finishes its task, the next task picked up by that thread will inherit stale MDC data — log pollution again.

> **Q: Is TaskDecorator related to Logback or Log4j2?**
> A: No. It is purely a Spring framework feature. We just use it as a bridge to copy MDC data across thread boundaries.

## The Problem — How Do You Debug a Specific Request?

You can't. There's no way to distinguish which log line was produced by which request. This is the core problem.

## The Solution — Correlation ID

> A **Correlation ID** is simply a **unique identifier assigned to each request.** This same ID is attached to every single log event that request generates — across your entire application.

```
Without Correlation ID ❌
──────────────────────────────────────────
INFO - payment processed     ← which request?

──────────────────────────────────────────

INFO - user created       - correlationId=C1   ← Request 1
INFO - payment processed  - correlationId=C2   ← Request 2
INFO - payment failed     - correlationId=C3   ← Request 3
INFO - order placed       - correlationId=C2   ← Request 2
```

Now when your manager asks about a failed payment, the customer gives you their **Correlation ID** (which was sent back to them in the response header). You go to your log aggregation tool (Datadog, Splunk, etc.), search for that ID, and **instantly see only the logs for that request.**

## Where to Implement Correlation ID — Why a Filter?

We need to:
1. **Assign** a unique Correlation ID when the request **enters** the application
2. **Put it in MDC** so all log statements automatically carry it
3. **Send it back** in the response header so the client has it
4. **Clear the MDC** when the request **exits**

The best place for all of this is a **Filter** — because a Filter is the **first thing that runs** when a request arrives and the **last thing that runs** when a response goes out.

```
Incoming Request
      │
      ▼
┌─────────────────────────────────────────────────────────────────┐
│                      FILTER CHAIN                               │
│                                                                 │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │              CorrelationIdFilter  (our filter)           │   │
│  │                                                          │   │
│  │  ON REQUEST IN:                                          │   │
│  │    1. Check if X-CorrelationId header exists             │   │
│  │    2. If yes → reuse it                                  │   │
│  │       If no  → generate new UUID                         │   │
│  │    3. MDC.put("correlationId", id)                       │   │
│  │    4. response.setHeader("X-CorrelationId", id)          │   │
│  │    5. proceed → filterChain.doFilter(...)                │   │
│  │                                                          │   │
│  │         ↓ entire application runs here ↓                 │   │
│  │    (all log statements carry correlationId from MDC)     │   │
│  │                                                          │   │
│  │  ON RESPONSE OUT (finally block):                        │   │
│  │    6. MDC.clear()  ← prevents log pollution              │   │
│  └──────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
      │
      ▼

(all logs here automatically carry correlationId) ✅
      │
      ▼

```

> **Why do we check if the header already has a Correlation ID?**
> This becomes important in microservices. If Service-1 calls Service-2, it passes its Correlation ID in the request header. Service-2's filter should **reuse** that same ID — not generate a new one. This way all logs across all services for a single original request carry the **same Correlation ID.** We'll go deeper on this in Step 5.

### The CorrelationIdFilter

```java
@Component
public class CorrelationIdFilter extends OncePerRequestFilter {

    // Key used in MDC map
    public static final String CORRELATION_ID = "correlationId";

    // HTTP header name
    public static final String CORRELATION_HEADER = "X-CorrelationId";

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain)
            throws ServletException, IOException {

        // Step 1: Check if incoming request already has a
        //         Correlation ID in its header
        //         (important for microservice-to-microservice calls)
        String correlationId = request.getHeader(CORRELATION_HEADER);

        // Step 2: If not present, generate a fresh unique ID
        if (correlationId == null || correlationId.isBlank()) {
            correlationId = UUID.randomUUID().toString();
        }

        try {
            // Step 3: Put into MDC
            //   → now ALL log statements in this request
            //     will automatically carry this correlationId
            MDC.put(CORRELATION_ID, correlationId);

            // Step 4: Also send it back in the response header
            //   → client can use this ID to report issues later
            response.setHeader(CORRELATION_HEADER, correlationId);

            // Step 5: Continue the filter chain
            //   → entire request processing happens here
            filterChain.doFilter(request, response);

        } finally {
            // Step 6: ALWAYS clear MDC when request exits
            //   → prevents log pollution for next request
            //     that picks up this thread
            MDC.clear();
        }
    }
}
```

## Interview Tips ⚡

> **Q: What is a Correlation ID and why is it needed?**
> A: A Correlation ID is a unique identifier assigned to each incoming request. It is attached to every log event that request generates by storing it in MDC. This allows developers to filter all logs for a specific request from thousands of log lines — especially useful when debugging failures in production.

> **Q: Where is the best place to implement Correlation ID logic in Spring Boot?**
> A: In a Filter (specifically `OncePerRequestFilter`). It is the earliest entry point for every HTTP request and the last exit point for responses. This ensures every log statement in the entire request lifecycle carries the Correlation ID without any controller or service needing to handle it.

> **Q: Why do we check if the Correlation ID header already exists before generating a new one?**
> A: In a microservices architecture, Service-1 may call Service-2 and pass its Correlation ID in the request header. Service-2 should reuse that same ID so that all logs across all services for one original request share the same Correlation ID. If Service-2 always generated a new ID, you'd lose the ability to trace a request end-to-end across services.

> **Q: Why do we send the Correlation ID back in the response header?**
> A: So the client receives it and can share it with the support or development team when reporting an issue. The developer then uses that ID to search the log aggregation tool and instantly retrieve all logs for that specific request.

## Distributed Tracing vs Correlation ID — What's the Difference?

This is one of the most commonly asked interview questions. Let's be very clear:

```

│                                                                     │

│                                                                     │
│  What it does:                                                      │
│  → Tracks the PATH of a request across microservices                │
```

## The Key Question — Can Trace ID and Correlation ID Be the Same?

> The instructor says: *"Both are unique per request. Can they be the same? YES. And that's what many big tech companies do."*

If they are the same ID, your log aggregation tool (like Datadog) can do **both things with one ID:**
- Track which services were involved (from tracing data)
- Filter detailed logs across all services (from log events)

This is the industry standard approach. And this is exactly what we're going to implement.

## How Distributed Tracing Helps Us — The ServerHttpObservationFilter

When you add Micrometer + OpenTelemetry tracing dependencies to your Spring Boot app, it automatically registers a filter called **`ServerHttpObservationFilter`.**

Here's what this filter does — and this is the **critical insight** of this entire lecture:

```
┌─────────────────────────────────────────────────────────────────────┐
│                  ServerHttpObservationFilter                        │
│                  (comes FREE with Micrometer)                       │
│                                                                     │
│  When request arrives at Service-1:                                 │
│                                                                     │
│  Step 1: Does request header have a traceId?                        │
│    → NO (fresh request from client)                                 │
│    → Generate NEW Trace ID  e.g. T1                                 │
│                                                                     │
│  Step 2: Put traceId into MDC  ← THIS IS THE KEY PART               │
│    MDC now has: { traceId: T1 }                                     │
│                                                                     │
│  Step 3: When Service-1 calls Service-2                             │
│    → Automatically passes traceId T1 in request header              │
│                                                                     │
│  At Service-2, same filter runs:                                    │
│  Step 1: Does request header have a traceId?                        │
│    → YES (T1 passed from Service-1)                                 │
│    → Reuse T1, do NOT generate new one                              │
│                                                                     │
│  Step 2: Put T1 into MDC                                            │

│  Result: Both Service-1 and Service-2 logs carry T1 ✅               │
```

> **The instructor's key insight:** *"Distributed tracing not only generates a Trace ID — it also puts it into the MDC. So when you do log.info(), this trace ID automatically comes into your log statement. You don't need a separate filter for correlation ID — tracing already handles it."*

This means:
- You get **free MDC propagation** across services via tracing
- Every log statement **automatically carries the trace ID**
- No need to manually pass correlation ID in headers — tracing does it

```java
@Component
public class CorrelationIdFilter extends OncePerRequestFilter {

    public static final String CORRELATION_ID     = "correlationId";
    public static final String CORRELATION_HEADER = "X-CorrelationId";

    // Tracer comes from Micrometer — gives us access to current traceId
    @Autowired
    private Tracer tracer;

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain)
            throws ServletException, IOException {

        try {
            /*
             Step 1: Try to get the traceId from Micrometer Tracer
             (ServerHttpObservationFilter already ran before this
              and set the traceId, so it's available here)

             Priority:
               → If traceId exists → reuse it as correlationId
                 (same ID for tracing + logging — industry standard)
               → If traceId is null (tracing disabled) → generate
                 fresh UUID so correlation logging still works
            */
            String uniqueId = tracer.currentSpan()
                                    .context()
                                    .traceId();

            if (uniqueId == null) {
                // Fallback: tracing is disabled or not available
                uniqueId = UUID.randomUUID().toString();
            }

            /*
             Step 2: Put correlationId into MDC
             Now ALL log statements in this request automatically
             carry this ID — in controller, service, repository etc.
            */
            MDC.put(CORRELATION_ID, uniqueId);

            /*
             Step 3: Send correlationId back in response header
             Client receives this and can share it for debugging
            */
            response.setHeader(CORRELATION_HEADER, uniqueId);

            // Step 4: Continue filter chain
            // Entire request processing happens here
            filterChain.doFilter(request, response);

        } finally {
            /*
             Step 5: ALWAYS clear MDC
             Prevents log pollution when thread is reused
            */
            MDC.clear();
        }
    }
}
```

## Complete Summary of All Concepts

| Concept | What it is | Problem it solves |
|---|---|---|
| **MDC** | Per-thread key-value map | Auto-attaches context to every log statement |
| **MDC.clear()** | Clears MDC map | Prevents log pollution in thread pools |
| **TaskDecorator** | Wrapper around Runnable | Copies parent MDC to child thread in @Async |
| **Correlation ID** | Unique ID per request | Filter all logs for one specific request |
| **Filter** | Entry/exit point for HTTP | Best place to set + clear Correlation ID |
| **Distributed Tracing** | Tracks request path across services | Shows which service called which + timing |
| **Trace ID = Correlation ID** | Same ID used for both | One ID serves both tracing + log filtering |

## Final Interview Tips ⚡

> **Q: How do you achieve distributed logging in a microservices architecture?**
> A: Using MDC + Correlation ID + Distributed Tracing together. Each request gets a unique Trace ID via Micrometer's `ServerHttpObservationFilter`, which is also placed into MDC automatically. A custom `CorrelationIdFilter` reuses this same Trace ID as the Correlation ID and sends it back in the response header. Since Micrometer automatically passes the Trace ID in headers between services, all downstream services reuse the same ID. Every log statement across all services carries this ID, allowing a log aggregation tool like Datadog to filter all logs for a specific request with a single search.

> **Q: Why is Trace ID and Correlation ID kept the same in production?**
> A: Because both are unique per request. Using the same ID means a developer only needs one ID to both track the request path (via Jaeger/tracing tool) and filter detailed logs (via Datadog/log aggregation tool). It simplifies debugging significantly.

> **Q: What happens if distributed tracing is disabled? Will correlation logging break?**
> A: No. In the `CorrelationIdFilter`, we first try to get the Trace ID from Micrometer's `Tracer`. If it returns null (tracing disabled), we fall back to generating a fresh UUID. So correlation logging works independently of tracing.

> **Q: How does MDC data flow from Service-1 to Service-2?**
> A: It doesn't flow directly through MDC. Micrometer automatically passes the Trace ID in the HTTP request header when Service-1 calls Service-2. Service-2's `ServerHttpObservationFilter` reads this header, reuses the same Trace ID, and puts it into Service-2's own MDC. The `CorrelationIdFilter` then also picks it up and puts it as the Correlation ID. So the same ID ends up in MDC of both services.
